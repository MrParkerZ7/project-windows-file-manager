## Concept

The 3a redesign makes two choices the code cannot explain to a later reader, and both are expensive to reverse.

**The first is a resource layer.** Today there is no `ResourceDictionary` anywhere in the tree (`App.xaml` is seven lines with an empty `<Application.Resources>`), `MainWindow.xaml` holds 78 `<Style>` blocks of which only 6 are keyed, and 70 distinct hex literals are typed inline. After T-001/T-003 the same colours arrive through `{DynamicResource}` brush keys defined in a theme dictionary set. A maintainer who opens the new XAML, sees a semantic brush key where a `#CFD8DC` used to be, and "fixes" it back to a literal — or swaps `DynamicResource` for `StaticResource` because it profiles marginally faster — silently destroys the seam that makes the follow-on theme goal (4a) a dictionary swap instead of a 3,000-line rewrite. Nothing in the build catches either mistake: StyleCop and the .NET analyzers read C#, not XAML, and `TreatWarningsAsErrors` (ADR-009) therefore has no opinion about a resource key.

**The second is a frame.** The 260px | 1px | 1fr | 1px | 360px tool-window grid, the fixed chrome band heights (34 / 38 / 30 / 36 / 26 / 40 / 26), the two `GridSplitter`s where zero exist today, and the split of one 2,796-line file into per-panel `UserControl`s are a structural commitment. The decomposition boundary is not arbitrary — it is drawn on the tool-window edges the artboard defines — and it deliberately does **not** introduce per-panel ViewModels, because that would quietly undo ADR-002.

This task writes the record: what was chosen, against which lines of which files, what it costs, and — the clause that earns the ADR its keep — the small set of grep-checkable invariants under which the 4a theme goal costs one new dictionary and zero changes to any view. It ships no code. **It also invents nothing:** the ADR is transcribed from the shipped tree, and where this spec sketches a shape it is a sketch, not a contract (§ Detail's banner). Its whole value is that the next person to touch the theme dictionaries or the shell can read *why* before they read *what*.

### `## Decision`
Six numbered sub-decisions, each stated *against the code that implements it* (house rule) — i.e. each quotes the shipped file it describes. Full mechanics in § Detail:

1. **A layered token dictionary set** (palette values → semantic tokens → component styles), merged once in `App.xaml`, in a fixed, load-bearing order.
2. **`DynamicResource` for anything a theme could change; `StaticResource` for structure** — with the rule table and the two places `DynamicResource` is illegal.
3. **Keyed styles only during the epic; no implicit (`TargetType`-without-`x:Key`) styles** while the legacy monolith is still in the tree.
4. **The IDE frame as the decomposition seam** — `UserControl` boundaries drawn on tool-window edges, in the `WindowsFileManager.Views.*` namespace, with `GridSplitter`s in the two 1px columns, splitter widths persisted at drag-completion, and results-column alignment by fixed widths rather than shared sizing.
5. **No per-panel ViewModels** — panels inherit the single `MainViewModel` `DataContext`. ADR-002 is untouched.
6. **The 4a seam** — the invariants under which a later theme is one new palette dictionary and zero view edits, stated as checkable rules rather than as a promise.

## 1 · The token layer the ADR records — *shape normative, all names `⟨illustrative⟩`*

**Three dictionaries merged in `App.xaml` in a fixed order.** Order is load-bearing and that fact **is** normative: `StaticResource` cannot resolve a forward reference, so a component style whose `BasedOn` points at a base style fails at parse unless the dictionary defining it is merged earlier. The palette dictionary must be **first** (lowest merge index) because it is the theme-swap slot.

```xml
<!-- ⟨illustrative⟩ src/WindowsFileManager/App.xaml — quote the shipped block instead -->
<Application.Resources>
  <ResourceDictionary>
    <ResourceDictionary.MergedDictionaries>
      <ResourceDictionary Source="Themes/Palette.Broadsheet.xaml"/>   <!-- index 0 — the 4a swap slot -->
      <ResourceDictionary Source="Themes/Tokens.xaml"/>               <!-- index 1 -->
      <ResourceDictionary Source="Themes/Controls.xaml"/>             <!-- index 2 -->
    </ResourceDictionary.MergedDictionaries>
  </ResourceDictionary>
</Application.Resources>
```

`Source` is the same-assembly relative form; `.xaml` under a `UseWPF` SDK project defaults to build action `Page`, so these compile to BAML — no loose-file I/O at startup. **The folder name is not magic** (normative caveat, whatever the folder ended up called): WPF's generic-theme lookup applies only to a `Themes/generic.xaml` consumed by a custom `Control`'s `DefaultStyleKey`. This epic ships `UserControl`s and `Style`s, not custom `Control`s, so `AssemblyInfo.cs`'s existing `[assembly: ThemeInfo(ResourceDictionaryLocation.None, ResourceDictionaryLocation.SourceAssembly)]` stays exactly as it is.

**Palette dictionary — values only.** One `Color` and one `SolidColorBrush` per canvas token, keys mirroring the CSS custom-property names so the canvas and the code stay diff-able. The **values** are normative (they are the design system); the **key names** are `⟨illustrative⟩`:

| Canvas token | `x:Key` `⟨illustrative⟩` | Value (normative) |
|---|---|---|
| `--color-bg` | `Color.Bg` / `Brush.Bg` | `#F3F2F2` |
| `--color-surface` | `Color.Surface` / `Brush.Surface` | `#EAE9E9` |
| `--color-text` | `Color.Text` / `Brush.Text` | `#201E1D` |
| `--color-accent` | `Color.Accent` / `Brush.Accent` | `#0088B0` |
| `--color-accent-2` | `Color.Accent2` / `Brush.Accent2` | `#D6006C` |
| `--color-divider` | `Color.Divider` / `Brush.Divider` | `#29201E1D` |
| `--color-neutral-100…900` | `Color.Neutral100…900` | `#F8F4F4` `#EAE7E7` `#D7D3D3` `#BAB6B6` `#9B9797` `#7D7979` `#605D5D` `#444141` `#2D2B2B` |
| `--color-accent-100…900` | `Color.Accent100…900` | `#E9F8FF` … `#0A303E` |
| `--color-process-yellow` | `Color.ProcessYellow` | `#EDBB00` |

**The `color-mix` translation rule** — normative, and the ADR states it once because two artboard hairlines use it and nobody should re-derive it: CSS `color-mix(in srgb, <c> N%, transparent)` becomes WPF `#AARRGGBB` with `AA = round(N × 2.55)`. So `--color-divider` (16% of `#201E1D`) → **`#29201E1D`**; the per-copy row rule (6% of text) → **`#0F201E1D`**; the design system's `.text-muted` (55%) → **`#8C201E1D`**; `::selection` (30% accent) → **`#4D0088B0`**. Record the caveat: an alpha brush composites against whatever is behind it, so a hairline over the surface colour reads a shade darker than the same hairline over the background — accepted, because that is exactly what the CSS does.

**Declaring the full ramp is not the same as using it** (normative, and the 4a guard depends on it). The palette declares all nine neutral and nine accent steps plus process-yellow because that is the design system; 3a *uses* the second accent at exactly one site — the action-bar phrase `will be recycled` (`<span style="color:var(--color-accent-2)">` in the artboard) — and does not use process-yellow at all. Generalising those into a meaning system is 4a. The ADR must say this explicitly or a later reader will read the ramp as licence.

**Semantic-token dictionary — aliases and scales.** Semantic brushes are *aliases*: declared with a `StaticResource` reference to a palette `Color` on a `SolidColorBrush`'s `Color` (resolving inside the dictionary layer, at load, once), and consumed from views by `DynamicResource`. Names below are `⟨illustrative⟩`; the *pattern* — surface·part·role, dotted, greppable — is the normative part:

```xml
<!-- ⟨illustrative⟩ -->
<SolidColorBrush x:Key="Brush.Window.Background"        Color="{StaticResource Color.Bg}"/>
<SolidColorBrush x:Key="Brush.TitleBar.Background"      Color="{StaticResource Color.Surface}"/>
<SolidColorBrush x:Key="Brush.ToolWindow.Header.Border" Color="{StaticResource Color.Divider}"/>
<SolidColorBrush x:Key="Brush.Toolbar.Background"       Color="{StaticResource Color.Neutral100}"/>
<SolidColorBrush x:Key="Brush.Splitter"                 Color="{StaticResource Color.Divider}"/>
<SolidColorBrush x:Key="Brush.Row.Divider"              Color="#0F201E1D"/>
<SolidColorBrush x:Key="Brush.Text.Muted"               Color="{StaticResource Color.Neutral600}"/>
<SolidColorBrush x:Key="Brush.Tab.Active.Underline"     Color="{StaticResource Color.Accent}"/>
```

`x:Key` accepts dots — it is a string key, not an identifier — so a dotted namespace is legal and greps cleanly. That property is normative because invariants TOK-1/TOK-2 depend on the keys being greppable by prefix; the exact prefixes are whatever shipped.

Non-colour scales live here too. **Chrome band heights are `Double`, not `GridLength`** (normative rationale; keys `⟨illustrative⟩`):

```xml
<!-- ⟨illustrative⟩ -->
xmlns:sys="clr-namespace:System;assembly=System.Runtime"
<sys:Double x:Key="Size.TitleBar">34</sys:Double>
<sys:Double x:Key="Size.TabStrip">38</sys:Double>
<sys:Double x:Key="Size.ToolWindowHeader">30</sys:Double>
<sys:Double x:Key="Size.Toolbar">36</sys:Double>
<sys:Double x:Key="Size.ColumnHeader">26</sys:Double>
<sys:Double x:Key="Size.GroupRow">32</sys:Double>
<sys:Double x:Key="Size.CopyRow">30</sys:Double>
<sys:Double x:Key="Size.ActionBar">40</sys:Double>
<sys:Double x:Key="Size.StatusBar">26</sys:Double>
<sys:Double x:Key="Size.RulesToolbar">32</sys:Double>
```

Applied as `Height="{StaticResource …}"` on the band's `Border`, with the containing `RowDefinition Height="Auto"`. The ADR records *why* a band height is a `Double` and not a `GridLength`: `Double` needs no converter, is directly settable on `FrameworkElement.Height`, and keeps the row definition trivially readable. **(Contrast the results-grid column widths, which *are* `GridLength` resources — § 4.)** The two panel widths (**260** Scope, **360** right stack) are the deliberate exception — they are literal `ColumnDefinition Width` values with `MinWidth`, because a `GridSplitter` makes them user-mutable and a token would imply a constant that is not one.

Spacing and radius follow the design system's own scale: 5 / 10 / 15 / 20 / 30 / 40 (`Thickness`), radii 1 / 2 / 4 (`CornerRadius`). Typography: body and heading families both resolve per Fork D, heading weight SemiBold 600, plus the artboard's sizes — body 13, heading 14, toolbar 12.5, meta 12, kicker 11 (uppercase, `.08em` → WPF has no letter-spacing on `TextBlock`; the ADR records that section kickers either fake spacing per-character or accept it as untracked, which is the honest statement).

**Component-style dictionary (T-003) — no colour definitions.** Tool-window header, primary/secondary button, editor tab, vertical splitter, toolbar chip, link-styled button (the artboard's `<a>` affordances), and the Scope `Match duplicates by` segmented control (two `RadioButton`s with a shared `GroupName`, templated as a segmented pair). Style names `⟨illustrative⟩`. Normative: **every colour inside these `Setter`s is a `DynamicResource` brush reference, and this dictionary defines no `Color`/`SolidColorBrush` of its own** (that is invariant TOK-3).

## 2 · `DynamicResource` vs `StaticResource` — the rule the ADR exists to fix in place *(entirely normative)*

| Reference kind | Mechanism | Why |
|---|---|---|
| Any `Brush` consumed by a view or a `Setter` | **`DynamicResource`** | Re-resolved on every lookup and tracked against dictionary change — a runtime palette swap propagates without rebuilding the visual tree |
| `Style="{...}"`, `BasedOn="{...}"` | **`StaticResource`** | A theme changes token *values*, never style *identity*; and `Style.BasedOn` is a plain CLR property, not a `DependencyProperty`, so `DynamicResource` on it is **illegal** and fails at parse |
| Converters (`BoolToVisibility`, `MiniPreview`, `FileTypeIcon`, …) | **`StaticResource`** | Stateless, theme-invariant, and cheaper resolved once |
| Sizes, spacing, radii, column widths | **`StaticResource`** | Theme-invariant. A density toggle is a separate, unscheduled decision |
| `DataTemplate`, `ItemsPanelTemplate` | **`StaticResource`** | Structure |
| Inside a `Binding` (`ConverterParameter`, `StringFormat`) | **`StaticResource` only** | Those are not `DependencyProperty`s; `DynamicResource` silently yields nothing there |

The cost the ADR must name plainly: **a mistyped `DynamicResource` key produces no error and no warning.** It resolves to `DependencyProperty.UnsetValue`, the property falls back to its default, and you get a black-on-transparent element at runtime — discovered by eye, in a build that ADR-009 otherwise guarantees is warning-free. `StaticResource` at least throws `XamlParseException` at load. This asymmetry is the single largest new failure mode the epic introduces, and the ADR states it as such rather than burying it.

Second cost, quantified where it matters: each `DynamicResource` installs a weak listener on the resource-lookup chain. In a static band that is free; inside a `DataTemplate` instantiated per duplicate-copy row it multiplies by row count. The rule the ADR records: **inside a hot `DataTemplate`, style the container once (`ItemContainerStyle`) rather than putting per-element `DynamicResource` on every child.**

Third, an enabling detail: palette brushes may carry `po:Freeze="True"` (`xmlns:po="http://schemas.microsoft.com/winfx/2006/xaml/presentation/options"` with `mc:Ignorable="po"`). Freezing is safe *because* the swap replaces the whole dictionary rather than mutating a brush, and frozen `Freezable`s skip change-notification bookkeeping. Record it only if it shipped.

## 3 · Keyed styles only, while the monolith is still standing *(normative)*

No implicit styles (a `<Style TargetType="Button">` without `x:Key`) go in `App.xaml` for the duration of the epic. Reason, concrete: `MainWindow.xaml`'s un-migrated regions and `Views/ProfileNameDialog.xaml` (50 lines) inherit application resources, so one implicit `Button` style would silently restyle the profile dialog and every legacy button mid-migration, with no diff to point at. Cost, stated honestly: every element in the new shell carries an explicit `Style="{StaticResource ...}"` — more markup than an implicit-style design would need. Promoting the settled styles to implicit once `MainWindow.xaml` is retired is a follow-on, not a regret.

## 4 · The frame as the decomposition seam

`UserControl` boundaries are drawn on the artboard's tool-window edges, and the resulting types live under **`WindowsFileManager.Views.*`**. That namespace choice is not cosmetic — it is a coverage decision, and it is normative. `tests/WindowsFileManager.Tests/coverlet.runsettings` includes `[WindowsFileManager]WindowsFileManager.Helpers*` and `[WindowsFileManager]WindowsFileManager.ViewModels*` and excludes `[WindowsFileManager]*Views*`. A control placed in, say, `WindowsFileManager.Controls` would match **neither** filter and would sit outside coverage by accident rather than by decision. Staying under `Views.*` makes both filters agree, and the ADR records that rule so the next control lands in the right place.

The shell grid, literally the artboard's `grid-template-columns: 260px 1px 1fr 1px 360px`:

```xml
<Grid.ColumnDefinitions>
  <ColumnDefinition Width="260" MinWidth="200"/>
  <ColumnDefinition Width="1"/>
  <ColumnDefinition Width="*"   MinWidth="480"/>
  <ColumnDefinition Width="1"/>
  <ColumnDefinition Width="360" MinWidth="280"/>
</Grid.ColumnDefinitions>
<GridSplitter Grid.Column="1" Width="7" Margin="-3,0"
              HorizontalAlignment="Center" VerticalAlignment="Stretch"
              ResizeBehavior="PreviousAndNext" ResizeDirection="Columns"
              Background="Transparent" ShowsPreview="False"/>
```

The ADR records the hit-target trick and why: the artboard's splitter is a **1px** rule, and a 1px hit target is unusable with a mouse and impossible with a touchpad. The visible hairline is the 1px column's own background brush; the `GridSplitter` sits on top, wider, with a negative horizontal margin so it overhangs into the neighbours without displacing them. (Exact width/margin: whatever T-005 shipped.) Same construction for the right stack's rows (Preview over Rules) with `ResizeDirection="Rows"`.

**Splitter persistence — recorded from T-005, and it does *not* narrow ADR-006.**
An earlier draft of this task asserted that splitter widths join the **window-geometry group**, captured only in `MainWindow_Closing` → `SaveWindowState` (SPEC-009 rule 12), as a deliberate narrowing of ADR-006. **T-005 shipped the opposite, and better, answer:** persistence fires on `GridSplitter.DragCompleted` — at mutation time, which is exactly what ADR-006 asks for. The `DragDelta` write-storm the geometry-group workaround was invented to dodge never materialises, because `DragCompleted` raises once per gesture, not once per pixel. What the ADR therefore records:

- **ADR-006 is honoured, not narrowed.** No exception clause is needed, and the ADR must not claim one — a false "we narrowed ADR-006" note would send a future reader hunting for a trade-off that was never made.
- **Splitter widths do not inherit the geometry hole.** SPEC-009 § Not implemented (line 119) records that window geometry is lost on a crash or force-kill *because* `SaveWindowState` runs only from `Window.Closing`. Splitter widths, written at drag-completion, survive it. The ADR states that asymmetry plainly — geometry at close, splitters at mutation — rather than implying one uniform cadence.
- **The fields, their type, their per-profile-vs-global placement, and the SPEC-009 edit belong to T-005**, not here. T-012 quotes what shipped in `AppSettings` and in SPEC-009's persistence-trigger table (line ~54) and rule list.
- **Cross-task agreement is a precondition.** If, at ADR-writing time, T-005's shipped code and SPEC-009's rules disagree about the cadence, T-012 **stops** and the disagreement is settled inside T-005. An ADR records a settled decision; it does not adjudicate a live spec-vs-code conflict, and writing one that picks a side would create exactly the kind of drift `docs/specs/_index.md` § Sync contract exists to prevent.

**Chrome contract**, straight off the artboard, as a table in the ADR (normative numbers): title bar 34 · tab strip 38 · tool-window header 30 · results toolbar 36 · column header 26 · group row 32 · copy row 30 · action bar 40 · rules toolbar 32 · status bar 26.

**Results-grid column alignment — recorded from T-007, `SharedSizeGroup` explicitly rejected.**
The results grid's column set is `28 / * / 130 / 90 / 70 / 90` with a 10px gutter and `0,12` padding. An earlier draft of this task named `Grid.IsSharedSizeScope` + `SharedSizeGroup` as the mechanism that keeps the header row and every data row aligned. **T-007 rejected it and shipped fixed widths instead**, and the ADR records the rejection *with its reason*, because a later maintainer reaching for `SharedSizeGroup` — the textbook answer to this exact problem — would reintroduce the regression:

- A shared-size scope must measure every participating column across **every** row that joins the scope, on every measure pass. Inside a virtualized list that can hold thousands of copy rows, that defeats `VirtualizingStackPanel` container recycling — the scope forces realization/measurement work proportional to the item count rather than to the visible window, which is the whole point of virtualization.
- The shipped mechanism: the five fixed widths are `GridLength` resources in the token layer (`⟨illustrative⟩` keys), referenced by `StaticResource` from both the column-header row and the row `DataTemplate`; the name column is `*` and absorbs the remainder. Because every row `Grid` is laid out at the same available width with the same fixed columns, the `*` column resolves identically in each — pixel alignment with **no cross-row measure pass**. (`GridLength` has a type converter, so `<GridLength x:Key="…">130</GridLength>` is valid dictionary content; this is the one place a `GridLength` token is right and a `Double` is not.)
- The ADR states the cost honestly: fixed widths mean the columns do not auto-fit their content, so a long `Modified` format or a localized header can clip. That is accepted; virtualized scroll performance on a list of thousands of duplicate copies outranks it.

**One consequence worth calling out because it retires a known defect.** `ARCHITECTURE.md` § 9 records that `TabControl_SelectionChanged` (`MainWindow.xaml.cs:190`) does `(tabControl.SelectedItem as TabItem)?.Header as string` and then compares to `"Folder"` / `"History"` — but the History `TabItem` (`MainWindow.xaml:1715`) carries a `TextBlock` header, so the cast yields `null`, the `else` branch runs, and `IsHistoryActive` is **never true**. The new tab strip templates every tab header, so string-matching a header becomes structurally impossible; activation must key off `SelectedIndex`, `TabItem.Tag`, or `x:Name`. The ADR records that the frame *forces* the fix rather than merely enabling it — and that removing the § 9 row belongs to the task that ships the fix (T-004).

## 5 · No per-panel ViewModels — ADR-002 stays intact *(normative)*

Each panel `UserControl` inherits the `MainViewModel` `DataContext` through the visual tree; `MainWindow.xaml`'s `<Window.DataContext><vm:MainViewModel/></Window.DataContext>` remains the single composition point. No `ViewModelBase` subclass is added, no DI container appears, no messenger. Binding paths are unchanged — `{Binding DuplicateGroups}`, `{Binding UndoLastActionCommand}`, `{Binding StatusMessage}`, `{Binding ProfileNames}`, `{Binding ActiveProfileName, Mode=TwoWay}` all resolve exactly as they do today, just from a child control.

Cost, named: a `UserControl` has no statically-known `DataContext`, so XAML tooling loses IntelliSense and design-time rendering unless each control declares `mc:Ignorable="d"` + `d:DataContext="{d:DesignInstance Type=vm:MainViewModel, IsDesignTimeCreatable=False}"`. `IsDesignTimeCreatable=False` is required — `MainViewModel`'s parameterless constructor touches settings and the resource monitor, which must not run in a designer. The ADR makes this a rule, not a suggestion, because without it the epic trades one unreadable file for eleven un-navigable ones.

Second cost: the seven undo buttons collapsing to one (T-009) is *possible* today — `UndoLastActionCommand` already gates on `ActionHistory.Count > 0` at `MainViewModel.cs:665` — but SPEC-004:69 still documents its `CanExecute` as "always". ## 6 · The 4a seam — stated as invariants, not as a promise *(normative)*

4a is a **values-only** change plus additive keys. The proof is in the canvas itself: the 4a artboard is the 3a markup with the same custom-property *names* redeclared on the card element (`--color-bg: {{ tBg }}; --color-surface: {{ tSurface }}; --color-text: {{ tText }}; …`). The token names are the theme seam by construction. In WPF the equivalent is one assignment at the palette dictionary's merge index:

```csharp
// ⟨illustrative⟩ path and dictionary name
Application.Current.Resources.MergedDictionaries[0] =
    new ResourceDictionary { Source = new Uri(
        "/WindowsFileManager;component/Themes/Palette.Broadsheet.Dark.xaml", UriKind.Relative) };
```

— every `DynamicResource` brush re-resolves automatically. That is *free* if and only if four invariants hold. The ADR states them as numbered, greppable clauses; the greps below are written against the `⟨illustrative⟩` names and **must be rewritten against the shipped key prefixes and folder names before they are pasted into the ADR** — an invariant whose grep does not run is worse than no invariant:

| # | Invariant (normative) | Check — must return no rows (`⟨illustrative⟩` paths/prefixes) |
|---|---|---|
| **TOK-1** | No colour literal outside the palette dictionary | `grep -rnE '#[0-9A-Fa-f]{6,8}' --include=*.xaml src/WindowsFileManager \| grep -v 'Themes/Palette'` |
| **TOK-2** | No brush is referenced statically | `grep -rn 'StaticResource Brush\.' --include=*.xaml src/WindowsFileManager` |
| **TOK-3** | The component-style dictionary defines no colours | `grep -nE '<(SolidColorBrush\|Color)' src/WindowsFileManager/Themes/Controls.xaml` |
| **FRM-1** | Chrome heights come from tokens, not literals | `grep -rnE 'Height="(34\|38\|30\|36\|26\|40\|32)"' --include=*.xaml src/WindowsFileManager/Views` |

Also recorded: a named `Brushes.*` static (`Brushes.Black`, `Brushes.White`) violates TOK-1 in spirit and must be listed alongside it, since it greps differently.

And the successor rule, so the next author does not get it wrong: **a future theme ADR extends this one, it does not supersede it.** ADR-012 decides the *seam*; it deliberately decides nothing about a dark palette, a colour-meaning system, or a theme toggle. Those are 4a's to decide, and they will slot in as an additional palette dictionary plus additive semantic keys — provided the four invariants above held.

## 7 · The Consequences the ADR must not soften

**Negative — six, all real:**

1. **A typo'd `DynamicResource` key is invisible to every gate in the repo.** StyleCop and the .NET analyzers (ADR-009) read C#; nothing reads XAML resource keys. `TreatWarningsAsErrors` cannot help. Failure mode: an element renders with a default brush and nobody notices until a human looks.
2. **The whole token layer sits outside the coverage gate.** ADR-011 enforces 100% line/branch/method — over `Core`, `Application`, `Helpers*`, `ViewModels*`. The theme dictionaries and `Views/**` are `Page`/excluded, so a wrong colour, a wrong band height, and a broken splitter all ship with a green CI.
3. **Every visual check costs a full rebuild.** ADR-010 records that `dotnet watch` is web-only; verifying one hairline means stop app → `dotnet run --project src/WindowsFileManager` → re-select folders → re-scan → look. Multiply by the epic's surface count. **This is the epic's dominant cost and belongs in the record.**
4. **Custom `WindowChrome` re-implements what the OS gave for free** (Fork C, if that is what shipped) — Snap Layouts, maximize bounds under mixed DPI, high-contrast caption painting, double-click-to-maximize — all as `HwndSourceHook` code in `Views`, outside coverage, untestable in the xUnit process.
5. **Keyed-only styling is verbose**, and while the migration runs the app carries two styling systems at once — 70 inline hexes in the shrinking legacy file and the token layer in the new one — so a colour can legitimately appear "wrong" in one region and right in another until T-002 finishes.
6. **A shipped font grows the MSIX** (Fork D) and interacts with ADR-008's packaging.

**Positive:** no new `PackageReference` — `ResourceDictionary`, `GridSplitter`, `WindowChrome` and plain `GridLength`/`Double` dictionary resources are all in-box, so the zero-dependency UI of ADR-002/ADR-010 survives intact; 70 hex literals collapse to one dictionary; four grep-checkable invariants replace review-by-eye for the class of mistake that would break 4a; splitter widths persist at mutation time, extending ADR-006's guarantee to a new class of state rather than carving an exception out of it; the decomposition finally gives the shell reviewable diffs.

**Neutral:** `ThemeInfo` unchanged; the theme folder does not invoke generic-theme lookup; three merged dictionaries add negligible startup parse; `MainViewModel` stays `[ExcludeFromCodeCoverage]` and is not touched by this decision.

**Encoding and glyphs.** The ADR quotes artboard glyphs — `▾ ↶ ✕ ▢ ⋯ ≥ ↓ ·`. Write UTF-8 with the same encoding and line endings the existing `docs/adr/*.md` use; a BOM or a CRLF/LF flip produces a whole-file diff that hides the real change.

**The dirty working tree.** 11 modified test files (+1,690 lines) and 2 untracked paths from an interrupted `perfect-quality` run are sitting there. A bare `git commit -a` or `git add -A` folds someone else's unfinished coverage work into a docs commit and makes the ADR's own evidence trail unreadable. Path-scope the commit.

**Invariants that do not hold yet.** If T-002 has not finished retiring `MainWindow.xaml`, `TOK-1` legitimately returns rows. The honest ADR records the rule and a dated exception list ("as of `<date>`, N hexes remain in `MainWindow.xaml` pending T-002") rather than either lying or omitting the invariant.

**`d:DataContext` and the designer.** `IsDesignTimeCreatable=True` would let a designer construct `MainViewModel`, whose parameterless constructor touches settings and starts the resource monitor. The ADR mandates `False`. Worth stating because the "helpful" fix when design-time preview is blank is exactly to flip it to `True`.

**`x:Shared`.** Any non-`Freezable` resource reused across template instantiations (a `Storyboard`, a shared control instance) needs `x:Shared="False"` or every consumer gets the same object. Not needed for brushes, styles, or `GridLength`/`Double` scalars, but the ADR notes it so the first person to add one does not debug it twice.

## Risks

**The ADR is written too early and becomes fiction.** `docs/adr/README.md` is explicit that an ADR is written *from evidence*. This is not a hypothetical risk — it has already been demonstrated on this very spec: an earlier draft of § Detail confidently recorded (a) a splitter-persistence cadence T-005 did not ship, (b) `Grid.IsSharedSizeScope` as the alignment mechanism T-007 explicitly rejected, and (c) a full dictionary/key naming scheme no implementing task is bound to. All three read as settled fact. Authored before T-004…T-009 land, an ADR's statements about band heights, splitter construction, cadence and key names describe a plan, and the first maintainer to diff it against the shipped tree loses trust in the whole record. *Mitigation:* Fork B's recommended answer (write after T-011, from the tree), plus § Detail's illustrative banner and the acceptance name-trace pass.

**A wrong mechanism in the record is worse than no record.** An ADR that names `SharedSizeGroup` does not merely misdescribe — it *recommends*, because that is what an ADR is for. The next maintainer reading it would replace fixed widths with a shared-size scope and kill virtualization on a list of thousands of copy rows, believing they were restoring the documented design. Likewise a "we narrowed ADR-006" clause sends readers looking for a trade-off nobody made. *Mitigation:* record rejections **with their reasons** (the ADR states shared sizing was considered and rejected), and cross-read the shipped code for both clauses (acceptance cases 22–23).

**The 4a-compat claim is unfalsifiable until 4a is attempted.** "One dictionary swap, zero view changes" cannot be proven by anything in the repo today. *Mitigation:* state it as four checkable invariants plus a conditional, never as a guarantee — and rewrite the greps against shipped names so a future reader can actually run them. A grep that does not run is decoration.

**Silent invariant erosion.** TOK-1/TOK-2 are honoured only while somebody remembers to grep. The repo has no XAML gate, and ADR-009's `TreatWarningsAsErrors` cannot see resource keys. *Mitigation named in the ADR:* a `scripts/Check-DesignTokens.ps1` CI gate is the obvious follow-on, precedented by `Check-Coverage.ps1` (which ADR-011 accepted despite having no test of its own). It is deliberately **out of scope** here so T-012 stays code-free — but the ADR should propose it in `### Negative` so the gap is recorded rather than forgotten.

**Bundling two decisions weakens future supersession.** If the frame is later replaced but the token layer survives, a successor ADR must supersede a record that is half still-true — and `docs/adr/README.md` has no vocabulary for partial supersession. *Mitigation:* the ADR numbers its six sub-decisions so a successor can supersede by reference ("supersedes ADR-012 § 4-5"); Fork A's two-ADR alternative removes the risk entirely at the cost of duplicated Context.

**Register drift.** Four registers must agree. The repo has form here — `ARCHITECTURE.md` § 9 already documents a coverage `Exclude` entry (`*Helpers.Win32Api*`) pointing at a type that does not exist. A missing row is the same class of defect. *Mitigation:* the `grep -l 'ADR-012'` check in acceptance.

**Scope bleed into 4a.** The token *ramp* legitimately declares nine neutral steps, nine accent steps, a second accent, and process-yellow — and every one of those is a building block of 4a's colour-as-meaning system. It is very easy to slide from "the palette declares a second accent" to "destructive actions are magenta". The first is 3a; the second is 4a and is mis-targeted. *Mitigation:* the ADR states that 3a uses the second accent at exactly one artboard site and that generalising it is a follow-on; plus the human 4a-guard read in acceptance.

**The commit sweeps the in-flight test batch.** 11 modified test files sit unstaged in the tree. *Mitigation:* path-scoped commit, asserted in acceptance case 18.

**Fork C answered late.** If the window-chrome question is still open when T-004 builds, T-004 picks one and T-012 must record *that*, not the recommendation. *Mitigation:* the ADR is authored from the shipped `MainWindow.xaml` `WindowStyle`/`WindowChrome`, and acceptance case 12 cross-reads them.

**Under-selling the dev-loop cost.** The temptation is to write a confident ADR that reads as if the visual outcome were verified. It was not, and cannot be: no UI tests, no visual-regression harness, no hot reload. An ADR that omits this is the one that lets the next epic be estimated wrong. *Mitigation:* it is `### Negative` item 3, stated in ADR-010's own blunt register.

## Open decision

Four real forks. Each has a recommended default so an engineer is never blocked, but each is a judgement only the user can settle.

---

**FORK A — one ADR, or two?**
The repo's own rule (`docs/adr/README.md`): *"An ADR records **one** decision."* This task bundles two mechanisms — a token/resource layer and a shell/layout restructure.

- **Recommended: ONE ADR (ADR-012).** House precedent tolerates a coherent bundle: ADR-010 bundles the platform choice *and* its dev-loop consequence; ADR-011 bundles four mechanical changes (collector, script, runsettings scope, package removal) under one decision. The decision the user actually made was singular — *adopt 3a* — and the token layer and the frame are the two halves of landing it. Splitting them produces two ADRs whose Context sections are 80% identical.
- **Alternative: TWO** — `ADR-012` *Broadsheet design-token ResourceDictionary layer* + `ADR-013` *IDE tool-window frame and per-panel UserControl decomposition*. Argument for: they are independently reversible (the token layer survives any future layout), they have disjoint consequence sets, and a future layout ADR should supersede only the frame half. Cost: two files, **eight** register rows instead of four, and ADR numbers are never reusable if you later merge them.
- **If unanswered:** build the ONE-ADR shape. § Design gives the section order; the split map is in § Detail so the alternative costs a file move, not a rewrite.

---

**FORK B — `Proposed` now, or `Accepted` at the end?**
`docs/adr/README.md` defines a `Proposed` status and then notes *"No ADR in this repo currently holds this status"*; every one of the eleven carries `Accepted — <date> (commit <sha>)`.

- **Recommended: `Accepted`, authored at T-012 after T-011 lands**, with `Status: Accepted — <YYYY-MM-DD> (commits <first>…<last> of the 3a epic)`. This matches house practice, and — decisively — satisfies the README's *"written from evidence"* rule: the ADR describes the theme dictionaries and shell controls **as they exist on disk**, not as they were planned. An ADR written first would be a design doc wearing an ADR's clothes. The three corrections this spec absorbed (see § Risks, "written too early") are direct evidence that the plan and the shipped tree already diverge in at least three places.
- **Alternative:** land the body during T-001 as `Status: Proposed`, so T-002…T-011 commit messages can cite `ADR-012`, then flip to `Accepted` in T-012 with the real shas. Cost: a `Proposed` ADR sits in the tree for the length of the epic, and the README's observation about statuses goes stale.
- **This fork sets `when`.** The recommendation is why this task is `later`.

---

**FORK C — custom `WindowChrome`, or keep the native Windows title bar?**
The 3a artboard puts the app name, the `Photos cleanup ▾` profile switcher, **and** `— ▢ ✕` on one 34px row. Native WPF chrome cannot host the profile switcher, so artboard fidelity requires `WindowStyle="None"` + `System.Windows.Shell.WindowChrome`.

- **Recommended: custom `WindowChrome`.** The artboard is the requirement, and the profile switcher's move off the current full-width docked strip (`MainWindow.xaml:71`) is the whole point of the 34px row. Named costs the ADR must record: (1) **Windows 11 Snap Layouts break** on a templated maximize button unless `WM_NCHITTEST` returns `HTMAXBUTTON` for it (an `HwndSourceHook` — new code, in `Views`, coverage-excluded, untestable); (2) the classic `WindowChrome` **maximized-overflow bug** — a maximized window overhangs the work area by `ResizeBorderThickness` on multi-DPI setups, needing a `MaxHeight` clamp from `SystemParameters.WorkArea` on `WM_GETMINMAXINFO`; (3) **high-contrast themes** stop repainting the caption; (4) double-click-to-maximize and drag-to-restore must be re-implemented via `WindowChrome.CaptionHeight` + `IsHitTestVisibleInChrome="True"` on the interactive children.
- **Alternative:** keep the native caption bar and place the 34px strip immediately below it — Snap Layouts, DPI, accessibility and caption theming all stay free; the deviation is that `— ▢ ✕` sit on the OS caption instead of the artboard's row, and the strip carries only name + profile switcher. This is a **visible deviation from 3a** and must be recorded in the ADR as such if chosen.
- **If unanswered:** record custom `WindowChrome` with all four mitigations spelled out; it is what T-004 was scoped against. **Whatever T-004 actually shipped is what the ADR records** — read `MainWindow.xaml`'s `WindowStyle`, do not restate this fork's recommendation.

---

**FORK D — ship `Source Serif 4`, or fall back to a system face?**
The Broadsheet design system sets `--font-heading` **and** `--font-body` to `"Source Serif 4", system-ui, sans-serif` (`_ds/broadsheet-…/styles.css:52-54`). Source Serif 4 is not a Windows system font, so the app becomes serif-typeset only if the font ships.

- **Recommended: ship it.** SIL OFL 1.1 permits redistribution inside the MSIX. Add `<Resource Include="Assets\Fonts\*.ttf" />` to `WindowsFileManager.csproj` and set the token to `pack://application:,,,/Assets/Fonts/#Source Serif 4`. Ship the two static cuts actually used — Regular 400 and SemiBold 600 — not the variable file (WPF's variable-font support is partial; static cuts are ≈250–400 KB each). This grows the MSIX; note the interaction with **ADR-008**.
- **Alternative:** set the body/heading font tokens to a fallback chain and ship nothing — the design system itself declares `system-ui` as an accepted fallback, so this is a sanctioned degradation, not a violation. On Windows that resolves to Segoe UI and the "broadsheet" character is lost.
- **If unanswered:** record shipping-with-fallback: `FontFamily="pack://application:,,,/Assets/Fonts/#Source Serif 4, Segoe UI"` — WPF walks the comma list, so a missing resource degrades instead of throwing. Again: record the `.csproj` and the token as they shipped.
