## Concept

`src/WindowsFileManager/Views/MainWindow.xaml` is 2,796 lines / 222,866 bytes holding the entire product surface: three tabs, three docked side panels, a profile bar, a status bar, 78 `<Style>` blocks, 25 `ControlTemplate`s, 19 `DataTemplate`s, 21 help popups and 364 hardcoded hex-colour occurrences. Every remaining task in the 3a epic wants to edit a different part of it, and they cannot — the file is a single edit surface with no seams.

T-002 cuts the seams and nothing else. It is a **pure relocation**: every element, attribute, binding, trigger, template and popup string moves byte-for-byte into one of nine `UserControl`s grouped by role (chrome / screen / panel), the two application-level resource entries move into `Themes/`, and `MainWindow.xaml` shrinks to a composition root that names them. No visual change. No binding path change. No ViewModel change. No new feature. The success test is that a user cannot tell the build changed, while T-003 through T-011 each get a file they own outright.

Because the epic's later tasks were written against `MainWindow.xaml` line numbers, this task also ships the **translation table** (§ Interfaces) that converts every downstream line-anchored region into a post-decomposition file path. After T-002 lands, no downstream spec may cite a `MainWindow.xaml` line number; T-002 is therefore a **hard** predecessor of T-003 through T-011, not a soft one.

Four things make this non-trivial rather than a copy-paste, and they are what the Detail section is about: (1) the six keyed entries in `Window.Resources` — five converters and `HelpButtonStyle`, referenced 38 times across what become seven different files — stop resolving the moment their consumers leave the Window's XAML, so they must move to `Application.Resources` first, into the single `Themes/` folder the epic now shares; (2) six `x:Name` elements (`VideoPlayer`, `AudioPlayer`, and the two sliders and two mute buttons) are reached by nine code-behind handlers, and one *other* handler in a different region (`DuplicateGroups_SelectionChanged`) reaches across to stop them — a coupling that survives only if it is re-expressed as an explicit event through the composition root, and whose *source* (a `SelectionChanged`, not a property change) is a behavioural constraint T-008 inherits; (3) the `Header as string` match in `TabControl_SelectionChanged` means the History tab's `TextBlock` header takes the *else* branch and `IsHistoryActive` is never set true — a documented invariant (`docs/modules/ui.md` rule 18, SPEC-005:140, SPEC-006:127) that a well-meaning "clean up the header" during the move would silently flip; (4) T-001's design-token contract test must grow to cover the nine new files, on a parity basis, or 364 relocated hex literals quietly escape the net T-001 built.

The three defects the epic brief lists (the Delete popup's false permanence claim, the drifted match-type / folder-search / custom-rules popups, the `Contains`/`Ignore` vs `Include`/`Exclude` string at MainWindow.xaml:1094) are **not** fixed here — they travel verbatim into `DuplicatesScreen.xaml` and are T-010's to correct. T-002 moving them without fixing them is deliberate: mixing a text fix into a 2,700-line move destroys the only verification this task has, which is that nothing changed.

## Detail

### 1. Resource relocation — the change that must land first (and its one home)

`Window.Resources` (lines 16–69) is the **only** `.Resources` block in the 2,796 lines — verified: `grep -nE '<[A-Za-z]+\.Resources>'` returns exactly one hit, line 16. Every one of the other 77 `<Style>` blocks is an inline property-element style (`<Button.Style><Style TargetType="Button">…`) that applies to its own element only and therefore travels with its region needing nothing. That single block holds six keys used 38 times:

| Key | Type | Uses | Consumers after split |
|---|---|---|---|
| `HelpButtonStyle` | `Style TargetType="ToggleButton"` | 21 | ProfileBar, ScanScopeBar, FoldersScreen, DuplicatesScreen, FolderActionPanel |
| `BoolToVisibility` | `helpers:BoolToVisibilityConverter` | 10 | MainWindow, AppStatusBar, ScanScopeBar, FoldersScreen, DuplicatesScreen, FolderActionPanel, PreviewPanel |
| `InverseBool` | `helpers:InverseBoolConverter` | 4 | FoldersScreen, DuplicatesScreen |
| `InverseBoolToVisibility` | `helpers:InverseBoolToVisibilityConverter` | 1 | DuplicatesScreen (line 941 base-filter bar) |
| `MiniPreview` | `helpers:MiniPreviewConverter` | 1 | DuplicatesScreen (line 1595 thumbnail) |
| `FileTypeIcon` | `helpers:FileTypeIconConverter` | 1 | DuplicatesScreen |

`StaticResource` resolves at **parse time** by walking the element tree being parsed, then `Application.Resources`, then theme dictionaries. A `UserControl` is parsed as its own root — it is not yet attached to the `Window` — so the instant `{StaticResource HelpButtonStyle}` leaves `MainWindow.xaml` it throws `XamlParseException: Cannot find resource named 'HelpButtonStyle'`. Application-level is therefore mandatory, not stylistic — **and it is why T-003 cannot own the `HelpButtonStyle` move** (decision S2): the move is a precondition of T-002 compiling at all, so it belongs to T-002 or to nobody.

Create two dictionaries **in `Themes/`** (decision S1) and merge them:

```xml
<!-- src/WindowsFileManager/Themes/Converters.xaml -->
<ResourceDictionary xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
                    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
                    xmlns:helpers="clr-namespace:WindowsFileManager.Helpers">
    <helpers:BoolToVisibilityConverter x:Key="BoolToVisibility" />
    <helpers:InverseBoolConverter x:Key="InverseBool" />
    <helpers:InverseBoolToVisibilityConverter x:Key="InverseBoolToVisibility" />
    <helpers:MiniPreviewConverter x:Key="MiniPreview" />
    <helpers:FileTypeIconConverter x:Key="FileTypeIcon" />
</ResourceDictionary>
```

`Themes/Legacy.HelpButton.xaml` receives lines 23–68 **verbatim** — the whole `HelpButtonStyle` including its `ControlTemplate` (`Border x:Name="Circle"`, `Popup x:Name="HelpPopup"` with `IsOpen="{Binding IsChecked, RelativeSource={RelativeSource TemplatedParent}}"`, the `TextBlock` carrying `helpers:FormattedTextBehavior.FormattedText="{TemplateBinding Tag}"`, and the two `ControlTemplate.Triggers`). It needs `xmlns:helpers` for that attached property. The filename is T-003's choice, adopted here so the block is never relocated twice; T-003 edits its *contents* in place and its spec's relocation step is deleted.

`App.xaml` becomes — one folder, one merge list, fixed order:

```xml
<Application.Resources>
    <ResourceDictionary>
        <ResourceDictionary.MergedDictionaries>
            <ResourceDictionary Source="Themes/Broadsheet.Tokens.xaml" />   <!-- T-001, first -->
            <ResourceDictionary Source="Themes/Converters.xaml" />          <!-- T-002 -->
            <ResourceDictionary Source="Themes/Legacy.HelpButton.xaml" />   <!-- T-002; T-003 restyles in place -->
        </ResourceDictionary.MergedDictionaries>
    </ResourceDictionary>
</Application.Resources>
```

Tokens go first because `Legacy.HelpButton.xaml` may reference token keys once T-003 restyles it (`{DynamicResource}` would resolve regardless, but `{StaticResource}` inside a merged dictionary is order-sensitive, and keeping tokens first removes the whole class of question). There are no duplicate keys across the three files — assert it (acceptance).

`Window.Resources` is then deleted outright — not left empty. Note `SubtractConverter` and `PercentToWidthConverter` are **not** keyed and must not be added: `PercentToWidthConverter` is reached as `{x:Static helpers:PercentToWidthConverter.Instance}` (2 uses, both in AnalyticsPanel at 1918 and 1990), and `SubtractConverter` has zero XAML references (verified — it is referenced only by its own tests).

### 2. `xmlns` header every extracted file needs

`grep -o 'helpers:'` = 12 occurrences across three distinct members. Give each new `.xaml` only the prefixes it uses:

```xml
<UserControl x:Class="WindowsFileManager.Views.Panels.PreviewPanel"
             xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
             xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
             xmlns:d="http://schemas.microsoft.com/expression/blend/2008"
             xmlns:mc="http://schemas.openxmlformats.org/markup-compatibility/2006"
             xmlns:vm="clr-namespace:WindowsFileManager.ViewModels"
             xmlns:helpers="clr-namespace:WindowsFileManager.Helpers"
             mc:Ignorable="d"
             d:DataContext="{d:DesignInstance Type=vm:MainViewModel, IsDesignTimeCreatable=False}"
             d:DesignWidth="380" d:DesignHeight="800">
```

`IsDesignTimeCreatable=False` is load-bearing: `MainViewModel`'s parameterless constructor is the composition root — it builds a `SettingsService` over `%APPDATA%\WindowsFileManager\settings.json` and starts a `DispatcherTimer`. `True` would run all of that inside the XAML designer.

Which files need `xmlns:helpers`: `FoldersScreen` and `FolderActionPanel` (`helpers:TextBoxEnterKeyBehavior.Command`, 4 uses total), `AnalyticsPanel` (`x:Static helpers:PercentToWidthConverter.Instance`, 2 uses), plus `Themes/Legacy.HelpButton.xaml` (`FormattedTextBehavior`). No other file needs it.

### 3. Bindings — what survives untouched, and why

- **21 `{Binding DataContext.X, RelativeSource={RelativeSource AncestorType=Window}}`** (lines 303, 386, 604, 621, 640, 653, 676, 694, 1301, 1318, 1337, 1342, 1446, 1572, 1578, 1584, 1595, 1650, 1656, 1663, 1826). `AncestorType=Window` walks the **runtime** visual tree, and every UserControl is still a descendant of the one `MainWindow`. **Copy all 21 verbatim. Do not retarget them to `AncestorType=UserControl`** — that changes which element supplies `DataContext` and is a behaviour change disguised as tidying. (It also means the nine controls do not bind correctly when hosted outside a Window, which is why the smoke test asserts parse only, never binding.)
- **6 `ElementName` bindings** — verified all six source/target pairs are region-local, so no `NameScope` is crossed: `FolderPatternInput` :437 → :448, :457 (FoldersScreen); `FolderSearchDepthInput` :468 → :480 (FoldersScreen); `ThumbImg` :1598 → :1621 (DuplicatesScreen, and both ends are inside the *same* `DataTemplate` namescope); `SubfolderFilterBox` :2108 → :2118, `FileTypeFilterBox` :2287 → :2297, `FlattenFileTypeFilterBox` :2459 → :2469 (all FolderActionPanel). Zero cross-control `ElementName` exists — this is the single biggest reason the split is safe. **A UserControl creates its own NameScope; had one pair straddled the cut it would have failed silently** (a `System.Windows.Data Error` in Debug output, no exception, no visual clue).
- **2 `AncestorType=Grid`** (:1920, :1992) drive the wasted-space bar width off `<Grid Height="20">` at :1913/:1985. Both ancestor and descendant land in `AnalyticsPanel`. **Do not introduce a wrapper `Grid`** around the panel content — the nearest-ancestor lookup would retarget to it and the bars would size off the panel width.
- **`x:Name` inside `ControlTemplate`s** — `Circle`, `HelpPopup`, `SearchBorder` (:501), `UpBorder`/`DownBorder` (:608/:625 in FoldersScreen **and** :1305/:1322 in DuplicatesScreen), `RemoveBorder`/`RemoveText` (:1452/:1454), `ThumbImg` (:1598). Template namescopes are private, which is why `UpBorder` currently exists twice in one file legally. After the split they are in different files as well; leave both. Do not "deduplicate" them.
- **The Analytics panel's inner `DataContext` override** — `<StackPanel DataContext="{Binding Analytics}">` at :1851 is *inside* the extracted region, so `AnalyticsPanel`'s root inherits `MainViewModel` and re-scopes below it exactly as today.

### 4. The one real coupling: `DuplicateGroups_SelectionChanged` → the media players

Today, at MainWindow.xaml.cs:

```csharp
private void DuplicateGroups_SelectionChanged(object sender, SelectionChangedEventArgs e)
{
    try { VideoPlayer.Stop(); AudioPlayer.Stop(); }
    catch { /* Media elements may not be initialized yet */ }
}
```

The `ListView` is in the Duplication tab (:1543, `SelectionMode="Extended"`, `SelectedItem="{Binding SelectedDuplicateGroup}"`); the players are in the Preview panel (:2672, :2713). After the split they are **siblings**, and neither may know about the other. Solve it in the composition root:

1. `PreviewPanel.xaml.cs` exposes the capability, keeping the `try`/`catch` verbatim:
   ```csharp
   /// <summary>Stops both media players. Safe before the players are initialised.</summary>
   /// <remarks>Retirement owner: T-008 (see § Interfaces § Published API and its retirement contract).</remarks>
   public void StopMedia()
   {
       try { VideoPlayer.Stop(); AudioPlayer.Stop(); }
       catch { /* Media elements may not be initialized yet */ }
   }
   ```
2. `DuplicatesScreen.xaml.cs` keeps the `SelectionChanged="DuplicateGroups_SelectionChanged"` wiring on the `ListView` and turns the body into a raise:
   ```csharp
   /// <summary>Raised when the duplicate-group selection changes (source: ListView.SelectionChanged).</summary>
   /// <remarks>Retirement owner: T-008. The SelectionChanged source is contractual — see boundary case B6.</remarks>
   public event EventHandler? GroupSelectionChanged;

   private void DuplicateGroups_SelectionChanged(object sender, SelectionChangedEventArgs e)
       => this.GroupSelectionChanged?.Invoke(this, EventArgs.Empty);
   ```
3. `MainWindow.xaml` wires the two together by name:
   ```xml
   <TabItem Header="Duplication">
       <screens:DuplicatesScreen GroupSelectionChanged="OnDuplicateGroupSelectionChanged" />
   </TabItem>
   …
   <Border Grid.Column="2" … Visibility="{Binding IsPreviewVisible, Converter={StaticResource BoolToVisibility}}">
       <panels:PreviewPanel x:Name="PreviewPanelHost" />
   </Border>
   ```
   ```csharp
   private void OnDuplicateGroupSelectionChanged(object? sender, EventArgs e) => PreviewPanelHost.StopMedia();
   ```

**Rejected alternative, and why it is a downstream constraint rather than a preference:** having `PreviewPanel` subscribe to `MainViewModel.PropertyChanged` and stop on `SelectedDuplicateGroup` — or, as T-008 currently proposes, on `PreviewMediaUri`/`PreviewType` — is *not* equivalent. `SelectionMode="Extended"` means ctrl-clicking a second group raises `SelectionChanged` while `SelectedItem` — the anchor — does not change, so no property changes and no stop happens; media keeps playing over a different selection. Today that stops the media. This is pinned as boundary case B6 here and, per decision S3, is inherited by **T-008 as a regression row**: T-008 may delete `StopMedia()` and `GroupSelectionChanged` when it rebuilds the stack, but whatever replaces them must still be *sourced from the `ListView`'s `SelectionChanged`*.

**Why the members are published at all rather than kept internal:** the two controls are siblings under a composition root that is itself replaced by T-005; an `internal` member would work today but would force T-005 or T-008 to re-widen it, and a shared static/messenger would introduce a mediator this codebase does not have (no DI container, hand-rolled MVVM per ADR-002). Two documented members with a named retirement owner is the smallest honest surface.

`PreviewPanel` is constructed regardless of `IsPreviewVisible`, because `Visibility` affects layout and rendering only — the element tree is built either way, so `PreviewPanelHost` is never null. Same as today.

### 5. `ProfileNameDialog` ownership

Three handlers currently do `Owner = this` where `this` is the `Window`. In `ProfileBar.xaml.cs`, `this` is a `UserControl` — `Owner` requires a `Window` and this is a compile error, not a silent bug. Replace with:

```csharp
var owner = Window.GetWindow(this);
var dialog = new ProfileNameDialog(…);
if (owner is not null) { dialog.Owner = owner; }
if (dialog.ShowDialog() == true) { vm.CreateProfileCommand.Execute(dialog.EnteredName); }
```

The null guard matters for the XAML load test (fork 2A), where the control has no Window ancestor. `DeleteProfile_Click`'s two `MessageBox.Show` calls pass no owner today — leave them ownerless; adding one changes modal centring.

`ProfileBar.xaml.cs` reaches the VM the same way MainWindow does: `if (DataContext is not MainViewModel vm) { return; }`, which works because `DataContext` is inherited down the tree from the Window.

### 6. `IntegerTextBox_PreviewTextInput` — the two-consumer handler

Wired at :471 (`FolderSearchDepthInput`, FoldersScreen) and :2249 (the link-siblings layer box, FolderActionPanel). XAML event attributes bind to an instance method on the *root's* code-behind class, so each control needs its own method; only the body is shared.

```csharp
// src/WindowsFileManager/Views/Support/NumericInputFilter.cs
namespace WindowsFileManager.Views.Support;

/// <summary>Digit-only <see cref="System.Windows.Controls.TextBox"/> input filtering.</summary>
[ExcludeFromCodeCoverage]
internal static class NumericInputFilter
{
    /// <summary>Marks the composition handled when any character is not a digit.</summary>
    internal static void HandleDigitsOnly(TextCompositionEventArgs e)
    {
        foreach (var ch in e.Text)
        {
            if (!char.IsDigit(ch)) { e.Handled = true; return; }
        }
    }
}
```

Each consumer: `private void IntegerTextBox_PreviewTextInput(object sender, TextCompositionEventArgs e) => NumericInputFilter.HandleDigitsOnly(e);` — the `sender` parameter is unused today too, so dropping it from the shared method is behaviour-neutral and avoids a StyleCop/CA unused-parameter warning under `TreatWarningsAsErrors`.

An attached property (`helpers:NumericTextBoxBehavior.DigitsOnly="True"`) would be nicer XAML but puts a new type in `Helpers/` — inside the coverage `Include` — for no gain here. Deferred to T-011, which reworks these inputs anyway.

### 7. `TabControl_SelectionChanged` — preserve the dead branch

Stays in `MainWindow.xaml.cs` unchanged, including the guard `e.Source != tabControl`. That guard is still needed: `SelectionChanged` is a bubbling routed event and `DuplicateGroupsList`'s (:1547) and every `ComboBox`'s still bubble to the `TabControl` after the split, exactly as they do now — and `DuplicatesScreen` does **not** set `e.Handled`, so nothing changes.

The History `TabItem` keeps `<TabItem.Header><TextBlock Text="🕘 History" Foreground="#B8860B" FontWeight="Bold" /></TabItem.Header>` **verbatim in `MainWindow.xaml`**. `Header as string` is `null` for a `TextBlock`, so `header == "History"` is false and the *else* branch runs — `IsHistoryActive` is never set true, and the preview/analytics panels are **restored** rather than hidden on the History tab. That is documented three times (`docs/modules/ui.md` rule 18, SPEC-005:140, SPEC-006:127). Converting the header to `Header="History"` during the move revives the dead branch and changes what the user sees. Do not.

### 8. Build wiring — nothing to add to the `.csproj`

`UseWPF=true` gives the SDK default globs `Page Include="**/*.xaml"` (excluding the `ApplicationDefinition`), so all nine `UserControl`s and both `ResourceDictionary` files under `Views/` and `Themes/` are compiled automatically. `src/WindowsFileManager/WindowsFileManager.csproj` needs **no** edit; adding explicit `<Page>` items would produce duplicate-item errors.

### 9. Coverage — state this honestly

`tests/WindowsFileManager.Tests/coverlet.runsettings` is the single source of coverage scope:

```
Include: [WindowsFileManager.Core]*, [WindowsFileManager.Application]*,
         [WindowsFileManager]WindowsFileManager.Helpers*, [WindowsFileManager]WindowsFileManager.ViewModels*
Exclude: [WindowsFileManager]*Views*, [WindowsFileManager]*Helpers.Win32Api*, [WindowsFileManager]XamlGeneratedNamespace*
```

`WindowsFileManager.Views.Chrome|Screens|Panels|Support` are outside `Include` **and** matched by the `*Views*` `Exclude`. Every product line this task writes therefore lands outside the 100% gate. Each new code-behind still gets `[ExcludeFromCodeCoverage]` for belt-and-braces parity with `MainWindow`/`ProfileNameDialog`, as `docs/modules/ui.md` § Testing documents.

**The consequence, said plainly: the 100% gate will stay green through this refactor while proving nothing about it.** The measured surface is `Converters.cs` + `RelayCommand` + `ViewModelBase` and this task does not touch them. The gate's only value here is as a *negative* control — if `Check-Coverage.ps1` reports anything other than 100%, a measured type was changed by accident and the change is out of scope. (Test-project files this task edits — the `DesignTokenContractTests` glob in § 11, and `XamlLoadTests.cs` under fork 2A — are test code and are not themselves measured, so they do not weaken that negative control.)

**No new product code lands under the gate.** That is a design constraint, not an accident: `NumericInputFilter` is deliberately placed in `Views/Support/` rather than `Helpers/` for exactly this reason. If a reviewer proposes moving it to `Helpers/`, it needs `[ExcludeFromCodeCoverage]` or a full test.

Real verification is therefore: (a) `dotnet build -c Release` under `TreatWarningsAsErrors` + `CodeAnalysisTreatWarningsAsErrors` + StyleCop — this catches the compile-level breaks (`Owner = this`, missing `xmlns`, duplicate names in one namescope, undocumented public members); (b) `dotnet format --verify-no-changes`; (c) the **marker-parity greps** in acceptance, which mechanically prove the move lost nothing; (d) the extended `DesignTokenContractTests` glob (§ 11); (e) the XAML load test if fork 2A is taken; (f) the manual smoke run, watching the debugger's Output window for `System.Windows.Data Error:` lines — the only signal a binding broke, since WPF binding failures are silent by design.

### 10. Suggested XAML load test (fork 2A)

```csharp
// tests/WindowsFileManager.Tests/Views/XamlLoadTests.cs
[Theory]
[InlineData(typeof(ProfileBar))] … one row per control …
public void Control_loads_without_XamlParseException(Type controlType)
{
    Exception? captured = null;
    var t = new Thread(() =>
    {
        try
        {
            if (System.Windows.Application.Current is null)
            {
                var app = new System.Windows.Application();
                System.Windows.Application.LoadComponent(
                    app, new Uri("/WindowsFileManager;component/App.xaml", UriKind.Relative));
            }
            Activator.CreateInstance(controlType);
        }
        catch (Exception ex) { captured = ex; }

    t.SetApartmentState(ApartmentState.STA);
    t.Start();
    t.Join();
    captured.Should().BeNull();
}
```

Loading `App.xaml` is what populates `Application.Resources` with the relocated keys — without it every control that uses `HelpButtonStyle` throws, which is precisely the regression the test exists to catch. `xunit.runner.json` already disables both assembly and collection parallelism, so the single-`Application`-per-AppDomain rule is satisfied with no extra attributes. No `DataContext` is set, so no binding is exercised and `MainViewModel`'s disk-touching constructor never runs.

### 11. Design-token contract test — accepting T-001 Interfaces § 7

T-001 ships `DesignTokenContractTests` over a glob of XAML files. T-002 relocates 364 hex-colour occurrences out of `MainWindow.xaml` into nine new files; if the glob is not extended in the same commit, those literals leave T-001's net silently and the epic loses its only mechanical colour guard exactly when the surface fragments.

**Extend the glob to `Views/Chrome/*.xaml`, `Views/Screens/*.xaml`, `Views/Panels/*.xaml` in this commit** — on a strict **parity** basis:

- The nine files inherit the **same assertion mode** T-001 applied to `MainWindow.xaml`, not a stricter one. T-002 adds no literal and tokenises none, so whatever T-001 left permitted in `MainWindow.xaml` (an allowlist, a baseline count, a `// TODO: T-00x` exemption list — whichever shape T-001 chose) must be **transferred entry-by-entry to the file the literal now lives in**, keyed by the same colour value.
- **Read T-001's test before writing this.** If it asserts "zero raw hex", then by construction `MainWindow.xaml` was already at zero when T-002 started, the nine files inherit zero, and the extension is free. If it asserts against a baseline/allowlist, the transfer above is mechanical: the sum of the nine per-file allowlists must equal `MainWindow.xaml`'s pre-move allowlist exactly.
- **Never suppress to go green.** A red glob after the move means one of two things and both are in scope to fix here: an allowlist entry was not transferred, or a literal was accidentally added/changed during the move (which is also a marker-parity failure — see R4).
- The History `TabItem`'s `#FFF8DC`/`#DAA520` stay in `MainWindow.xaml`, which is already in the glob; they need no transfer.
- **If fork 1B is taken**, the glob covers `Views/Screens/*.xaml` by wildcard, so the five sub-files are picked up with no further edit — but the per-file allowlist split changes, and the transfer must follow the finer cut.

`Themes/*.xaml` is T-001's own glob territory and T-002 does not touch its coverage — except that `Legacy.HelpButton.xaml` arrives carrying `HelpButtonStyle`'s eight hex literals if T-001 did not tokenise them, in which case the same transfer rule applies to that file's allowlist entries.

## Edge cases

1. **`{StaticResource}` in a `UserControl` resolves at parse time, not attach time.** The moment a consumer leaves `MainWindow.xaml`, the Window's `Resources` are not on its lookup chain. Symptom: `XamlParseException` on construction, which in a `Visibility="Collapsed"` panel surfaces only when the user first opens it. This is why the resource move must land *before or with* the first extracted control, never after — and why `HelpButtonStyle`'s relocation cannot be deferred to T-003.

2. **Merged-dictionary order is only load-bearing for duplicate keys and `{StaticResource}` inside a dictionary.** Tokens are merged first so a restyled `Legacy.HelpButton.xaml` can use `{StaticResource}` token keys later without T-003 having to reorder `App.xaml`. Acceptance asserts zero duplicate keys across the three files precisely because a duplicate would resolve silently to the last-merged one.

3. **The History `TabItem` header is a `TextBlock`, so `Header as string` is `null`.** The `else if (header == "History")` branch in `TabControl_SelectionChanged` is dead code and `IsHistoryActive` is never set true. Documented in `docs/modules/ui.md` rule 18, SPEC-005:140, SPEC-006:127. Preserve exactly — the temptation to "simplify" the header during the move is the single highest-probability behaviour break in this task.

4. **Extended multi-select fires `SelectionChanged` without changing `SelectedItem`.** `DuplicateGroupsList` (:1543) is `SelectionMode="Extended"` with `SelectedItem="{Binding SelectedDuplicateGroup}"`. Ctrl-clicking a second group raises the event while the anchor stays put. Any reimplementation of the media-stop coupling that keys off a property change (`SelectedDuplicateGroup`, and equally `PreviewMediaUri`/`PreviewType`) silently loses this case. It is B6 here **and a T-008 acceptance row** under the retirement contract.

5. **WPF binding failures are silent.** Nothing throws, nothing renders differently in a Collapsed panel, and no test catches it. A crossed `ElementName` or a mistyped `DataContext.` path shows only as a `System.Windows.Data Error:` line in the debugger's Output window. Verified mitigation: all seven `ElementName` usages are region-local today, so the split crosses no namescope — but the debugger check stays in acceptance because a hand-typed path could still slip in.

6. **`x:Name` duplication is legal across `ControlTemplate` namescopes and illegal within one.** `UpBorder`/`DownBorder` exist twice today (:608/:625 and :1305/:1322) precisely because each pair sits in its own template. After the split they are in different files too. A reviewer "deduplicating" them would break two spinner controls.

7. **`AncestorType=Grid` is a nearest-ancestor walk.** The two analytics wasted-space bars (:1920, :1992) size off `<Grid Height="20">` immediately above them. Wrapping `AnalyticsPanel`'s content in any new `Grid` retargets nothing *provided* the local grid is still the nearest — but inserting a `Grid` *between* the bar and its 20px parent would. Keep the extracted content's element tree byte-identical.

8. **`Owner = this` stops compiling in a `UserControl`.** Caught by the compiler, but the *fix* has a runtime edge: `Window.GetWindow(this)` returns `null` when the control has no Window ancestor (the XAML load test, the designer). Guard the assignment; do not guard `ShowDialog()`.

9. **A `MediaElement` inside a `Visibility="Collapsed"` parent is still constructed.** `Visibility` affects layout and rendering only. `PreviewPanelHost.StopMedia()` is therefore always callable — matching today's behaviour, where the same `try`/`catch` exists for the pre-`InitializeComponent` window rather than the collapsed window.

10. **`SelectionChanged` still bubbles from inside the extracted screens to the `TabControl`.** The existing `e.Source != tabControl` guard is what stops a `ComboBox` or `ListView` selection from being mistaken for a tab change. `DuplicatesScreen` must **not** set `e.Handled` in its handler — today's code doesn't, and setting it would break nothing visible but would change the routed-event trace.

11. **`d:DesignInstance` with `IsDesignTimeCreatable=True` runs `MainViewModel`'s real constructor** — reading `%APPDATA%\WindowsFileManager\settings.json` and starting a `DispatcherTimer` inside the XAML designer. Always `False`.

12. **Adding a testable type to `Helpers/` or `ViewModels/` without `[ExcludeFromCodeCoverage]` puts it under the 100% gate instantly.** `NumericInputFilter` lives in `Views/Support/` for exactly this reason. If review moves it, it needs the attribute or a full test — and `docs/modules/ui.md` § Testing's exclusion table needs the new row.

13. **Explicit `<Page Include>` items in the `.csproj` collide with the SDK's default globs.** `UseWPF=true` already globs `**/*.xaml`. Adding them produces NETSDK1022 duplicate-item errors. This also means new files under `Themes/` are picked up with no `.csproj` edit.

14. **Two `Grid.Row="0"` borders in the Duplication tab are mutually exclusive, not a mistake.** :941 (base filters, `InverseBoolToVisibility` on `DuplicateMatchByRegex`) and :1017 (regex bar, `BoolToVisibility`) deliberately overlap in the same grid cell. Both must land in `DuplicatesScreen` and both converters must resolve there.

15. **A second, near-duplicate status readout lives inside the Duplication tab** (:1694–1713 — `StatusMessage` + `ResourceMemory`/`ResourceCpu`/`ResourceThreads`, duplicating the global bar at :118–196). It moves with `DuplicatesScreen` unchanged. Do not collapse it here — that is T-009's "one status bar" work, and doing it now breaks marker parity.

16. **The design-token contract test can go red for two opposite reasons and only one is a defect in this task.** A missing *transfer* (an allowlist entry left behind on `MainWindow.xaml`) and an accidental literal *change* both surface identically. Diff the pre- and post-move literal multiset per file: if the union is unchanged, it is a transfer bug; if the union differs, marker parity (R4) is also red and a literal was edited. Never reconcile by widening the exemption (F8).

17. **T-001's contract test may assert zero literals rather than an allowlist.** In that case `MainWindow.xaml` is already at zero when T-002 starts and the glob extension is free — but read the test before assuming; guessing its shape is how a "one-line glob edit" becomes a 364-literal tokenisation that belongs to T-001.

It must be committed separately, stashed, or discarded **before** T-002 starts — see Dependencies.

## Risks

**R1 — Silent binding breakage (highest).** WPF reports a failed binding as a Debug-output line and nothing else. A crossed `ElementName`, a mistyped `DataContext.` path, or a lost `RelativeSource` produces a blank control, not a crash — and with no UI tests and `Views` excluded from coverage, no gate catches it. *Mitigation:* all seven `ElementName` pairs verified region-local before the cut; all 21 `AncestorType=Window` bindings copied verbatim rather than retargeted; acceptance requires a full manual pass under the debugger with **zero** `System.Windows.Data Error:` lines; the marker-parity greps make a dropped binding countable.

**R2 — The 100% coverage gate is theatre for this task.** Every product line written lands in `WindowsFileManager.Views.*`, which is both outside `<Include>` and matched by `<Exclude>[WindowsFileManager]*Views*`. The gate will pass whether the refactor is perfect or catastrophic. *Mitigation:* say so in the PR description rather than implying the gate covered it; treat the gate as a negative control (a drop means a measured type was touched by accident); take fork 2A so at least parse-time failure is caught mechanically; note that the token-contract glob (R19) is now the one gate that does look at the new files, which is why F8 forbids suppressing it.

**R3 — A "small tidy" during the move becomes a behaviour change.** Four specific ones, ranked by likelihood: converting the History `TabItem`'s `TextBlock` header to `Header="History"` (revives the dead branch — R8/F5); fixing one of the four drifted help strings while it is in front of you (destroys marker parity and steals T-010's diff — F6); restyling `HelpButtonStyle` while relocating it (steals T-003's diff — F10); replacing the cross-control media stop with a `PropertyChanged` subscription (loses the extended-multi-select case — B6). *Mitigation:* all four are explicit fail-path acceptance rows.

**R4 — 2,700 lines of hand-moved XAML is a large, low-signal diff.** Review fatigue is real and a single dropped attribute is invisible in a diff this size. *Mitigation:* the twelve marker-parity counts are cheap, mechanical and reviewable in one screen; require them in the PR body, not just in the checklist. Consider moving region by region in nine commits on the branch, squashed or not, so each diff is readable — the docs/spec updates and the token-glob extension then land in the final commit alongside the whole change.

**R5 — Cross-task resource-home divergence (was the top blocking finding).** Three tasks proposed three folders (`Resources/`, `Themes/`, `Styles/`) and `HelpButtonStyle` had three declared destinations across T-002/T-003/T-010. Left unresolved, `App.xaml` ends up merging from three trees, the style moves twice, and two specs claim the same SPEC-010 edit. *Mitigation:* decisions S1 and S2 settle one folder (`Themes/`), one relocation owner (T-002), one restyle owner in place (T-003), one retirement owner (T-010, new filename); R18/F9/F10 make it checkable; § serves_spec splits SPEC-010 into three disjoint edits. **Residual risk:** T-003 and T-010 must actually be revised to match — this spec cannot enforce that unilaterally, so treat S1–S2 as epic-level decisions to be applied to those two specs before either starts.

**R6 — Fork 2A introduces the first `Application`-hosting test.** A leaked `Application.Current` across reruns, or a `Dispatcher` that never shuts down, can hang a CI job. *Mitigation:* guard with `if (Application.Current is null)`; own the STA thread inside the test and `Join()` it; never call `app.Run()`; never set a `DataContext` (which would run `MainViewModel`'s disk-touching constructor). `xunit.runner.json` already serialises everything, removing the parallelism class of failure entirely.
