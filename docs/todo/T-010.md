## Concept

Today the app has two help mechanisms and neither is accountable to anything. 81 literal `ToolTip=` attributes and 21 `?`-circle popups (`HelpButtonStyle` `ToggleButton`s carrying a markup string in `Tag`) sit in `Views/MainWindow.xaml`. The popups grew to 21 without a single code change — which was the point of making help pure data — but the same property means nothing ever checked them against the code. Four have verifiably drifted, and a fifth renders broken markup:

1. `TAKE ACTION on selected files` (MainWindow.xaml:1484) says Delete *"Permanently removes checked files from disk. `<w>`No Recycle Bin — cannot be undone.`</w>`"* Every delete path calls `MainViewModel.cs:4101` → `VbFileSystem.DeleteFile(path, OnlyErrorDialogs, SendToRecycleBin)` and pushes an undoable `RecycleFiles` history entry. The app is telling users their files are gone when they are recoverable.
2. `CUSTOM FILTER RULES` (:1094) names the actions "Contains" and "Ignore"; the enum is `FilterAction.Include` / `FilterAction.Exclude` (`FilterRule.cs:9,12`) and the ComboBox shows those names. It then says *"`<w>`Ignore ALWAYS overrides Contains.`</w>`"* — true of the `ApplyIgnoreRules` post-pass, false of ▶ Apply, which is first-match-wins with a `break` at `MainViewModel.cs:3029`.
3. `FOLDER SEARCH` (:421) says *"`<b>`Matching:`</b>` Case-insensitive contains match."* — the description of the feature before six match types existed.
4. `MATCH TYPES` (:433) documents five of six; `NotContain` (`FolderSearchPattern.cs:26`) is implemented and selectable but undocumented.
5. `MATCH BY NAME REGEX` (:1030) wraps its examples in `<code>…</code>`. The parser recognises only `b`, `h`, `w` and `link=`; SPEC-010 rule 10 sends everything else through verbatim, so users see literal angle brackets on screen.

**Defect 1 is not a design problem and must not wait for one.** It is four `Tag` strings and a README line. **Stage A** corrects them in place, in the monolith, and deletes the four now-false `## Not implemented` bullets that document the drift across SPEC-003, SPEC-004, SPEC-007 and SPEC-010 — plus the one rule row (SPEC-004:69) that is itself wrong. That commit stands alone, ships today, and needs nothing from the redesign.

**Stage B** is 3a's answer, which is structural rather than editorial. Its panels carry no `?` circles at all: explanation lives as short muted captions sitting next to the control they describe (`first match wins` under the Rules header, `last scan 10:12 · 4.2 s` beside Scan, `2 sub` on a folder row, `will be recycled` in the action bar) and as uppercase section labels (`Target folders`, `Skip folders named`, `Match duplicates by`). What a caption cannot hold — one paragraph of "what is this panel for" — moves to a single per-panel popover in the 30px tool-window header, of which there are eight, not twenty-one.

The rewrite is worth doing on its own merits, but the durable value is the mechanism that stops it drifting again: every retained string is re-derived from the rule in its owning spec, the six folder-search match types stop being prose and become a glossed enum the compiler and a `Theory` over `Enum.GetValues` keep complete, and a build-time test reads the shipped XAML and fails the build on the exact phrases that lied.

### 2 · New product code — `src/WindowsFileManager/Helpers/EnumGlossConverter.cs`

The only new C# in this task, and it is Stage B. Namespace **must** be `WindowsFileManager.Helpers` (the runsettings `Include` covers `[WindowsFileManager]WindowsFileManager.Helpers*`) and it **must not** carry `[ExcludeFromCodeCoverage]`.

```csharp
public sealed class EnumGlossConverter : MarkupExtension, IValueConverter
{
    public static readonly EnumGlossConverter Instance = new();

    public override object ProvideValue(IServiceProvider serviceProvider) => Instance;

    public object Convert(object value, Type targetType, object parameter, CultureInfo culture) => value switch
    {
        FolderMatchType m => Gloss(m),
        FilterAction a => Gloss(a),
        _ => string.Empty,
    };

    public object ConvertBack(object value, Type targetType, object parameter, CultureInfo culture)
        => throw new NotSupportedException();

    private static string Gloss(FolderMatchType m) => m switch
    {
        FolderMatchType.Include    => "name contains the text",
        FolderMatchType.Match      => "name is exactly the text",
        FolderMatchType.Contains   => "folder holds a child item matching the text",
        FolderMatchType.Exclude    => "name does not contain the text",
        FolderMatchType.Mismatch   => "name is not exactly the text",
        FolderMatchType.NotContain => "folder holds no child item matching the text",
        _ => string.Empty,
    };

    private static string Gloss(FilterAction a) => a switch
    {
        FilterAction.Include => "mark matching copies",
        FilterAction.Exclude => "leave matching copies unmarked",
        _ => string.Empty,
    };
}
```
Every gloss is a transcription of a spec row, not an invention: the six `FolderMatchType` lines are SPEC-007 rule 11's table verbatim-in-plain-English (note `Contains`/`NotContain` are about a *child item*, per rule 14 — the current popup's "folder has a child item (file/subfolder) inside it" is right and is preserved); the two `FilterAction` lines are SPEC-003 rule 5.

`ConvertBack` throwing `NotSupportedException` matches the house pattern already in `Converters.cs:59–62` and `:114–117`. `MarkupExtension` + `static readonly Instance` matches `PercentToWidthConverter` (`Converters.cs:40`).

### 3 · The eight popover strings (author these verbatim; XML-escape `<` `>` `&` `"` — no `&#x0a;`, each is one paragraph)

1. **Scope** — `Folders listed here are scanned for duplicates; <b>Include subfolders</b> walks every nested level. Names under <b>Skip folders named</b> match on folder name only, case-insensitively, at any depth. <b>Match duplicates by</b> picks content hash (SHA-256) or a name pattern.`
2. **Duplicate groups** — `Each group holds copies that matched — by SHA-256 content hash, or by equal captures from your name pattern. The toolbar changes what you see, never what was found: <b>Mark</b> acts on copies in every group, including groups the filters are currently hiding.` *(that last clause is SPEC-004 rule 2, a real trap nothing in the UI says today)*
3. **Preview** — `Shows the copy you selected — image, video, audio or text — with its size, pixel size, modified date and full path. <b>Auto</b> previews each copy as you select it; switch it off to preview only when you ask.`
4. **Rules** — `Rules run top to bottom and the <b>first</b> match decides a copy: <b>Include</b> marks it, <b>Exclude</b> leaves it unmarked, later rules are skipped. Disabled rules never match. <b>Mark All / Newer / Older</b> work differently — there every Exclude rule applies. <link=https://regex101.com>regex101.com</link>` *(SPEC-003 rules 5 and 7 — the asymmetry Stage A already corrected in the old popup, carried over unchanged)*
5. **Action bar** — `Both buttons act on every marked copy in every group, including groups the filters hide. <b>Recycle</b> sends them to the Windows Recycle Bin — nothing here deletes permanently — and <b>Undo</b> in the status bar restores the last action. <b>Move to…</b> relocates them, keeping filenames.` *(the Stage A correction, in its final form; grounded in SPEC-004 rules 10–13 and its invariant "every destructive action in this spec is recoverable")*
6. **Profile switcher** — `A profile is a saved workspace: target folders, skip names, filters, rules, search patterns and per-tab selections. Window size and position, the undo history and which profile is active are <b>shared by every profile</b>. At least one profile must exist.` *(SPEC-009 rules 6 and 7; the current popup omits the active-profile name)*
7. **Folder search** — `Searches every enabled target folder for subfolders, skipping excluded names. Each enabled pattern must pass — they combine with <b>AND</b> — and the match type beside a pattern says how it is tested. <b>Depth</b> limits the walk; empty means no limit, 1 means direct children only.` *(SPEC-007 rules 3, 10, 12, 13; the six types are glossed in the combo, not enumerated here)*
8. **Folder actions** — `Acts on the folders you checked above. <b>Scan</b> inventories their subfolder names and file types. <b>Clear</b> sends the checked subfolders or file types to the Recycle Bin. <b>Link siblings</b> writes .lnk shortcuts between folders under one parent. <b>Move to root</b> flattens nested files upward.`

### 8 · `ResourceKeyDriftTests` — the mechanical cure for invented keys (Stage B)

A second test class beside `HelpTextDriftTests`, in the same test assembly, pure XML — no WPF runtime, no STA, no pack URIs:

1. Glob `src/WindowsFileManager/**/*.xaml`, `XDocument.Load` each.
2. Collect **defined** keys: every `x:Key` attribute value in the tree.
3. Collect **referenced** keys: regex every attribute value for `{StaticResource X}` / `{DynamicResource X}` (including inside `Setter.Value`), capturing `X`.
4. Assert `referenced ⊆ defined ∪ allowList`, where the allow-list holds only framework keys (`SystemColors.*`, `SystemParameters.*`, WPF theme keys) and is a `private static readonly string[]` with a comment saying what it is for.
5. On failure, name every unresolved key and the file it was referenced from.

This makes the binding rule in §1 enforceable rather than aspirational: a placeholder that was never bound, a key spelled to T-010's taste rather than T-001's, or a `MergedDictionaries` entry dropped during the `Legacy.HelpButton` deletion all fail the build. It is test-assembly code (`IncludeTestAssembly=false`), so it costs nothing at the coverage gate.

## Edge cases

If Stage B finds itself rewriting a Stage A claim, that is a signal the claim was wrong the first time — go back to the owning spec rule, not to the earlier draft.

**Stage A keeps `<h>` and `<w>`.** It edits today's multi-section popups in place; the tags die only when the one-paragraph budget arrives in Stage B. Do not "modernise" the four strings in Stage A — that turns a 6-line diff into a redesign and re-couples it to the predecessors.

**3a draws no help affordance at all.** The artboard's tool-window headers carry only their own verbs. Adding a `?` is an invention — keep it visually silent (muted glyph, accent only on hover/checked, no filled circle) so it does not violate turn 3's "the typography, colors and controls stay Broadsheet — only the framing is IDE-standard". See decision D1.

**F1 is not implemented and must not be claimed.** No task in this epic resolves a focused element to a panel's help button, and SPEC-010 already documents the absence at :37 and :120 — those lines stay. The failure mode to avoid is the one the panel caught: one task promising the gesture in prose while another binds the key, with nobody owning the lookup. If F1 is ever built, the algorithm is sketched in Out of scope. Until then, `F1` appears nowhere in this task, T-011, or any spec edit except as a documented non-feature.

**The `<code>` bug is real and currently shipping.** `MATCH BY NAME REGEX` (`MainWindow.xaml:1030`) writes `&lt;code&gt;(?i)(abc).*?(\d{7,8})&lt;/code&gt;`. `FormattedTextBehavior.ParseAndApply` matches only `b`/`h`/`w`/`link=`, so the `else` arm emits `<code>` verbatim and users see angle brackets. **Stage A does not fix this** — it is a rendering defect, not a truth defect, and the string dies in Stage B. **High DPI.** `MaxWidth="320"` is device-independent, so the popover scales at 150%; the paragraph reflows. Verify the longest string (Scope, ~305 chars) does not exceed the working area height at 150% on a 720-tall display.

## Risks

**R1 — Ordering. (was high; now largely retired by the split.)** Six hard predecessors used to gate a live correctness defect. *Mitigation, now built in:* Stage A carries the four drifted strings, the README rename and the five doc edits with **zero** predecessors and ships first; only the caption/popover restructure waits. The residual risk is that someone folds Stage A back into Stage B "to save a commit" — the acceptance blocks are partitioned specifically to make that visible in review.

**R2 — Content loss. (Stage B only; certain; cost depends on D3.)** Compressing 21 popups totalling several thousand characters into 8 × ≤320 destroys the worked examples in `LINK SIBLING FOLDERS` (a full before/after directory listing), `MOVE FILES TO ROOT`, `CLEAR SELECTED SUBFOLDERS` and `MATCH BY NAME REGEX`. Some of that is genuinely the clearest explanation in the repo. *Mitigation:* decision D3 — verify each example survives in its owning spec and add it there in the Stage B commit if not; the UI loses it, the docs do not.

**R3 — The drift test becomes an obstacle rather than a guard. (medium.)** It hard-codes "exactly 8 popovers" and "≤45 tooltips". Every later panel addition trips it. *Mitigation:* both live in one `private const` block with an XML comment pointing at SPEC-010's inventory table, so changing them is a deliberate act that forces the spec edit — that is the mechanism working, not failing. But say so in the test's summary or the next engineer will just bump the number.

**R4 — Banned-phrase false positives. (medium.)** `Contains` is a live `FolderMatchType` member *and* a retired `FilterAction` name. A naive `.Contains("Contains")` assertion fails on the correct gloss. *Mitigation:* ban the surrounding phrases (`Contains (check matching files)`, `Contains (select)`, `Ignore ALWAYS overrides`), not the bare token; add a positive test that the legitimate `FolderMatchType.Contains` gloss passes.

**R5 — Popover placement at the screen edge. (medium, Stage B.)** The Rules and Preview popovers hang off buttons ~40px from the right edge of a 1600px window with a 320px body. WPF's `Bottom` placement nudges against the **screen**, not the window, so an unmaximized window near the right edge behaves differently from a maximized one. *Mitigation:* row 5 of the Stage B matrix — screenshot both states at 1600×900 and 1280×720. Resist "fixing" it with a hand-tuned `HorizontalOffset`, which breaks the other case.

**R6 — Coverage gate on new code. (low likelihood, cheap to hit, Stage B.)** `EnumGlossConverter` lands inside the measured `Helpers` namespace and needs 100% **branch** coverage: both undefined-enum `_ =>` arms and the `ConvertBack` throw are easy to miss. A method with zero covered lines counts as uncovered under `Check-Coverage.ps1`'s derived method rate, so `ProvideValue` must be called by a test too. *Mitigation:* matrix rows 20–24 exist precisely for this; run the two-command gate locally before pushing.

**R7 — Silent regression in what is not tested. (medium, permanent.)** Nothing renders a popover in CI. A `Style` key typo, a missing `MergedDictionaries` entry, or a `DynamicResource` that resolves to nothing produces an invisible or unstyled popover that every automated check passes. *Mitigation, strengthened:* `ResourceKeyDriftTests` now catches exactly the typo/missing-entry/unresolved-key subset statically. What remains uncovered is *visual* wrongness — a resolvable key that looks wrong — and that stays a manual smoke pass with screenshots attached to the PR. This is the honest limit of verification here and belongs in the PR body, not papered over.

**R8 — Scope creep into 4a. (medium.)** "Fix the help colours" is one keystroke from "tokenise the four `FormattedTextBehavior` brushes", which is one from a semantic colour system — turn 4, explicitly excluded. *Mitigation:* decision D2a freezes `FormattedTextBehavior`; the Stage B acceptance list asserts the file is byte-identical to `HEAD`.

**R9 — Spec-sync commit bloat. (medium, Stage B.)** Stage B touches 4 specs, a module doc, CHANGELOG, ~8 XAML files, 1 new C# file and 3 test files. Adding the uncommitted 11-file test batch on top makes review impossible. *Mitigation:* land or discard that batch first, in its own commit. Stage A is immune — it is a 6-line source diff plus doc edits.

**R10 — Re-drift. (low, by design.)** Once the drift tests exist, help text can still go stale in ways they cannot see — a popover that is grammatical, short, tag-clean and simply *wrong* about a rule nobody banned a phrase for. *Mitigation:* accept it. The tests catch the recurring mechanical classes (retired names, permanence claims, missing enum members, bad markup, unresolved keys); the re-derivation discipline in acceptance ("every retained string traced to a numbered rule in its owning spec") is what catches the rest, and it is a human step. **Note the gap Stage A opens deliberately:** between Stage A and Stage B the strings are correct but still unguarded, so a fifth drift could appear in that window. That window is the price of shipping the fix early, and it is smaller than the window that exists today.

**R11 — Catalogue-key mismatch. (was the blocking finding; now medium and mechanically caught.)** This spec previously named brush and style keys that matched neither T-001's nor T-003's namespace, which would have shipped either a parallel naming scheme or an unresolvable reference. *Mitigation:* keys are no longer authored here — Detail §1 declares *roles* with `⟨placeholder⟩` labels, binding happens at implementation against the published catalogue, the four keys this task does author are registered in T-003's index, and `ResourceKeyDriftTests` fails the build on any key nothing defines. The residual risk is a role T-001 never publishes; the rule there is raise it, never invent.

**R12 — Two-stage rework tax. (low.)** Stage B could re-litigate wording Stage A already settled. *Mitigation:* Stage A authors strings 1–3 as the claims Stage B lifts, so the restructure is a move. String 4 (`MATCH TYPES`) is knowingly transitional — Stage A adds one paragraph that Stage B deletes wholesale in favour of the enum gloss; that is ~6 lines of throwaway text, bought in exchange for documenting an undocumented feature months earlier.

## Open decision

Six forks. D1–D4 are unchanged from the previous revision. D5 and D6 are the panel's blocking items, settled here as cross-task contracts — they need a nod from the T-002/T-003 owners, not from the user.

**D1 — Where does the panel popover hang?** The 3a artboard draws **no `?` affordance anywhere**. Every tool-window header shows only its own verbs (`Scope: + Folder · ⋯`, `Preview: Auto ✓ · ✕`, `Rules: + Rule · Apply`). The one-paragraph popover requires an affordance, so one must be invented. Options:
- **(a) A muted `?` glyph as the last item in each 30px tool-window header's action group. (Recommended.)** Discoverable, consistent across all eight panels, one style, works for keyboard focus. Costs one new glyph the artboard does not show.
- (b) An "About this panel" item inside the `⋯` overflow. Faithful to the artboard (invents nothing) but only Scope has a `⋯`; the other seven panels would need one added anyway, and it buries help two clicks deep.
- (c) A `ToolTip` on the tool-window header title only. Invents nothing at all, but a hover-only, dismiss-on-move surface cannot hold a paragraph and is invisible to keyboard users.

Pick before writing the panel-help button style; the whole Stage B Detail assumes (a). **Stage A does not depend on this.**

**D2 — Does the `<h>` / `<w>` markup survive?** `FormattedTextBehavior` hard-codes four brushes (`#0D47A1` highlight, `#C62828` on `#FFEBEE` warning, `#1565C0` link) in C#. Under Stage B's one-paragraph budget the new popovers use only `<b>` and one `<link>`, so `<h>` and `<w>` become dead grammar. Options:
- **(a) Leave `FormattedTextBehavior` untouched; the grammar keeps branches nothing calls. (Recommended.)** Zero code churn, `[ExcludeFromCodeCoverage]` stays true, and the uncommitted `tests/WindowsFileManager.Tests/Helpers/FormattedTextBehaviorTests.cs` (which asserts exactly that attribute) still passes unchanged.
- (b) Strip the `h`/`w` branches from the parser. Smaller surface, but it edits a file that is `[ExcludeFromCodeCoverage]` — so the deletion is unverified by the gate — and it drags the uncommitted test batch into this commit. It also drifts toward the colour-as-meaning question, which belongs to 4a and is out of scope here.

Note the Stage A consequence: Stage A **keeps** `<h>` and `<w>` in the corrected strings, because it is editing today's multi-section popups in place, not converting them to paragraphs. The tags die in Stage B.

**D3 — What happens to the four worked examples?** (Stage B only.) `LINK SIBLING FOLDERS`, `MOVE FILES TO ROOT`, `CLEAR SELECTED SUBFOLDERS` and `MATCH BY NAME REGEX` carry before/after directory listings and pattern examples (up to 903 chars) that cannot survive a ≤320-char paragraph. Default, unless the user says otherwise: **let the examples leave the UI, after verifying each one already exists in its owning spec (SPEC-008, SPEC-003, SPEC-001) and adding it there in the Stage B commit if it does not.** The alternative — a new `docs/HELP.md` linked from the popovers — adds a documentation kind the `docs/specs/_index.md` sync contract does not define, and would need its own home in the "one home per kind" table.

**D4 — Do redundant `ToolTip`s get deleted or kept as a redundant a11y path?** (Stage B only.) Default: **delete a literal `ToolTip` wherever the control already renders its own text label or sits directly above/below a caption saying the same thing; keep it wherever the control's visible content is a glyph, image, or empty.** T-011 owns the accessibility verification, so if the user wants tooltips retained everywhere as a screen-reader path, say so before the audit runs — it changes the count assertion in the drift test.

**D5 — F1: dropped, not specified. (SETTLED.)** The panel is right that nothing anywhere defines how F1 resolves a focused element to a panel's help button, and inventing that resolution is real work (a focus-ancestor walk, a per-panel registration, and a decision about what happens when focus sits in the title bar or the status bar). **The claim is withdrawn from this task, from T-011's gesture list, and from the SPEC-010 rewrite.** SPEC-010's existing `## Not implemented` bullet — "No F1 key handler, no help menu, no 'show all help' mode…" (:120) and the matching line at :37 — **remains true and stays in the file**, so the docs need no change to accommodate the withdrawal; only T-011's binding list loses a row. The algorithm a future task would need is written down in Out of scope so it is not re-invented from scratch. If the epic owner instead wants F1 shipped, it becomes its own task with its own acceptance — not a bullet borrowed between two tasks, which is how it came to be claimed in one place and bound in another with nobody owning the lookup.

**D6 — Two stages, one task id. (SETTLED — restructure of scheduling, not of scope.)** The Delete popup's false permanence claim is a live user-facing correctness defect; it sat behind six hard predecessors at `when: later` only because it was bundled with the restructure that needs them. It is now **Stage A: a string-and-docs-only commit with zero predecessors, `when: now`, P1**, with its own acceptance block below. Stage B is everything else, unchanged, still gated on T-001/T-002/T-003/T-006–T-009. Stage A deliberately takes the **cheapest correct** form — it edits `Tag` attribute values inside `MainWindow.xaml` and touches no C#, no styles and no coverage-measured code, so it cannot be blocked by StyleCop, the coverage gate, or the uncommitted test batch. Where the budget allows, Stage A authors the corrected text as the **exact paragraph Stage B will move**, so the restructure relocates strings rather than rewriting them a second time. If the epic prefers two ids over two stages, Stage A splits off as `T-010a` with no edits — the acceptance list, the spec edits and the dependency set are already partitioned along that line.
