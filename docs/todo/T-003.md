## Concept

3a is not a new screen — it is a **vocabulary**. Read the artboard as a parts list and the same dozen parts recur: a 30px tool-window header with a name left, actions right and a hairline under it (×4 — Scope, Duplicate groups, Preview, Rules); a flat accent text link (×17 — `+ Folder`, `⋯`, `+ Add`, `Expand all`, `Collapse all`, `All/Newer/Older/By rules/None`, `Preview`, `Recycle`, `Auto ✓`, `✕`, `+ Rule`, `Apply`, `Enable all`, `Disable all`); a 14px square accent checkbox (×8); an uppercase 11px kicker (×4, including the results column-header row); a 1px-bordered 2px-radius pill dropdown (×6); a tinted 26–40px band (×5); a 10px `▼`/`▶` disclosure glyph; a row that washes `accent-100` when selected and is separated from its neighbour by a 6%-ink rule.

Today the repo has the opposite of a vocabulary. `MainWindow.xaml` carries **78 `<Style>` blocks of which only 6 are keyed** — the other 72 are anonymous inline styles pasted at their point of use, each re-declaring a `Border` + `ContentPresenter` `ControlTemplate` and its own hover/checked triggers, with **70 distinct hardcoded hex colours** between them. `App.xaml` is 314 bytes with an empty `<Application.Resources/>`. That is why the same toggle button appears four times at lines 748, 793, 838 and 883 with four slightly different colour sets.

T-003's job is to make the vocabulary exist **once**, as keyed WPF resources over T-001's tokens, so T-004 through T-009 are composition tasks rather than restyling tasks. The review panel found three places where that had already failed on paper before a line was written — three consumers hand-rolling a tool-window header, two tasks defining the same splitter, and a `ToggleButton` disclosure glyph plus a selected-row container that every consumer invented locally. Publishing those four shapes here, under the names the consumers already use, is the whole point of the task; a component library whose flagship abstraction has no consumer is a library that has already lost.

It is deliberately a **zero-behaviour, zero-visual commit**: every style is keyed, nothing is an implicit `TargetType`-only style, so not one pixel of the running app changes until a consumer opts in. That property is what makes an L-sized change to a WPF app with no UI tests and no visual-regression harness safe to land at all — and it is enforced mechanically, not by intent (§ Acceptance, `BCL-05`).

## Design

**Shape.** Four new XAML ResourceDictionaries under **`src/WindowsFileManager/Themes/`** — T-001's folder (S1) — plus one aggregator, one `App.xaml` edit, one XML-level test class. **No new production C#** under decisions D1-A / D2-A.

```
src/WindowsFileManager/
  App.xaml                            ← EDIT: one MergedDictionaries entry (T-001 adds the tokens line)
  Themes/                             ← T-001 creates this folder; T-003 adds four files to it
    Broadsheet.Tokens.xaml            ← T-001's — consumed, never edited here
    Broadsheet.Components.xaml        ← NEW: aggregator; merges the four families below
    Broadsheet.Text.xaml              ← NEW: kicker, caption, code, glyph, tags, group title, disclosure toggle
    Broadsheet.Buttons.xaml           ← NEW: primary / secondary / ghost / link / link-muted / icon
    Broadsheet.Inputs.xaml            ← NEW: textbox, numeric, combobox, checkbox, keep-radio, segment, row containers
    Broadsheet.Frame.xaml             ← NEW: tool-window header, bands, rules, splitters, statusbar, tabs, focus visual
  Resources/HelpStyles.xaml           ← T-002's — NOT touched by this task
tests/WindowsFileManager.Tests/
  Themes/BroadsheetComponentDictionaryTests.cs  ← NEW: XML-level structural gate (no STA, no WPF objects)
  WindowsFileManager.Tests.csproj     ← EDIT: <None Link> copy of src Themes/*.xaml to output
```

**Merge order (`App.xaml`, exact and load-bearing).** Tokens first, components second. Under S3 the structural tokens are `StaticResource`, and `StaticResource` resolves at parse time in dictionary order — so a components-before-tokens merge is now a hard runtime failure, not a latent one:

```xml
<Application.Resources>
    <ResourceDictionary>
        <ResourceDictionary.MergedDictionaries>
            <ResourceDictionary Source="/WindowsFileManager;component/Themes/Broadsheet.Tokens.xaml" />
            <ResourceDictionary Source="/WindowsFileManager;component/Themes/Broadsheet.Components.xaml" />
            <!-- T-002's Resources/HelpStyles.xaml also merges here; order relative to these two is free -->
        </ResourceDictionary.MergedDictionaries>
    </ResourceDictionary>
</Application.Resources>
```

The tokens line is **T-001's** to add; T-003 adds the components line and leaves everything else in the list alone. `BCL-07` asserts *tokens before components* and tolerates any number of additional sibling entries, so T-002's dictionary can land before or after without a test churn. No `.csproj` change is needed for the new XAML: with `UseWPF=true` the SDK auto-globs `**/*.xaml` into `Page`, and `App.xaml` stays `ApplicationDefinition`.

**Six invariants the whole library obeys.** These are what the test class enforces and what a reviewer reads the diff against.

1. **Keyed only.** Every `<Style>` carries an `x:Key`. No `<Style TargetType="X">` without a key anywhere in `Themes/Broadsheet.*.xaml`. An implicit style in an app-level dictionary restyles every instance of that type in the process — including the 21 help popups and `ProfileNameDialog.xaml` — which turns this commit from zero-visual to whole-app-visual.
2. **No literal colour.** No `#RRGGBB`, `#AARRGGBB` or named `Brushes.*` appears in any component file. Every colour is `{DynamicResource Broadsheet.Brush.*}`.
3. **Reference kind follows themeability (T-001 contract §3, S3).** `Broadsheet.Brush.*` and `Broadsheet.Font.*` → **`DynamicResource`** (a theme swap must be able to replace them). `Broadsheet.Radius.*`, `Broadsheet.Thickness.*`, `Broadsheet.Size.*` and any `Double`/`GridLength` → **`StaticResource`** (structure is not themeable, and a `StaticResource` typo throws `XamlParseException` at load, where a `DynamicResource` typo silently yields the property default). This is a two-way rule and `BCL-03` checks both directions.
4. **Compact metrics, not the design system's marketing metrics.** The Broadsheet CSS ships `.btn` at `padding 10px 18px` / `font-size 14px` and `.input` at `min-height:36px` / `14px`. **3a overrides every one of them inline** — verified: buttons `min-height:28px`, `padding:0 14px` (Scan) / `0 12px` (action bar) / `0 10px` (Rules Add), `font-size:13px`/`12.5px`; the Rules compose input `min-height:28px`, `font-size:12.5px`. The library's base styles carry **3a's numbers**. Recorded in the dictionary header comment and in `ui.md`.
5. **Font size inherits from the band.** A band style sets `TextElement.FontSize` / `.Foreground` / `.FontFamily`; component styles **omit** `FontSize` unless 3a pins that component away from its band. A `Setter` for `FontSize` defeats WPF property-value inheritance, so omitting it is the mechanism, not laziness — `Broadsheet.Button.Link` renders at 12px in a tool-window header and 12.5px in the results toolbar from one key, exactly as the artboard does.
6. **Hairlines snap.** Every 1px element sets `SnapsToDevicePixels="True"` and `UseLayoutRounding="True"`. WPF lays out in DIPs; at 125%/150% an unsnapped 1px border renders as a 1.25px grey smear or vanishes. 3a has 14 one-pixel rules, a 1px vertical toolbar separator and two 1px splitters — this is not cosmetic.

**Naming.** T-001's `Broadsheet.` dotted namespace, verbatim (S2), one segment per level: `Broadsheet.<Component>[.<Variant>]`. Where a sibling task already named a shape, this library adopts that noun so the consumer's diff is a prefix change and nothing more — `PaneSplitter` from T-005, `ToolWindow.Header` from T-006/7/8, `Toggle.Glyph` from T-007's `GlyphToggleStyle`.

```
<Setter Property="Content" Value="▶" />                       <!-- collapsed default -->
<Trigger Property="IsChecked" Value="True">
    <Setter Property="Content" Value="▼" />
</Trigger>
<Trigger Property="IsMouseOver" Value="True">
    <Setter TargetName="Bd" Property="Background"
            Value="{DynamicResource Broadsheet.Brush.HoverInk}" />

```

A `Content` setter on the *style* is overridden by any `Content` a consumer sets in markup, so T-007 must **not** set `Content` on these toggles — noted in the dictionary header and in § Interfaces-C.

**Three knowing deviations, recorded in the file header and in `ui.md`:**

- **`letter-spacing:.08em` is dropped.** WPF's `TextBlock` has **no character-spacing property** — `CharacterSpacing` is WinUI/UWP; `Typography.*` exposes OpenType features, not tracking. The alternatives are one `Run` per character (destroys screen-reader text and selection) or a custom `GlyphRun` control (disproportionate for four labels). Kickers ship **uppercase in the source string**, 11px, `Neutral600`, no tracking. Do not re-open this in review.
- **Radius comes from `StaticResource`.** `CornerRadius` is not a brush and is not themeable; per S3 it is `{StaticResource Broadsheet.Radius.Md}` (`2`) / `.Sm` (`1`), never `DynamicResource`.
- **Tags are two fixed keys**, not per-file-type tinted — see § Out of scope.

### 6. `Themes/Broadsheet.Frame.xaml` — the two pane splitters (T-003 owns these, per S5)

3a's body grid is literally `grid-template-columns: 260px 1px 1fr 1px 360px` and the right stack is `grid-template-rows: 1fr 1px 1fr`. T-005 builds the grids and **consumes** these keys; its own `PaneSplitter*` definitions are struck. **The repo has zero `GridSplitter` elements today** — this is entirely new.

**`Broadsheet.PaneSplitter.Vertical`** (`TargetType="GridSplitter"`):

```
Setters: Width=1, HorizontalAlignment=Stretch, VerticalAlignment=Stretch,
         ResizeDirection=Columns, ResizeBehavior=PreviousAndNext,
         Background=Transparent, Cursor=SizeWE,
         Focusable=True, KeyboardIncrement=8,
         SnapsToDevicePixels=True, UseLayoutRounding=True,
         FocusVisualStyle={StaticResource Broadsheet.FocusVisual}

Template: <Grid Width="9" HorizontalAlignment="Center" Background="Transparent">
            <Border Width="1" HorizontalAlignment="Center"
                    Background="{DynamicResource Broadsheet.Brush.Divider}"
                    SnapsToDevicePixels="True" />
          </Grid>
```

**The 9px template root inside a 1px column is deliberate and is the whole point.** A 1px hit target is unusable with a mouse. WPF does not clip a child to its parent cell unless `ClipToBounds="True"`, so the transparent 9px `Grid` overhangs the 1px column by 4px each side and becomes the drag surface, while the visible line stays exactly 1px. `Background="Transparent"` (not unset) is required — a `null` background is not hit-testable and the splitter would render but never drag. `ResizeBehavior="PreviousAndNext"` is required because the splitter's own column is a fixed 1px and the default `BasedOnAlignment` would try to resize it.

**`Broadsheet.PaneSplitter.Horizontal`**: the same with `Height=1`, `ResizeDirection=Rows`, `Cursor=SizeNS`, template root `Height="9" VerticalAlignment="Center"`, inner `Border Height="1"`.

### 9. The glyph-font pin — with a stated fallback so it cannot tofu

3a's chrome is full of text glyphs: `▾ ▼ ▶ ✓ ✕ ⋯ ↶ — ▢ ≥ ↓ ·`. If the body font resolves to Source Serif 4, most of those are absent from the face and WPF font fallback substitutes them per-glyph — visibly mismatched weights and baselines across the frame.

## Edge cases

**E-01 — `PART_ContentHost` is not optional.** WPF's `TextBoxBase` locates its editing surface by that exact literal name. Rename or drop it and the build is green, the style applies, and the box renders permanently empty and refuses keystrokes. Same class of trap: `PART_ToggleButton` / `PART_Popup` / `ContentSite` in `ComboBox`, `IsItemsHost="True"` on the `TabPanel`. `BCL-08` exists solely for these.

**E-02 — a `StaticResource` typo throws; a `DynamicResource` typo does not.** This is the whole reason for the S3 split. `CornerRadius="{DynamicResource Broadsheet.Radius.Mdd}"` yields a silent `0` — square corners nobody notices for weeks. The same typo under `StaticResource` throws `XamlParseException` at load, on the first screen that uses it. Structure is therefore `StaticResource` by rule, not by taste, and `BCL-03` enforces both directions.

**E-03 — a null `Tag` must degrade silently.** `ContentPresenter Content="{TemplateBinding Tag}"` with `Tag` unset binds to `null`, measures zero, and lays out cleanly — for the tab strip and the text-field placeholder alike. No `TargetNullValue`, no fallback, no converter (cases 25–26).

**E-04 — `Trigger Property="Text" Value=""` fires at load.** `TextBox.Text`'s default is `""`, so the placeholder is visible before any binding runs and disappears on the first character; it also reappears when the box is cleared. This is why no `StringToVisibility` converter is needed and none should be added.

**E-05 — a 1px `GridSplitter` needs an explicit `Background`.** `Background="Transparent"` is hit-testable in WPF; an unset (`null`) background is **not**, and the splitter becomes undraggable while still rendering. The transparent 9px template root and the `Transparent` fill are both load-bearing.

**E-06 — `ResizeBehavior` must be `PreviousAndNext`.** The splitter sits in its own fixed 1px column; the default `BasedOnAlignment` would attempt to resize *that* column and the drag would do nothing visible.

**E-07 — `Margin="0,0,0,-1"` on the tab underline overhangs its band.** WPF does not clip children to their parent unless `ClipToBounds="True"`. If T-004 ever sets `ClipToBounds` on the tab-strip band, the underline is cut and the design breaks. Noted in the file header.

**E-08 — the History tab's `Header` is already not a string.** `MainWindow.xaml:1717` sets it to a `TextBlock`, so `MainWindow.xaml.cs:190`'s `Header as string` yields `null` and the `"History"` branch at line 202 is dead **today, before this epic touches anything**. `Broadsheet.TabItem` deliberately ships **no `HeaderTemplate`**, so a string `Header` stays a string. Hand the dead branch to T-004 as a known finding.

**E-09 — the tool-window header docks `Right` before it measures `Left`.** In a `DockPanel` with `LastChildFill="False"`, the right-docked actions get their desired width first and the title takes what remains. At a narrow Scope pane the title must ellipsise rather than clip mid-glyph — hence `TextTrimming="CharacterEllipsis"` on `Broadsheet.ToolWindow.HeaderTitle` (case 40).

**E-10 — a style's `Content` setter loses to markup.** `Broadsheet.Toggle.Glyph` supplies `▶`/`▼` from its `IsChecked` trigger. A consumer that also writes `Content="▼"` in XAML wins permanently and the glyph never flips. Local value beats style setter in WPF's precedence order; documented in § Interfaces-C, not mechanically catchable here (case 29).

**E-11 — `Segoe Fluent Icons` is Windows 11-only.** `TargetPlatformMinVersion` is `10.0.17763.0` (Windows 10 1809). `Broadsheet.Font.Glyph` must resolve to `Segoe UI Symbol` first, or every glyph in the frame becomes a tofu box on Windows 10.

**E-12 — the test's file copy must be `None`, not `Content`.** The test project sets `UseWPF=true`. A `Content`-typed `.xaml` risks being picked up by WPF item handling; `None` with `CopyToOutputDirectory` never becomes a `Page` and copies reliably in CI.

**E-13 — a selected `ListBoxItem` greys when its pane loses focus** unless the `IsSelected=True` + `Selector.IsSelectionActive=False` MultiTrigger is present. 3a shows the Scope row washed `accent-100` unconditionally; without the MultiTrigger the wash flips to the system inactive colour the moment the user clicks into the results pane (case 32).

**E-14 — `Application.Resources` is the last stop in resource lookup, and it is populated first.** `Application` construction loads `App.xaml`'s merged dictionaries before `StartupUri` builds the window, so app-level keys are always available to a view. It also means an *implicit* style added here would reach every control in the process including `ProfileNameDialog.xaml` — which is why invariant 1 is mechanically enforced rather than merely stated.

**E-15 — `Themes/` is a conventional name with one special case this task does not hit.** WPF gives `Themes/Generic.xaml` special meaning only for custom `Control` subclasses that set `DefaultStyleKeyProperty`. This library ships no custom control and no `Generic.xaml`, so the folder is an ordinary folder and the dictionaries load only because `App.xaml` merges them explicitly. Do not create a `Generic.xaml` "for consistency" — it would be auto-discovered and its contents applied implicitly, defeating invariant 1.

**E-16 — DPI and the tab underline interact.** At 150% scaling, a 2px underline with a −1 DIP margin can land a half-pixel off the 1px strip rule. `UseLayoutRounding="True"` on both the `TabItem` template root and the tab-strip band is what makes them meet; case 38 checks it on a real scaled display, not in the designer.

**E-17 — the working tree is already dirty.** 11 modified test files (+1,690 lines) and 2 untracked paths from an interrupted coverage run are sitting there. Commit this task with an explicit pathspec. Do not run `git add -A`.

## Risks

**R-1 — a key-name mismatch with T-001 is not a build error, and it is now the epic's single highest-value failure (the reason `BCL-02` and the S2 settlement exist).** WPF resolves resources at parse/render time, not compile time. With ~40 component keys pointing at ~25 token keys owned by a *different task*, and T-004–T-011 binding these component keys as literal strings, one prefix drift ships green and surfaces as an unstyled control — possibly weeks later, in T-008. This nearly happened: the previous draft used `Bs*` against T-001's `Broadsheet.*`, which would have made **every one of the ~40 published keys wrong at once**. *Mitigation:* S2 (adopt T-001's spelling verbatim), `BCL-02` (every reference resolves), `BCL-01` (every published key exists exactly once). *Residual:* the test only knows about keys defined in `Themes/`; a reference to a key in some future third dictionary would false-positive.

**R-2 — an implicit style would restyle the entire process.** An app-level `<Style TargetType="Button">` with no key reaches every `Button` in the app, `ProfileNameDialog.xaml`, all 21 help popups and every WPF-internal templated part. That single mistake converts a zero-visual commit into an unreviewable whole-app change. *Mitigation:* invariant 1 + `BCL-05` + E-15's warning against creating `Themes/Generic.xaml`. Treat any future request to "just make it implicit so consumers don't have to opt in" as a rejection.

**R-3 — a published abstraction with no consumer is worse than no abstraction.** The review found this task shipping a `HeaderedContentControl` tool-window while three consumer tasks hand-rolled `Border`+`DockPanel` headers and named keys this library never published — and separately, two consumer tasks inventing row containers and a disclosure toggle locally. A component library that consumers route around costs the epic twice: once to build it, once to reconcile the divergence. *Mitigation:* S4 and the six ★ keys adopt the consumers' own nouns so their diffs are prefix changes. *Standing check for the remaining consumer specs:* before T-004..T-009 is written, grep it for any `…Style` name not in § Interfaces-B — every hit is either a missing library key or a consumer going its own way.

**R-4 — duplicate ownership across specs.** Two independent duplications reached the panel: `HelpButtonStyle` moved by both T-002 and T-003 (with SPEC-010 edited twice for the same fact), and the pane splitters defined by both T-003 and T-005 in the same file path. Both are now settled one-owner (§ serves_spec, S5), but the class recurs whenever two specs touch the same file. *Mitigation:* case 23 makes a stray `HelpButtonStyle` in this diff a review rejection; the § Dependencies reciprocal-edit clause makes T-005's strike explicit rather than assumed.

**R-5 — no visual-regression harness exists, and this task cannot create one.** Everything in the § Acceptance "visual fidelity" block is a human eye against an HTML artboard. A wrong shade, a 1px offset, a hover state that never fires — none of it fails CI. *Mitigation:* keep the commit zero-visual so there is a trivially checkable invariant ("the app looks exactly as it did"), and defer real fidelity risk to the consumer tasks where the change is visible and reviewable. *Do not* claim the 100% coverage number says anything about styling.

**R-6 — `ComboBox.ItemContainerStyle` is a silent gap.** Because implicit styles are forbidden, a consumer that omits it gets WPF's default dropdown chrome — no error, no test failure, just a wrong-looking popup. Case 28 records this as an accepted gap; the only realistic mitigations are review discipline and the header comment. The same shape applies to a consumer setting `Content` on a glyph toggle (case 29).

**R-7 — `MainWindow.xaml.cs:190`'s string-keyed tab dispatch is fragile and one of its three branches is already dead.** Any `TabItem` styling that turns `Header` into a visual tree silently changes app behaviour with no test to catch it (`Views` is coverage-excluded and there are no UI tests). *Mitigation:* `Broadsheet.TabItem` ships no `HeaderTemplate`; the dead History branch is handed to T-004 explicitly rather than quietly inherited.

**R-8 — the `Tag` slot convention is untyped and will be forgotten.** After S4 it means two different things on two control types, and nothing enforces it. *Mitigation:* documented in two dictionary headers, in `ui.md`, and in § Interfaces-C. *Escape hatch:* decision D1-B trades this for typed attached properties at the cost of production C# under the coverage gate.

**R-9 — the ComboBox template is the single largest piece of hand-written WPF here.** A fully-replaced `ComboBox` chrome is where template-part mistakes cluster, and its failure mode (a dropdown that never opens) is only found by running the app. *Mitigation:* `BCL-08` asserts the three part names; the manual pass must actually open every dropdown, not just look at the closed pill.

**R-10 — the glyph font is a cross-task dependency on a token the design system never had.** If T-001 closes without `Broadsheet.Font.Glyph`, every `▾ ▼ ▶ ✓ ✕ ⋯ ↶` in the frame renders as tofu, with a green build and a passing coverage gate. *Mitigation:* the request is landed in T-001's acceptance **and** T-003 carries its own removable fallback with `BCL-10` asserting the key resolves from somewhere — so the worst case is a redundant definition and a `BCL-06` nudge to delete it, never a broken frame.

**R-11 — scope creep from turn 4.** This library sits one step from a semantic colour system: `Broadsheet.Brush.Accent2` is already in it for one string of text, and "while we're here, let's add a danger brush / tinted rows / duotone icons" is a natural-sounding review comment. It is out of scope by explicit user instruction; see § Out of scope. Reject it in review with a pointer there.

**R-12 — a dirty working tree at commit time.** An interrupted coverage run has left 11 modified test files (+1,690 lines) and 2 untracked paths. A bare `git commit -a` or `git add -A` would sweep them in and make this commit unreviewable. *Mitigation:* pathspec-scoped commit; § Acceptance case 43.

## Open decision

### Settled by the review panel — do not re-open

These five were open questions in the previous draft and are now closed. They are recorded because reversing any of them silently breaks a sibling task that binds by name.

- **S1 — Folder is `Themes/`, not `Styles/`.** T-001 ships `Themes/Broadsheet.Tokens.xaml`; T-004 and T-005 reference `Themes/`. One folder. (`Themes/Generic.xaml` is WPF-special only for custom `Control` subclasses with a `DefaultStyleKey`; this task ships none, so the conventional folder name carries no hidden behaviour — see § Edge cases E-15.)
- **S2 — Key prefix is T-001's `Broadsheet.` dotted namespace, verbatim.** No `Bs*` anywhere. T-001's contract explicitly forbids a third prefix, and T-004–T-011 bind these keys as literal strings; a prefix that differs by one character is a runtime failure with a green build (§ Risks R-1).
- **S3 — `DynamicResource` is for themeable values only.** Per T-001 contract §3: brushes and font families are `DynamicResource`; structural values (`CornerRadius`, `Thickness`, `Double`, `GridLength`) are `StaticResource`, so a typo throws at load instead of silently falling back to the property default. The previous blanket "`DynamicResource` for every token reference" is withdrawn — it produced `CornerRadius="{DynamicResource Broadsheet.Radius.Md}"`, which fails *silently* to `0` on a typo. Mechanically enforced by `BCL-03`.
- **S4 — the tool-window header is a `Border`, not a `HeaderedContentControl`.** T-006, T-007 and T-008 each hand-roll a `Border`+`DockPanel` 30px header and name a `ToolWindowHeaderStyle` / `ToolWindowHeaderBorderStyle` this task did not publish — three consumers, zero users of the flagship abstraction. T-003 now publishes the Border-based shape those tasks already assume (`Broadsheet.ToolWindow.Header` + `.HeaderTitle` + `.HeaderActions`, § Detail step 4), and the `HeaderedContentControl` template is dropped. Consequence: the header no longer needs a content slot, so decision D1 below shrinks from three slots to two.
- **S5 — T-003 owns the pane splitters.** They were duplicated with T-005's `Themes/Broadsheet.Frame.xaml` `PaneSplitter*` styles. T-003 is the component library, so the styles live here — **in the same file T-005 already names**, under T-005's own noun (`Broadsheet.PaneSplitter.Vertical` / `.Horizontal`), so T-005's consumer sites change by prefix only. **T-005 must strike its splitter-style definitions and consume these** (§ Dependencies).

### Two real forks that still need the user

**D1 — how a template receives its auxiliary content slot.** After S4 only two components need a slot the stock control lacks: the tab strip's right-aligned `Scan` + caption, and the text field's placeholder (`text or /regex/`).

- **Option A (§ Detail is written against this) — reuse `Tag`.** `<ContentPresenter Content="{TemplateBinding Tag}"/>` on the `TabControl`; `{TemplateBinding Tag}` for the placeholder. **Zero new C#, therefore zero movement under the 100% coverage gate**, and it matches the repo's own precedent (`HelpButtonStyle` carries its entire help body in `Tag`). Cost: `Tag` is untyped `object`, gives no IntelliSense, and is now spoken for on two control types.
- **Option B — typed attached properties** in `src/WindowsFileManager/Helpers/BroadsheetSlots.cs` (`Bs.TrailingContent`, `Bs.Placeholder`). Self-documenting. Cost: `Helpers/` is **inside** the coverage `Include` filter (`coverlet.runsettings:20`; `ARCHITECTURE.md:449` states it outright), so the file needs genuine 100% line/branch/method tests or a reviewed `[ExcludeFromCodeCoverage]` under ADR-011's regime. ~60 lines of production C# plus one test class, on a task that otherwise adds none.

Picking B changes exactly two template lines plus the new Helpers file and its guard test; nothing else in this spec moves.

**D2 — does the library ship a removable-chip style at all?** The epic prose calls Scope's *Skip folders named* entries "removable chips". **The 3a artboard does not draw chips** — verified at `Redesign Explorations.dc.html:159-162`: all three render as the *same* checkbox row used by *Target folders* directly above (14×14 square, `border:1.5px solid var(--color-accent)`, `border-radius:2px`, accent fill, `padding:5px 6px`). There is no `chip` class in the artboard and none in the Broadsheet design system.

- **Option A (recommended, § Detail is written against it) — no chip style.** Ship `Broadsheet.CheckBox` only; T-006 renders skip-folders as checkbox rows, exactly as drawn.
- **Option B — ship `Broadsheet.Chip` + `Broadsheet.Chip.Remove`** (~25 lines) and let T-006 choose. Costs a key that may never be consumed; a key with no consumer is dead XAML no analyzer flags.

*(Not a fork — recorded so nobody re-opens it: whether to embed the Source Serif 4 font file is **T-001's** call, since the font-family keys are tokens. T-003 consumes whatever T-001 defines and hard-codes a family in exactly one documented place, § Detail step 9.)*
