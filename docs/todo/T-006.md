## Concept

The Scope tool-window is the left 260px column of the 3a IDE frame: everything that answers *"what will the next scan look at, and what counts as a duplicate?"* — and nothing else.

Today those answers are scattered across two bordered boxes bolted above the tab control — originally `MainWindow.xaml:212-399`, relocated by T-002 into `Views/Chrome/ScanScopeBar.xaml` — that are **permanently visible on every tab**, including History, where they are meaningless. They occupy the full window width and roughly 130px of vertical space at all times, they use two different accent colours (`#C0C0C0`/`#E8EAF6` for targets, `#E65100`/`#FFE0B2` for excludes) for what is one idea, and they render both lists as `WrapPanel` chips — which means a user with eight target folders gets a reflowing block of chips with no stable row position, no keyboard navigation, and no room for per-folder information. A third piece of the same idea, the duplicate *matching mode*, lives somewhere else entirely: a `🔄 Use Regex` button inside the Duplication tab's filter bar, where it reads as a filter rather than as the scan's identity rule.

3a fixes this by IDE convention: one tool-window, one 30px header, one vertical stack of labelled sections, actions in the header rather than inline. The panel becomes a stable, scannable column — kicker label, list, kicker label, list, kicker label, control — and it is visible on the Duplicates screen where it applies rather than on all three.

The task is deliberately a *relocation with fidelity*, not a rewrite of scan behaviour. Every command the two old boxes bound to survives: `AddFolderCommand`, `AddFolderByPathCommand`, `RemoveFolderCommand`, `SelectAllTargetsCommand`, `ClearAllTargetsCommand`, `AddExcludeFolderCommand`, `RemoveExcludeFolderCommand`, `SelectAllExcludesCommand`, `ClearAllExcludesCommand`, `IncludeSubdirectories`, `ToggleDuplicateMatchModeCommand`'s effect. What changes is where they are, what they are called, and — the one genuinely new thing — that the panel now tells the truth about itself: a per-folder subfolder count so "Include subfolders" has a visible consequence, and a caption stating that the skip list is inert while Include subfolders is off, which has been true in `DuplicateScannerService` since 1.0.0 (SPEC-001 rule 3) and invisible to every user until now.

It is also the **first real consumer** of the T-001 token dictionary and the T-003 style catalogue: it must prove that a panel can be built with **zero** hardcoded hex and **zero** locally-invented resource keys, because three more tool-windows follow it.

**Padding and metrics, verbatim from the artboard:** header `height:30px; padding:0 12px`, title `font-weight:600`, actions `gap:12px; font-size:12px` — all of that is `BsToolWindowStyle`'s job, not this panel's. Body `padding:10px 12px 0`. Kicker `font-size:11px; letter-spacing:.08em; text-transform:uppercase; padding:4px 0`, and `margin-top:18px` on the second and third kickers only. List rows `padding:5px 6px; gap:8px`. Check indicator `14px × 14px; border:1.5px; border-radius:2px`. "Include subfolders" `margin:8px 6px 0; font-size:13px`, its dot `16px`. Segmented control `margin:4px 6px 0`, each segment `padding:5px 10px; font-size:12.5px`.

**Four structural decisions behind that shape:**

1. **The frame is `BsToolWindowStyle`, not a hand-built `Border`.** The panel's root element is a `HeaderedContentControl` with `Header="Scope"` and `Style="{DynamicResource BsToolWindowStyle}"`; the 30px bar, the SemiBold title, the 12px gap between actions and the 1px hairline all come from T-003's `ControlTemplate`. This panel supplies only the two action buttons, into the actions slot T-003 publishes (assumed `Tag`; see Interfaces). If T-003's template exposes no actions slot, **that is a T-003 gap to close in T-003** — T-006 does not work around it with a local header, or the four tool-windows of this epic ship four different headers.

2. **Each list is a `ListBox`, not the `ItemsControl`+`WrapPanel` it is today.** The artboard draws a vertical list with a filled selection row, which is a selection model, not a wrap of chips. A `ListBox` gives stable row order, arrow-key navigation, a focus rect, and a place for T-011 to hang `Delete`-key removal — for free, from the control we are already required to draw. Selection is presentational in this task: it binds to nothing in `MainViewModel`.

3. **Header actions replace the old inline button rows.** `+ Folder` is the browse dialog. Everything the two old boxes exposed as always-visible buttons — `✓ All`, `✕ Clear` (twice over), the typed-path `Add`, `Browse...` — moves behind `⋯`. Nothing is deleted; four commands that were four permanently-visible buttons become four menu items, which is what a 30px IDE header is for.

4. **The panel is honest about its own inertness.** SPEC-001 rule 3: exclusions are bypassed entirely when `IncludeSubdirectories` is false, because that mode visits no subdirectory. That has always been silently true. The panel now renders a one-line caption under the SKIP FOLDERS NAMED kicker when that condition holds, and dims the list. This is the same information the deleted `EXCLUDE FOLDER NAMES` popup should have carried and did not.

**Narrow-width behaviour (200–260px) — specified, not left to the splitter.** T-005's `PaneLayout.ScopeMinWidth` is **200**; T-006 does not ask for that to change and does not declare a floor of its own. Collapse order as the column narrows, from first to yield to never-yields:

| Rank | Element | Behaviour |
|---|---|---|
| 1 | `N sub` annotation | `Collapsed` once the panel's `ActualWidth` < **220** |
| 2 | Target / skip path text | `TextTrimming="CharacterEllipsis"`, full value in `ToolTip`, at all widths |
| 3 | `✕` row action | never yields — `Visibility="Hidden"` (reserves its 16px so hover causes no reflow), `Visible` on hover/focus |
| 4 | 14px check indicator | never yields |

The width test is a `DataTrigger` on `{Binding ActualWidth, RelativeSource={RelativeSource AncestorType={x:Type panels:ScopePanel}}}` through a new `WidthThresholdToBoolConverter` in `Helpers/Converters.cs` (`ActualWidth` is a notifying DP, so the trigger re-evaluates on every splitter drag). The converter goes in `Helpers/` deliberately: that namespace **is** inside the coverage `Include` (`[WindowsFileManager]WindowsFileManager.Helpers*`), so the threshold logic ships with tests instead of hiding in a `SizeChanged` handler under `Views/`.

**Where it lives:** `src/WindowsFileManager/Views/Panels/ScopePanel.xaml` — a `UserControl`, dropped into T-005's `Grid.Column="0"`. It inherits `MainViewModel` as `DataContext` from the window; it does not create its own. Because it sits under `Views/`, the coverage `Exclude` (`[WindowsFileManager]*Views*`) excludes it — which is precisely why the two pieces of real logic this task introduces (subfolder counting, width thresholding) are deliberately placed *outside* it, in `WindowsFileManager.Application` and `WindowsFileManager.Helpers`, where the 100% gate can reach them.

Two mechanics, both deliberate, replacing an earlier draft that would have failed deterministically:

- **The four command `MenuItem`s reach the view-model through `DataContext="{Binding PlacementTarget.DataContext, RelativeSource={RelativeSource Self}}"` on the `ContextMenu`.** A `ContextMenu` lives in its own `PopupRoot` and inherits no `DataContext` from its placement target's visual tree. This binding is a **property-path** binding on the `ContextMenu` itself — it involves no name lookup and therefore crosses the NameScope boundary correctly. Without it the four items bind to `null` and render permanently greyed, with no exception and no parse error.
- **The add-by-path reveal is a `DependencyProperty` on the panel driven by a `Click` handler — never an `ElementName` binding into the menu.** A `ContextMenu` establishes its **own NameScope**, so `Visibility="{Binding IsChecked, ElementName=AddByPathToggle, …}"` from the panel body to a `MenuItem` inside the menu **cannot resolve** — that is a deterministic failure, not a contingency. Event-handler wiring, by contrast, is compile-time and NameScope-independent: the `Click="AddByPath_Click"` handler is found because the `ContextMenu` is declared in this same XAML file. So:


Three mechanics that are load-bearing and easy to get wrong:

- **`RelativeSource AncestorType=UserControl`, not `AncestorType=Window`.** Every one of the seven `DataContext.<X>Command` bindings that today reads `AncestorType=Window` (pre-T-002 `MainWindow.xaml:303`, `:653`, …) must be rewritten when the markup moves into a `UserControl`. `AncestorType=Window` still *resolves* at runtime, so this is not a build error and not a XAML error — it is a binding that keeps working until someone hosts the panel outside a `Window`.
- **`ItemContainerStyle` must retemplate `ListBoxItem`.** Left alone, WPF paints its own `#FF0D7ADF` selection and hover fills over the Broadsheet palette. `BsListRowStyle` (T-003) sets `Padding="5,6"`, `BorderThickness="0"`, `HorizontalContentAlignment="Stretch"`, and a `ControlTemplate` whose `Border` responds to `IsSelected` → `Background = {DynamicResource BsAccent100Brush}` (`#e9f8ff`) and `IsMouseOver` → a 7%-ink wash. Without `HorizontalContentAlignment="Stretch"` the row content hugs left and the `2 sub` annotation never reaches the right edge.
- **The `✕` is hidden until hover or focus, and reserves its space.** `BsRowActionStyle` sets `Visibility="Hidden"` (not `Collapsed` — Hidden reserves layout width, so hovering causes no reflow) with two triggers: `IsMouseOver` on `{RelativeSource AncestorType=ListBoxItem}` → `Visible`, and `IsKeyboardFocusWithin` on the same ancestor → `Visible`. The focus trigger is not decoration — without it the remove action is mouse-only, which T-011 would have to come back and fix.

### Measured logic 1 — `FolderScopeService` (Application layer)

```csharp
namespace WindowsFileManager.Application.Services;

/// <summary>Answers questions about the shape of a scope folder.</summary>
public class FolderScopeService
{
    private readonly IFileSystemService _fileSystem;

    /// <summary>Initializes a new instance of the <see cref="FolderScopeService"/> class.</summary>
    /// <param name="fileSystem">The file-system abstraction.</param>
    public FolderScopeService(IFileSystemService fileSystem) => _fileSystem = fileSystem;

    /// <summary>Counts the immediate child directories of a folder.</summary>
    /// <param name="path">The folder to inspect.</param>
    /// <returns>The count, or <see langword="null"/> when the folder cannot be read.</returns>
    public int? CountImmediateSubfolders(string path)
    {
        if (string.IsNullOrWhiteSpace(path) || !_fileSystem.DirectoryExists(path))
        {
            return null;
        }

        try
        {
            return _fileSystem.EnumerateDirectories(path).Count();
        }
        catch (UnauthorizedAccessException)
        {
            return null;
        }
        catch (IOException)
        {
            return null;
        }
    }
}
```

It goes in the Application layer **on purpose**: `Views/` is excluded by the runsettings and `MainViewModel`/`ToggleItem` carry `[ExcludeFromCodeCoverage]`, so logic placed in either is logic nobody ever tests. `WindowsFileManager.Application` is in the `Include` and already references `WindowsFileManager.Core`, where `IFileSystemService` lives (`Core/Services/IFileSystemService.cs:45,86`) — no new project reference is needed. This class is inside `Include` and therefore ships with tests or the build fails.

`.Count()` sits **inside** the `try` on purpose: `Directory.EnumerateDirectories` is lazily evaluated, so an access or I/O failure surfaces during enumeration, not at the call. The tests must therefore drive the failure arms with a **throwing iterator** (a `yield`-based helper that throws on first `MoveNext`), not with `.Throws()` on the mock's return, or the catch arms are never entered.

### Measured logic 2 — `WidthThresholdToBoolConverter` (Helpers, also measured)

```csharp
/// <summary>Reports whether a measured width is below a threshold passed as the parameter.</summary>
public class WidthThresholdToBoolConverter : IValueConverter
{

    public static readonly WidthThresholdToBoolConverter Instance = new();

    /// <inheritdoc/>
    public object Convert(object value, Type targetType, object parameter, CultureInfo culture)
    {
        if (value is double width && parameter is string paramStr &&
            double.TryParse(paramStr, NumberStyles.Float, CultureInfo.InvariantCulture, out var threshold))
        {
            return width < threshold;
        }

        return false;
    }

    /// <inheritdoc/>
    public object ConvertBack(object value, Type targetType, object parameter, CultureInfo culture)
    {
        throw new NotSupportedException();
    }
}
```

`CultureInfo.InvariantCulture` is deliberate — the parameter is a XAML literal, not user input, and a comma-decimal locale must not change what `220` means.

### Orchestration (unmeasured, and honest about it)

`MainViewModel.RefreshSubfolderCountsAsync` stays in the excluded view-model because it is pure plumbing: snapshot `TargetPaths` into a `List<(ToggleItem, string)>` on the UI thread, `await Task.Run(...)` to call `CountImmediateSubfolders` for each, then marshal every assignment back with `Application.Current.Dispatcher.InvokeAsync` — `ToggleItem.SubfolderCount` raises `PropertyChanged` into a live `ListBox`, and WPF throws `InvalidOperationException` if that happens off the UI thread. Call sites: `AddFolder` and `AddFolderByPath` (the one new item only), and `ApplyProfile` (the whole list, fire-and-forget). **Not** called from `RemoveFolder`, the enable/disable toggle, or the skip-list paths — under Fork 2 option (a) the number does not depend on any of them.

## Edge cases

- **`ContextMenu` NameScope — the one that would have shipped broken.** A `ContextMenu` lives in its own `PopupRoot` **and establishes its own NameScope**. Two consequences, handled differently: (1) it inherits no `DataContext`, fixed by the `PlacementTarget.DataContext` property-path binding on the `ContextMenu` itself (property paths cross the boundary fine — matrix row 35); (2) `ElementName` **cannot** resolve across it in either direction, so the add-by-path reveal uses a `ScopePanel` `DependencyProperty` set from a `Click` handler instead (matrix row 36). Event-handler wiring is compile-time and NameScope-independent, which is why the handler route is deterministic where the binding route is deterministically dead. Neither failure raises an exception or a parse error, which is why both get matrix rows.
- **The `+ Add` skip toggle is a different case and keeps `ElementName`.** `AddSkipToggle` sits in the panel's own visual tree beside the kicker, sharing one NameScope with the row it reveals. Do not "fix" it into a second `DependencyProperty` — the menu was the only crossing.
- **`AncestorType=Window` survives the move.** Copying `Command="{Binding DataContext.RemoveFolderCommand, RelativeSource={RelativeSource AncestorType=Window}}"` verbatim out of the old chrome into the `UserControl` *works today* — the panel is inside a `Window`. It is still wrong, and it will break the day the panel is hosted in a dialog or a designer surface. Every relocated `AncestorType=Window` becomes `AncestorType=UserControl`.
- **`ObservableCollection` item mutation off the UI thread.** `RefreshSubfolderCountsAsync` runs the count on `Task.Run`; assigning `ToggleItem.SubfolderCount` from that thread raises `PropertyChanged` into a bound `ListBox` and throws `InvalidOperationException: The calling thread cannot access this object`. Every assignment marshals back through `Dispatcher.InvokeAsync`.
- **A target removed while its count is in flight.** The background task holds a `ToggleItem` reference for an item the user has since removed. Setting `SubfolderCount` on an orphan is harmless (no live binding, GC collects it) — but the code must not re-index into `TargetPaths` by position, because positions shift.
- **`{x:Null}` in a `DataTrigger`.** `<DataTrigger Binding="{Binding SubfolderCount}" Value="{x:Null}">` matches an unset `int?`. `Value="0"` matches the boxed integer via `TypeConverter`. Both triggers are needed — `null` and `0` are different states with the same rendering, and using only the `StringFormat`'s empty output would leave a `0 sub` visible. The third trigger (narrow width) sets the same `Visibility="Collapsed"`, so the three OR cleanly; none of them needs to un-set, because the `Style` has no `Visibility` `Setter` at rest.
- **The count is not "what Explorer shows", and SPEC-001 must say so.** `FileSystemService.EnumerateDirectories` passes `IgnoreInaccessible = true` and `AttributesToSkip = FileAttributes.System` (`Infrastructure/Services/FileSystemService.cs:52-58`). So on a drive root, `$RECYCLE.BIN` and `System Volume Information` are **excluded** from the count (system-attributed), and an unreadable child is silently skipped rather than throwing. This differs from an earlier reading of this spec, and it means the annotation is "children the scanner would see", which is the useful number — one sentence in SPEC-001 so a `4 sub` on a nearly-empty drive is not filed as a bug.
- **Which catch arm is actually reachable in production.** `IgnoreInaccessible` suppresses *child* access failures only; a `UnauthorizedAccessException` still escapes when the **target folder itself** is unreadable, and `PathTooLongException` (an `IOException`) can escape from a child path beyond `MAX_PATH`. Both arms are real, and both are covered deterministically in tests via a mocked `IFileSystemService` rather than by hunting for a real folder that reproduces them.
- **`.Count()` must sit inside the `try`.** `Directory.EnumerateDirectories` is lazy: the exception surfaces during enumeration, not at the call. A test that mocks `.Throws()` on the method call rather than returning a throwing iterator will pass while the production catch arms never execute — the coverage report would show them uncovered and the build would fail, which is the gate doing its job.
- **`PathTooLongException` from `DirectoryExists`, before the `try`.** `Directory.Exists` returns `false` rather than throwing for over-long paths in .NET 8, so the guard is safe — but if `FileSystemService.DirectoryExists` is ever reimplemented to propagate, the guard needs its own `try`. Assert the current behaviour in test 4 rather than assuming it.
- **Segmented-control write ordering.** Both `RadioButton`s bind `TwoWay` to the same source property; a click produces two writes (the newly-checked one, then the auto-unchecked one). Both resolve to the same value and `ViewModelBase.SetProperty`'s equality short-circuit swallows the second — but if anyone later replaces `SetProperty` with an unconditional raise, this becomes a double `SaveSettings()` per click and a disk write per toggle.
- **`GroupName` collisions.** `RadioButton.GroupName` is matched by string across the whole logical tree, not per-container. `ScopeMatchMode` must not be reused by T-007's toolbar or T-008's Rules panel, or a click in one panel will uncheck a radio in the other.
- **`ScrollViewer` nesting.** If a `ListBox` keeps its default `VerticalScrollBarVisibility="Auto"`, it swallows the mouse wheel and the outer panel scroller becomes unreachable once the pointer is over a list — the panel appears frozen at the top. `Disabled` on both `ListBox`es is not cosmetic.
- **`ActualWidth` as a trigger source.** `FrameworkElement.ActualWidth` is a read-only DP that notifies, so the narrow-width `DataTrigger` re-evaluates during a splitter drag — but it is `0` until the first layout pass, and `0 < 220` is `true`, so the annotation is briefly collapsed on load and appears on first arrange. Acceptable (sub-second, and the count is async anyway); do not "fix" it with a `Loaded` handler.
- **Letter-spacing.** WPF has no CSS `letter-spacing`. The kicker's `.08em` at 11px is `BsKickerStyle`'s problem, not this panel's — but if T-003 ships it without tracking, record the deviation in the commit rather than silently calling un-tracked kickers fidelity.
- **`Source Serif 4` missing on the machine.** WPF falls back per the `FontFamily` fallback list. `BsHeadingFontFamily` must carry a real fallback (`Source Serif 4, Segoe UI`), or every label silently reflows to the WPF default and the 260px measurements stop holding.
- **A scan running while the panel is edited.** `IsScanning` disables the target checkboxes and `Include subfolders`, but **not** `+ Folder` removal or the skip list today. `ScanOptions` is snapshotted at scan start (SPEC-001 rule 14), so a mid-scan edit cannot corrupt the run — but the panel will show a list that does not match what is being scanned. Out of scope to fix; worth a line in SPEC-001 so it is a known, documented state rather than a surprise.
- **Deleting the two help popups leaves `FormattedTextBehavior` with 19 consumers, not 0.** No dead-code removal is triggered; `HelpButtonStyle` stays in use until T-010.

## Open decision

Two genuine forks. Neither blocks the start of work — a recommended default is given for each so the engineer can build — but both change user-visible behaviour and both should get an explicit answer before merge.

**Fork 1 — where does the name-pattern regex box live once the mode switch moves to Scope?** `MainViewModel.DuplicateMatchRegex` is the pattern string; today its `TextBox` lives inside the *Match by Name Regex* filter bar (`MainWindow.xaml` ~line 1035), which is the whole bar that the Scope segmented control now replaces as the mode selector. The 3a artboard shows the segmented control in Scope **and shows no pattern field anywhere** — not in Scope, not in the results toolbar (which is exactly `Type · Copies ≥ · Size ≥ · Sort · Mark`). So the artboard does not answer it. Options:
  - **(a) Inline in Scope, revealed only in Name-pattern mode.** A single-line `TextBox` appears directly under the segmented control when `DuplicateMatchByRegex` is true. Pro: the whole "how do I identify a duplicate" question lives in one panel, which is what a Scope tool-window is for; the mode toggle and its one parameter are never separated. Con: adds a row the artboard does not draw, and 260px is tight for a regex. **← Recommended.**
  - **(b) Stays in the results editor toolbar (T-007 owns it).** The segmented control in Scope drives visibility of a pattern field in the centre toolbar. Pro: exact artboard fidelity for Scope. Con: splits one setting across two panels and puts a scan *input* in a *results* toolbar; also makes T-006 and T-007 co-own one feature.
  - **(c) `⋯ → Edit match pattern…` dialog.** Pro: zero artboard deviation. Con: a modal for a field the user iterates on is hostile; regressions the current inline-edit workflow.

  Everything except the pattern box's location is settled: the mode itself is a Scope control per the artboard. If (b) is chosen, this task ships only the segmented control and hands the pattern field to T-007 as a stated interface.

**Fork 2 — what does "2 sub" count?** The artboard annotates one target row with `2 sub` and leaves the other two blank. Two readings, and they are not the same number:
  - **(a) Immediate child directories of that folder, unfiltered.** Cheap (one `EnumerateDirectories`), stable, does not change when the user edits the skip list or unchecks Include subfolders. Reads as "this folder has 2 subfolders in it". **← Recommended.**
  - **(b) Subfolders the *next scan will actually visit*** — i.e. immediate children minus skip-list matches, and **0 / hidden entirely** when `Include subfolders` is off. Reads as "2 subfolders will be scanned". Genuinely more useful in a panel called *Scope*, and it makes the skip-list's effect visible. Con: recomputes on every skip-list edit and on the Include-subfolders toggle; the number is now a promise about scan behaviour that must stay correct, which is a bigger contract than an annotation deserves.
  - **(c) Full recursive descendant count.** Rejected — unbounded I/O on a deep tree for a decoration.

  The recommendation is (a) plus the honest caption for the inert-skip-list case (see Detail), which gets most of (b)'s value without making the number a behavioural promise. If (b) is chosen, add a `RefreshSubfolderCounts` call to the skip-list mutation paths and to the `IncludeSubdirectories` setter, and the annotation becomes SPEC-001 behaviour rather than SPEC-001 decoration.

**Explicitly NOT forks — resolved here, recorded so nobody re-opens them:**

1. **Chips vs checkbox rows for the skip list.** The epic brief calls the skip entries "removable chips" while the artboard renders them as accent-filled **checkbox rows** identical in shape to the target rows. The artboard wins on visuals, because chips would silently drop the per-entry enable toggle that `ProfileSettings.DisabledExcludeFolderNames` persists (SPEC-009 rule 6). Resolution: checkbox rows exactly as drawn, **plus** a hover- and focus-revealed `✕` for removal — the artboard's resting pixels are preserved and no persisted feature is lost.

2. **Resource key names come from T-001/T-003, not from this task.** An earlier draft of this spec invented `Brush.Accent100`, `BroadsheetSquareCheckBoxStyle`, `SegmentButtonStyle`, `ScopeRowContainerStyle`, `RowRemoveButtonStyle`, `ToolWindowActionLinkStyle`, `SectionKickerTextStyle`. None of those exist: T-001 publishes `Bs<Name>Brush` tokens (`BsAccent100Brush`) and T-003 publishes `BsToolWindowStyle`, `BsCheckBoxStyle`, `BsSegmentStyle`, `BsLinkStyle`. Resolution: **T-006 consumes T-003's published keys verbatim and invents none.** The three components T-003's catalogue does not yet name (the list row container, the row `✕`, the section kicker) are **requested from T-003 in T-003's own naming convention** — `BsListRowStyle`, `BsRowActionStyle`, `BsKickerStyle` — and T-006 does not start until they are published. A locally-defined duplicate style is exactly the drift T-001/T-003 exist to end.

3. **The panel does not hand-build its 30px header.** T-003 publishes `BsToolWindowStyle` (a `HeaderedContentControl` style) for the tool-window frame. Resolution: the Scope panel's root is a `HeaderedContentControl` styled with `BsToolWindowStyle`; header actions go in the slot T-003 publishes for them. Four panels must not ship four hand-rolled headers.

4. **Minimum width: 200px, T-005's number, not 220.** T-005 sets `PaneLayout.ScopeMinWidth = 200` and lets the splitter reach it. T-006 **conforms to 200 and specifies the degradation**, rather than asking T-005 to raise its floor: below 220px the `N sub` annotation collapses, the path ellipsizes, and the checkbox and the `✕` never yield. See Design → *Narrow-width behaviour*.
