## Concept

The IDE metaphor that 3a borrows is not only a visual idea — it is an *accessibility model*, and adopting it is what makes the frame keyboard-navigable at all.

Counted off the artboard, 3a exposes roughly **38 interactive controls**: 3 window buttons, a profile switcher, 3 tabs, `Scan`, 2 Scope header actions, 3 target-folder checkboxes, `Include subfolders`, `+ Add`, 3 skip-name chips, a 2-way segmented control, 2 splitters, `Expand all` / `Collapse all`, 4 filter inputs, 5 `Mark` verbs, the group tree with 4 verbs per row, 2 Preview header actions, 4 Rules header actions, 2 rule checkboxes, a 4-part compose row, 2 action-bar buttons, and one undo. Wire that as a flat Tab ring and reaching `Recycle 4 files` from the tab strip costs about thirty keystrokes. The redesign would ship *worse* keyboard access than the three-tab baseline it replaces — precisely the regression the planner warns about.

IntelliJ's answer, which 3a already imports visually, is that **the region is the unit of navigation**. Tab is scoped *inside* the focused region; a separate key cycles *between* regions. The obvious first cut of that idea — four stops, one per tool-window — is wrong, and the panel caught it: `TabNavigation="Cycle"` means Tab can never leave a region, so a four-stop ring silently strands the title bar, the tab strip's trailing `Scan`, the action bar and the status bar's undo with no way in at all. The ring must cover **every** region of the frame or it is not a navigation model, it is a trap with four doors. So it is eight stops, in reading order, and the action bar is its own stop rather than the tail of a long Results ring — which is also what keeps `Recycle 4 files` four keystrokes from the tab strip instead of thirty.

The 30px headers that 3a draws for visual grouping become the announced landmark names; the two 1px splitters that 3a draws as dividers become the focusable resize controls that let a keyboard user do what a mouse user does by dragging.

The second half is the contrast audit, and it turned up something the artboard cannot show: the Broadsheet light palette, rendered at 12–13px, fails AA on its captions, its links and its primary button — and on the status text and links it is *demonstrably worse than the app being replaced* (3.55:1 vs 5.27:1; 3.37:1 vs 5.75:1). A design-token dictionary (T-001) is the first moment in this codebase's life where that is checkable at all: 70 hardcoded hexes scattered through a 2,796-line file can only be audited by eye, but a dictionary of named brushes can be parsed by a test. That is why this task now runs **before** T-001 rather than after it: the audit is T-001's input, not its post-mortem, and the alternative is freezing a palette twice.

So this task is not a coat of ARIA-equivalent paint applied after the fact, and it is not a retrofit pass over seven merged files either. It is **the contract every other task builds against** — a name, a heading level, a tab scope and a focus visual per control, written down before the control exists — plus the three mechanical gates that keep the contract true after everyone has moved on.

The honest constraint sits underneath everything: `Views/*` is excluded from coverage, `MainViewModel` and every WPF-bound behaviour carry `[ExcludeFromCodeCoverage]`, and there is no UI test harness. Nothing here can prove that focus *visibly* lands somewhere. So the design deliberately pushes every checkable thing — contrast maths, accessible-name strings, palette conformance, and the presence of `AutomationProperties` in XAML — out of the untestable layer and into three mechanical gates, and states plainly that the screen-reader pass is manual and evidence-recorded.

## Design

| Phase | Contents | Runs |

**1 — Navigation model: eight region stops, local rings inside.**

Every region of the 3a frame is in the ring. Nothing is reachable only by mouse.

| # | F6 stop | Contents |
|---|---|---|
| 1 | Title bar | profile switcher, minimise / maximise / close |
| 2 | Tab strip | Duplicates · Folders · History (one stop, arrow keys within) + `Scan` |
| 3 | Scope tool-window | target list, include-subfolders, skip chips, `+ Add`, match-mode radios |
| 4 | Results editor | header actions, the one toolbar row, the group tree |
| 5 | Action bar | `Move to…`, `Recycle N files` |
| 6 | Preview tool-window | `Auto ✓`, `✕`, metadata |
| 7 | Rules tool-window | header actions, rule rows, compose row |
| 8 | Status bar | `↶ Undo` (the resource readouts are non-focusable text with names) |

The two splitters are focusable and sit in the **Tab** ring of the region to their left (Scope owns the Scope↔Results splitter; Results owns Results↔right-stack), so they are reachable without adding ring stops that a user would have to page through.

| Key | Behaviour | WPF mechanism |
|---|---|---|
| `Tab` / `Shift+Tab` | Cycles **within** the focused region only, wrapping | `KeyboardNavigation.TabNavigation="Cycle"` on each region root |
| `F6` / `Shift+F6` | Next / previous region, wrapping 1→8→1; **skips a region with no focusable control** | `ShellCommands.NextRegion` / `PreviousRegion`, `RoutedUICommand`, handled in the shell (T-004) |
| `Ctrl+Tab` / `Ctrl+Shift+Tab` | Next / previous editor tab | `TabControl` default; `KeyboardNavigation.ControlTabNavigation="Cycle"` |
| `←` `→` on the tab strip | Move between tabs when the strip has focus | `TabControl` default |
| `↑` `↓` in the results tree | Move between rows | `KeyboardNavigation.DirectionalNavigation="Contained"` |
| `←` `→` on a group row | Collapse / expand | `TreeViewItem` default |
| `F1` | Caption help for the focused control | `ShellCommands.ContextHelp`, `Window.InputBindings` |
| `Applications` / `Shift+F10` | Row context menu carrying the per-copy verbs | `ContextMenu` on the row `DataTemplate` |
| `Esc` | Close Preview; cancel an in-flight splitter drag | `ShellCommands.ClosePreview`; `GridSplitter` handles Esc natively |
| `Alt+<letter>` | Access keys — see §5 | `AccessText` via `_` in `Content` |

`F6` is chosen over `Ctrl+Tab` for regions precisely because `Ctrl+Tab` must stay on the editor tabs to match the IDE convention 3a claims.

Distance check, against the acceptance bar: tab strip → `Recycle 4 files` = `F6 F6 F6` (Scope, Results, Action bar) + `Tab` = **4 keystrokes**, or `Alt+R` = 1. Worst case anywhere-to-anywhere is 4 `F6` presses because the ring wraps in both directions.

**2 — Focus visibility: two mechanisms, because one is not enough.**

WPF's default focus visual is a 1px dotted `#000000` rectangle. On dense 30px rows over `#f3f2f2` it is nearly invisible and stylistically foreign to Broadsheet. Two replacements, deliberately different — **both authored in T-003's component library** against T-001's brushes; this task supplies the recipe, the contrast maths and the acceptance:

- **Adorner ring** for buttons, links, inputs, combos, splitters — a `FocusVisualStyle` drawing a 2px focus-brush rectangle at `Margin="-2"`. WPF renders `FocusVisualStyle` only when focus arrived from the keyboard, which gives "ring on Tab, none on click" for free.
- **In-template trigger** for list rows — an `IsKeyboardFocused` / `IsSelected` trigger **inside T-007's own item-container template**, painting a 3px accent left edge bar. Row focus **cannot** rely on the adorner: adorners are clipped by the `ScrollViewer` of a virtualising `ItemsControl`, so a focused row scrolled to the viewport edge would lose its ring entirely.

`accent-700 #006786` clears 3:1 against every ground in the frame — `bg` 5.72, `surface` 5.28, `neutral-100` 5.86, `accent-100` 5.89. The one place it fails is *inside* the filled primary button (ring on fill = 1.00:1), so the primary-button style needs a second focus brush; whichever pair ships under Fork 1, `PaletteContrastTests` pins it.

**3 — Naming: the frame announces itself.**

Each of the four tool-windows gets `AutomationProperties.Name` from its 30px header text and `HeadingLevel="Level2"`, so a screen reader's heading list reads *Scope · Duplicate groups · Preview · Rules*. The other four regions get a `Name` but no heading level (they are chrome, not content). Icon-only and glyph-only controls get explicit names; this is where the baseline is worst (`Content="↶"`, `"⋯"`, `"✕"`, `"▢"`, and the help `ToggleButton` whose `Content` is empty because the glyph is hardcoded in its template).

**4 — Live regions, scoped narrowly on purpose.**

`StatusMessage` becomes an `AutomationLiveSetting.Polite` region so scan completion and recycle results are announced without stealing focus. The three resource strings sharing that bar must be **excluded**: SPEC-006 rule 19 documents a `DispatcherTimer` at `Interval = 2 s` that "is never stopped or disposed — it runs for the process lifetime." A live region spanning the whole status bar would speak `RAM … CPU … Threads …` every two seconds forever — worse than the silent baseline. They get `LiveSetting="Off"` and a name. **Wired by T-009**, which builds the status bar; the recipe and the exclusion rationale are below in `## Detail`.

**5 — Access keys, and the template trap that silently kills them.**

`Alt+S` Scan · `Alt+F` + Folder · `Alt+A` + Add · `Alt+M` Move to… · `Alt+R` Recycle · `Alt+U` Undo · `Alt+E` Expand all · `Alt+C` Collapse all. The full allocation table lives in SPEC-011 so the next person adding a button checks it before inventing a collision.

Access keys only work when the templated `ContentPresenter` carries `RecognizesAccessKey="True"`, and the default for that property in a hand-written `ControlTemplate` is `False`. T-003 replaces every button template in this app, so **that requirement is an acceptance item on T-003**, and lint rule 5 catches it, because the failure mode is silent — the underline simply never appears and `Alt+S` does nothing.

**6 — Splitters as controls, not decoration.**

3a's splitters are 1px. A 1px `GridSplitter` is a 1px mouse target and a 1px focus ring. The splitter renders a 1px `divider` line but hit-tests 9px wide via negative margin, and carries a name, a `KeyboardIncrement` large enough to be usable, and a focus ring on the wider bounds. `GridSplitter` is focusable and handles arrow keys natively; its `GridSplitterAutomationPeer` exposes `ITransformProvider`, so panel resize reaches assistive tech without custom peer code. **Built by T-005**; the sizing, naming and `MinWidth` numbers are acceptance items on it.

**7 — Verification, layered honestly.**

| Layer | What it proves | Where it runs | Owner |
|---|---|---|---|
| `ContrastRatio` + `AccessibleNames` unit tests | the maths and the announced strings are correct | under the 100% gate | T-011 |
| `PaletteContrastTests` (XDocument over the shipped `.xaml`) | every token role pair meets its target, and the shipped hexes are the ones the fork chose | CI, no STA, no UI | T-011 |
| `scripts/Check-Accessibility.ps1` | every control that must carry a name does; no literal hex escaped into `Views/`; no template drops `RecognizesAccessKey` | CI gate 3c | T-011 |
| NVDA + keyboard-only checklist | focus is actually *visible*, order is actually sensible, announcements are actually useful | manual, dated + sha-stamped in SPEC-011 | T-011 |
| Per-control attributes, structure, styles | the frame satisfies the contract | each owning task's own acceptance | T-003 – T-010 |

The fourth row is not automatable in this repo and the spec says so rather than implying otherwise.

## Detail

### Files this task authors

**`src/WindowsFileManager/Helpers/ContrastRatio.cs`** — pure static, **no `[ExcludeFromCodeCoverage]`**, therefore measured by the `[WindowsFileManager]WindowsFileManager.Helpers*` include in `coverlet.runsettings` and under the 100% gate.

```csharp
public static class ContrastRatio
{
    public static Color ParseHex(string hex);                        // "#RRGGBB" and WPF's "#AARRGGBB"
    public static Color Flatten(Color foreground, Color background); // composites a non-opaque token
    public static double RelativeLuminance(Color color);             // WCAG 2.x sRGB formula
    public static double Between(Color a, Color b);
    public static bool MeetsAaText(Color fg, Color bg, bool isLargeText);   // 4.5 : 3.0
    public static bool MeetsNonText(Color fg, Color bg);                    // 3.0
}
```
`System.Windows.Media.Color` is a struct with no dispatcher affinity, so every one of these runs on the xUnit worker thread with no STA helper and no new package. `ParseHex` throws `FormatException` on a bad string — a branch the tests must hit for the 100% branch bar. `Flatten` exists because `--color-divider` is `color-mix(in srgb, #201e1d 16%, transparent)`, which lands in XAML as `#29201E1D`; comparing an alpha colour without compositing gives a meaningless ratio.

**`src/WindowsFileManager/Helpers/AccessibleNames.cs`** — pure static, measured, under the gate. Every method takes an `IFormatProvider` so tests are culture-deterministic and CI cannot flake on a locale.

```csharp
public static string ForUndo(ActionHistoryKind kind, int itemCount, DateTime at, IFormatProvider p);
public static string ForDuplicateGroup(string fileName, int copyCount, long sizeEach, long wasted, IFormatProvider p);
public static string ForKeepChoice(string fileName, bool isKept, IFormatProvider p);
public static string ForMarkSummary(int markedCount, long totalBytes, IFormatProvider p);
public static string ForSplitter(string leftPanel, string rightPanel, IFormatProvider p);
public static string ForRegion(string header, IFormatProvider p);
```
These exist because the visible strings are glyph-and-middot compositions a screen reader mangles. `↶` announces as nothing useful; `IMG_2041.jpg — 3 copies · 6.2 MB each · 12.4 MB wasted` announces the `·` as "middle dot" three times. `ForUndo` switches on `ActionHistoryKind` (`MoveFiles` · `RecycleFiles` · `RecycleDirectories` · `CreateShortcuts`, ordinals frozen per SPEC-004 rule 26) — four branches plus a default, all of which the tests must reach. The consuming tasks bind these; this task ships and proves them.

**`tests/WindowsFileManager.Tests/Helpers/ContrastRatioTests.cs`**, **`AccessibleNamesTests.cs`** — the 100% obligation for both types, including the culture `[Theory]`.

**`tests/WindowsFileManager.Tests/Themes/PaletteContrastTests.cs`** — parses the shipped `Broadsheet.Tokens.xaml` with `System.Xml.Linq` and asserts a declared table of `(foregroundKey, backgroundKey, targetRatio, expectedHex)` tuples. Three properties make it a gate rather than a comment:
1. **Ratio pinning** — every declared pair meets its target, with the failure message naming both keys and the measured ratio.
2. **Value pinning** — each role's hex is asserted against the value Fork 1 selected, so a token edited in T-001 without a corresponding audit fails here. This is the mechanism that stops T-001 and T-011 disagreeing.
3. **Completeness guard** — a `Broadsheet.Brush.Text.*` or `.Link*` key present in the dictionary with no assertion fails the test, so adding a role silently is impossible. An asserted key absent from the dictionary fails naming the key, never `KeyNotFoundException`.

Both `<SolidColorBrush x:Key="…" Color="#…"/>` and `<Color x:Key="…">#…</Color>` element forms are parsed. A missing dictionary file is an explicit failure, not a vacuous pass.

**`scripts/Check-Accessibility.ps1`** — parses every `src/WindowsFileManager/Views/**/*.xaml` with `[xml]` and fails non-zero on:

1. `Button` / `ToggleButton` / `RepeatButton` / `MenuItem` whose `Content` is absent, empty, or a single non-alphanumeric glyph (`↶ ⋯ ✕ ▢ — ▼ +`), with no `AutomationProperties.Name`.
2. `TextBox` / `ComboBox` / `PasswordBox` / `Slider` with neither `AutomationProperties.Name` nor `AutomationProperties.LabeledBy`.
3. `GridSplitter` with no `AutomationProperties.Name`.
4. Any literal `#RRGGBB` / `#AARRGGBB` in a `Foreground` / `Background` / `BorderBrush` / `Fill` / `Stroke` attribute under `Views/` — enforces T-001's "all colour through tokens" rule, which is also what keeps `PaletteContrastTests` authoritative rather than advisory.
5. A `ContentPresenter` inside a `ControlTemplate` whose `TargetType` is a `ButtonBase` descendant, lacking `RecognizesAccessKey="True"` — the silent access-key killer.
6. A `TabItem` whose `Header` is non-text (a `TextBlock` child, an emoji) with no `AutomationProperties.Name` — today's `🕘 History` tab at `MainWindow.xaml:1715` announces the emoji.

Ships with six seeded negative fixtures (one per rule) plus two positives, under `tests/fixtures/accessibility-lint/`, so the lint's own failure behaviour is provable.

**CI wiring** — `.github/workflows/ci.yml` gains **Gate 3c, *Accessibility lint***, inserted immediately after Gate 3b (*Coverage threshold*), `run: ./scripts/Check-Accessibility.ps1`, `shell: pwsh`, matching how `Check-Coverage.ps1` is invoked. Gate 4 (*Dependency audit*) and Gate 5 (*Upload coverage*) keep their numbers — the earlier draft's "gate 5" collided with the existing upload step.

**`docs/specs/SPEC-011-keyboard-access-and-accessibility.md`** — from `_TEMPLATE.md`, carrying the eight-stop ring table, the access-key allocation table, the naming inventory, the contrast table (baseline · 3a · shipped, with measured ratios), the gate descriptions, and a **Not implemented** section stating plainly that no automated test proves focus is visible, that Windows High Contrast is unsupported, and that nothing is localised.

### Contracts handed to other tasks

These are the *content* of the handed-back acceptance items in `## Interfaces` → *Provided*. They are written here once so the owning task can build them in rather than have them retrofitted.

**Token roles → T-001.** T-001's published contract must carry these role keys; this task supplies the list and (once Fork 1 is answered) the values. No dictionary is declared here.

`Broadsheet.Brush.Text.Primary` · `Text.Secondary` · `Text.Disabled` · `Link` · `Link.Hover` · `Accent` · `Accent.Strong` · `Accent.Tint` · `Destructive` · `Focus` · `Focus.OnAccent` · `Divider` · `ControlBorder` · `Surface` · `Surface.Raised` · `Background`

Two hard constraints on that dictionary:
- Every brush referenced from a `Style` or `ControlTemplate` uses **`DynamicResource`**, never `StaticResource`. This costs nothing today and is the single thing that keeps a future Windows High Contrast dictionary (out of scope) from being a rewrite.
- `ControlBorder` is **not** `Divider`. `divider` resolves to `#d1d0d0` over `bg` — **1.38:1**, far under the 3:1 SC 1.4.11 bar for a control boundary. Decorative 30px header hairlines may keep `divider`; the borders of checkboxes, radios, text inputs and combos need `neutral-600 #7d7979` (3.85:1) or darker. `neutral-500 #9b9797` at 2.59:1 is not sufficient for the unchecked-checkbox border the artboard draws.

**Focus visual + touch target styles → T-003.** Authored in T-003's component library, keyed so callers reference rather than copy. Recipe:

```xml
<Style x:Key="Broadsheet.FocusVisual" TargetType="{x:Type Control}">
  <Setter Property="Template">
    <Setter.Value>
      <ControlTemplate>
        <Rectangle Margin="-2" StrokeThickness="2" RadiusX="2" RadiusY="2"
                   Stroke="{DynamicResource Broadsheet.Brush.Focus}"
                   SnapsToDevicePixels="True" />
      </ControlTemplate>
    </Setter.Value>
  </Setter>
</Style>

<!-- Inside a filled primary button the accent ring vanishes (1.00:1). -->
<Style x:Key="Broadsheet.FocusVisual.OnAccent" TargetType="{x:Type Control}">
  <Setter Property="Template">
    <Setter.Value>
      <ControlTemplate>
        <Rectangle Margin="-3" StrokeThickness="2" RadiusX="2" RadiusY="2"
                   Stroke="{DynamicResource Broadsheet.Brush.Focus.OnAccent}"
                   SnapsToDevicePixels="True" />
      </ControlTemplate>
    </Setter.Value>
  </Setter>
</Style>

<!-- WCAG 2.2 SC 2.5.8: 24x24 minimum target, without growing the 14px visual. -->
<Style x:Key="Broadsheet.TouchTarget.Small" TargetType="{x:Type Control}">
  <Setter Property="MinWidth"  Value="24" />
  <Setter Property="MinHeight" Value="24" />
  <Setter Property="Background" Value="Transparent" />
  <Setter Property="HorizontalContentAlignment" Value="Center" />
  <Setter Property="VerticalContentAlignment"   Value="Center" />
</Style>
```
Plus: every button/link/toggle/input template carries `ContentPresenter RecognizesAccessKey="True"`, and no template sets `FocusVisualStyle="{x:Null}"` without substituting an in-template `IsKeyboardFocused` trigger.

**Row selection + focus treatment → T-007.** The earlier draft shipped a `ListViewItem` template around a `GridViewRowPresenter` bound to `GridView.ColumnCollection`. **T-007 builds the results list with a plain `ItemTemplate` and no `GridView`, so that template would render empty rows** — the panel is right and it is withdrawn. What this task requires instead is container-shape-agnostic:

- T-007 **declares its item-container type** (`ListBoxItem` / `ListViewItem` / `TreeViewItem`) and whether a `GridView` is in play, as part of its own interface. This task's acceptance references that declaration rather than presupposing it.
- Whatever the container, its template carries `FocusVisualStyle="{x:Null}"` **and** these two triggers, with the presenter appropriate to the shape T-007 chose (`ContentPresenter` for the plain-template case below; `GridViewRowPresenter` only if T-007 actually adopts a `GridView`):

```xml
<ControlTemplate TargetType="{x:Type ListBoxItem}">   <!-- container type per T-007's declaration -->
  <Grid>
    <Grid.ColumnDefinitions>
      <ColumnDefinition Width="3" />
      <ColumnDefinition Width="*" />
    </Grid.ColumnDefinitions>
    <Rectangle x:Name="EdgeBar" Grid.Column="0" Fill="Transparent" />
    <Border x:Name="RowFill" Grid.Column="1" Background="Transparent">
      <ContentPresenter />
    </Border>
  </Grid>
  <ControlTemplate.Triggers>
    <Trigger Property="IsSelected" Value="True">
      <Setter TargetName="EdgeBar" Property="Fill"       Value="{DynamicResource Broadsheet.Brush.Accent.Strong}" />
      <Setter TargetName="RowFill" Property="Background" Value="{DynamicResource Broadsheet.Brush.Accent.Tint}" />
    </Trigger>
    <Trigger Property="IsKeyboardFocused" Value="True">
      <Setter TargetName="RowFill" Property="BorderBrush"     Value="{DynamicResource Broadsheet.Brush.Focus}" />
      <Setter TargetName="RowFill" Property="BorderThickness" Value="2" />
    </Trigger>
  </ControlTemplate.Triggers>
</ControlTemplate>
```

The 3px edge bar is the SC 1.4.1 / 1.4.11 fix from Fork 1b — selection must not be conveyed by the `accent-100` tint alone (1.03:1).

**Shell keyboard wiring → T-004.** `ShellCommands` (a `static class` of `RoutedUICommand`) and the `F6` / `Shift+F6` / `F1` handlers live with the window shell, under `Views/`, which `coverlet.runsettings` excludes — correct, because a `RoutedUICommand` field initialiser and a focus-moving handler are unreachable-by-unit-test plumbing.

```csharp
public static class ShellCommands
{
    public static readonly RoutedUICommand NextRegion     = new("Next region",     nameof(NextRegion),     typeof(ShellCommands), new InputGestureCollection { new KeyGesture(Key.F6) });
    public static readonly RoutedUICommand PreviousRegion = new("Previous region", nameof(PreviousRegion), typeof(ShellCommands), new InputGestureCollection { new KeyGesture(Key.F6, ModifierKeys.Shift) });
    public static readonly RoutedUICommand ContextHelp    = new("Help for this control", nameof(ContextHelp), typeof(ShellCommands), new InputGestureCollection { new KeyGesture(Key.F1) });
    public static readonly RoutedUICommand ClosePreview   = new("Close preview",   nameof(ClosePreview),   typeof(ShellCommands));
}
```
The handler walks an ordered list of the eight region roots, skipping any whose subtree contains no enabled focusable (`Preview` collapsed, `Status bar` when undo is disabled), and no-ops while a modal is up.

Also on T-004: `Scan` is a **sibling** of the `TabControl`, not a child of its `TabPanel` — a `Button` inside `TabPanel` becomes an arrow-key stop in the tab ring. `KeyboardNavigation.ControlTabNavigation="Cycle"` on the `TabControl`. Each `TabItem` gets an explicit `AutomationProperties.Name` (`Duplicates` / `Folders` / `History`). Window controls get `Name` (`Minimise` / `Maximise` / `Close`) and `Broadsheet.TouchTarget.Small`. The profile switcher gets `AutomationProperties.Name="Active profile"` — today's `ProfileCombo` at `MainWindow.xaml:91` has only `ToolTip="Switch active profile"`, and a `ToolTip` is **not** an accessible name in UIA; it maps to `HelpText`.

**Live-region wiring → T-009.** In the shell code-behind (`[ExcludeFromCodeCoverage]`, correctly so — it needs a live visual tree):
```csharp
if (e.PropertyName == nameof(MainViewModel.StatusMessage)
    && AutomationPeer.ListenerExists(AutomationEvents.LiveRegionChanged))
{
    var peer = UIElementAutomationPeer.FromElement(StatusText)
               ?? UIElementAutomationPeer.CreatePeerForElement(StatusText);
    peer?.RaiseAutomationEvent(AutomationEvents.LiveRegionChanged);
}
```
`AutomationProperties.LiveSetting="Polite"` alone announces nothing in WPF — the event must be raised. `ListenerExists` avoids building peers when no assistive tech is attached. `ResourceMemory` / `ResourceCpu` / `ResourceThreads` carry `LiveSetting="Off"` explicitly, for the 2-second-timer reason in `## Design` §4. Also on T-009: the surviving undo control's `Name` from `AccessibleNames.ForUndo(...)`, and neither `Move to…` nor `Recycle N files` is `IsDefault` — a destructive action must not fire on a stray `Enter`.

## Edge cases

**A four-stop ring is a trap with four doors.** `TabNavigation="Cycle"` means Tab can never leave a region. With stops only on the four tool-windows, the title bar, the tab strip's `Scan`, the action bar and the status-bar undo have **no keyboard route at all** — and the acceptance bar "every interactive control is reachable by keyboard alone" would be unsatisfiable while every gate stayed green. Hence eight stops covering every region of the frame; cases 1–9.

**A region can become empty at runtime.** Preview collapses; the status bar's only focusable is the undo button, which is disabled whenever `ActionHistory.Count == 0` (`MainViewModel.cs:665`). `F6` must test for an *enabled* focusable in the subtree and skip, or focus lands nowhere and the ring appears broken. Cases 4 and 5.

**Container-shape mismatch.** The first draft's row style wrapped a `GridViewRowPresenter` bound to `GridView.ColumnCollection`; T-007 builds the list with a plain `ItemTemplate` and no `GridView`, so it would have rendered **empty rows** — a template that compiles, runs, and shows nothing. The row treatment is now a contract written against T-007's declared container type, with `ContentPresenter` as the default shape. Case 77.

**Adorner clipping on rows.** `FocusVisualStyle` renders into the adorner layer, which a virtualising `ScrollViewer` clips. A focused row at the viewport edge would lose its ring entirely. Hence the in-template `IsKeyboardFocused` trigger rather than the shared focus visual — case 15.

**`Ctrl+Tab` collision.** `TabControl` claims `Ctrl+Tab` natively. Had regions been bound to it (the obvious first instinct), editor-tab switching would silently break. `F6` for regions, `Ctrl+Tab` for tabs — case 11 pins the separation.

**`RecognizesAccessKey` defaults to `False` in a hand-written template.** T-003 replaces every button template in the app. Every access key dies silently — no underline, no activation, no warning. Lint rule 5 (case 35) is the only thing that catches it.

**Shared `GroupName` across an `ItemsControl`.** `RadioButton`s with a literal `GroupName` inside a repeated template join one global group: choosing a keeper in group A clears group B. Bind `GroupName` to a per-group key — case 76.

**The 2-second resource timer.** SPEC-006 rule 19: a `DispatcherTimer` at 2 s that "is never stopped or disposed." A live region spanning the whole status bar speaks RAM/CPU/threads every two seconds for the process lifetime — strictly worse than the silent baseline. Case 31 pins the exclusion with a 60-second idle observation.

**`LiveSetting` alone is inert in WPF.** Unlike ARIA, setting the property announces nothing; `RaiseAutomationEvent(AutomationEvents.LiveRegionChanged)` must fire. Conversely, raising it unguarded builds automation peers for every status change even with no assistive tech attached — hence `ListenerExists` (case 33).

**`ToolTip` is not an accessible name.** UIA maps `ToolTip` to `HelpText`. `ProfileCombo` (`MainWindow.xaml:91`) has `ToolTip="Switch active profile"` and reads as an unnamed combo box today. Case 68 pins that a tooltip does not satisfy the lint.

**Emoji in a header.** The History `TabItem` header is a `TextBlock` reading `🕘 History`; NVDA speaks the codepoint name. Case 66.

**1px `GridSplitter`.** A 1px control is a 1px mouse target and a 1px ring. Width 9 with `Margin="-4,0,-4,0"` inside the 1px column works because `Grid` does not clip children and hit-testing follows render bounds — but only while nothing upstream sets `ClipToBounds="True"`. If T-005 clips the body grid, the hit area silently collapses back to 1px with no visual change; that is why "no `ClipToBounds` on the body-grid ancestry" is an explicit T-005 acceptance item.

**`KeyboardIncrement` default is 1.0 DIP.** Resizing a 260px panel by 100px would take 100 keypresses. Case 17 requires ≥ 8 DIP per press.

**Panel collapsed to zero by keyboard.** Without `MinWidth`, arrow-key resize can drive a panel to zero while focus is inside it — focus becomes invisible and unrecoverable except by `F6`. Cases 18 and 20.

**`Esc` during a splitter drag.** `GridSplitter` cancels natively, but only while the drag is live; after commit, `Esc` must not silently revert. Case 19.

**`AllowsTransparency` popups do not take focus.** SPEC-010 rule 2 records `AllowsTransparency="True"`. Such a `Popup` is invisible to the keyboard unless focus is moved in explicitly and restored on close — otherwise `F1` opens a panel no keyboard user can read. Cases 70–71.

**`StaysOpen="False"` plus focus-in.** SPEC-010 rule 2 and its *"Two `?` buttons clicked in turn"* edge case: moving focus into the popup can itself register as the outside click that dismisses it. The focus move must happen after the popup opens, and the dismissal handler must not fire on its own focus-in.

**Culture-sensitive formatting.** `ToString` on sizes and times under `tr-TR` or `de-DE` changes separators and casing. Every `AccessibleNames` method takes an `IFormatProvider`; case 29 runs a culture theory.

**`ActionHistoryKind` ordinals are frozen.** SPEC-004 rule 26: the enum serialises as integers into `settings.json`. `ForUndo` must switch on all four *and* carry a default arm for a value read back from a newer settings file — case 24, also a required branch for the 100% bar.

**Exactly-at-threshold ratios.** 4.50 and 3.00 must be inclusive; the AA text bar is `>= 4.5`, not `> 4.5`. Cases 51 and 54 pin both boundaries, and `MeetsAaText`'s large-text branch needs both arms (52, 53) for branch coverage.

**Alpha tokens.** `--color-divider` is `color-mix(in srgb, #201e1d 16%, transparent)` and lands as `#29201E1D`. Computing its ratio without compositing over the actual ground yields a meaningless number — cases 43, 48–50.

**Palette-test brittleness.** If a token is later expressed as `<SolidColorBrush Color="{StaticResource SomeColor}"/>`, the XML parse silently finds no hex. The test must fail loudly on an unresolvable key (case 59) rather than skip the pair — a skipped pair is a hole in the gate that looks like a pass.

**Value pinning cuts both ways.** Pinning expected hexes stops T-001 drifting, but it also means a *deliberate* palette change fails CI until the audit entry moves with it. That is the intent — the failure message says which role changed and what its new ratio is, so the fix is one line plus a re-measure, not an investigation.

**The uncommitted working tree.** Eleven modified test files (+1,690 lines) plus untracked `FormattedTextBehaviorTests.cs` and `tests/.../ViewModels/` sit in the tree from an interrupted coverage run. `PercentToWidthConverterTests.cs` is among them and is in the same folder this task adds tests to. Land or revert that batch **before** starting, or `Check-Coverage.ps1` reports a baseline that has nothing to do with this task's changes.

**Existing baseline failures this task does not silently inherit.** `#888888` (25 uses, 3.54:1), `#999999` (14 uses, 2.85:1), `#AAAAAA` (7 uses, 2.32:1), `#E65100` (3.79:1), `#558B2F` (3.55:1) already fail AA today. They disappear with the monolith, but if any survive into a token they must be recorded as a known failure in SPEC-011 rather than pass unexamined because "it was like that before."

## Risks

**The audit finding invalidates part of the design, and only the user can resolve it.** Fork 1 is not a preference question: the artboard's caption and link colours are measurably worse than the app being replaced (3.55 vs 5.27; 3.37 vs 5.75). If the user picks canvas-exact, this task ships a documented regression. *Mitigation:* Fork 1 is surfaced with numbers and in-ramp replacements **before any token value is frozen** (that is what Phase 1 is for); whichever branch is chosen `PaletteContrastTests` pins both the ratio and the hex, and options B/C carry a CHANGELOG obligation so a knowingly-shipped regression is visible to users, not buried in a spec appendix.

**The handback can be dropped.** The task's cost used to sit inside seven other tasks as a retrofit; it now sits there as *contracts*, which is better but not free — a contract nobody adds to their checklist is a contract that silently evaporates, and the gates would still be green. *Mitigation:* acceptance item 79 makes the handback itself the deliverable — every *Provided* row must appear in its owning task's acceptance before that task starts, and a declined row must be recorded in SPEC-011 § Not implemented with a reason.

**Phase 1 gates T-001, so a slow fork answer stalls the design system.** T-001 is the first task of the epic and cannot freeze values until Fork 1 is decided. *Mitigation:* Phase 1 is small (an audit already performed and tabulated here plus a role list) and has zero code dependencies, so it can be answered in one sitting; if the answer slips, T-001 can build the dictionary *structure* with placeholder values and land the values in a second, mechanical commit — the ordering that costs least.

**Nothing here proves focus is actually visible.** Three mechanical gates cover contrast maths, name strings, palette conformance and attribute presence. None proves the ring renders, that tab order feels right, or that NVDA says something useful. Cases 1–20, 30–36 and 70–78 are manual. A future edit to a `ControlTemplate` can silently break focus visibility with every gate green. *Mitigation:* stated plainly in SPEC-011 § Not implemented; the manual run is dated and sha-stamped so staleness is visible. Fork 2 option B closes this at the cost of a new test project and an edit to `coverlet.runsettings`, the file that declares itself the single source of coverage scope.

**A new measured type is a new 100% obligation, permanently.** `ContrastRatio` and `AccessibleNames` sit under `Helpers/`, which `coverlet.runsettings` includes. Every future branch added to either must be covered or CI goes red — including the `ActionHistoryKind` default arm and both sides of the sRGB knee. *Mitigation:* both are pure static string/number functions with no I/O and no WPF runtime dependency, the cheapest possible thing to hold at 100%. The genuinely untestable parts (peer creation, focus movement, popup focus restore) live under `Views/`, which is excluded — an honest split, not a coverage dodge.

**`ExcludeFromCodeCoverage` is an easy escape hatch that would hollow this out.** Adding the attribute to `ContrastRatio` would make the palette gate vanish while the build stays green. *Mitigation:* SPEC-011 records that neither type carries it and why; review treats adding it as a spec change.

**Lint rule 4 will fight the other tasks.** "No literal hex under `Views/`" is strict, and a single expedient `Foreground="#666666"` during T-007 fails CI for everyone on `main`. Given branch policy is main-only with concurrent sessions, that blocks other people's work. *Mitigation:* the lint lands **after** T-009 merges, warn-only for exactly one commit, then flips to error — an explicit acceptance item, not an intention.

**Value pinning makes the palette test a two-file edit.** Changing a token now requires touching T-001's dictionary and this task's assertion table together. *Mitigation:* that is the point — it is precisely what stops T-001 and T-011 disagreeing — and the failure message names the role, the old and new hex and the resulting ratio, so the second edit is mechanical.

**Access keys can collide invisibly.** `Alt+R` for *Recycle* and *+ Rule* both plausibly live on screen at once; WPF resolves a collision by cycling rather than erroring. *Mitigation:* case 36; the allocation is a table in SPEC-011 so the next person adding a button checks it.

**`AutomationProperties.HeadingLevel` support varies by assistive tech.** It is a real WPF property since .NET Core 3.0, but NVDA's heading-list behaviour for WPF UIA is not guaranteed identical to Narrator's. *Mitigation:* headings are additive — every region also has a `Name`, so region identity survives where heading navigation is unsupported.

**The negative-margin splitter is brittle.** It works because `Grid` does not clip, a default anyone can flip. *Mitigation:* an explicit T-005 acceptance item plus a comment in the XAML naming the dependency; if T-005 needs `ClipToBounds`, the splitter moves to a dedicated non-clipped host.

**Palette-test false confidence.** The test parses XML, not the loaded `ResourceDictionary`. A merge-order bug in `App.xaml` could mean the audited dictionary is not the one that renders. *Mitigation:* lint rule 4 guarantees no colour bypasses the dictionary; SPEC-011 records the limitation explicitly.

**Scope creep toward turn 4.** "Fix the contrast" is one short step from "introduce a semantic colour system", exactly the mis-targeting the brief rejects. *Mitigation:* remediation is confined to re-pointing existing text roles at existing ramp steps — no new colour, no new meaning, no new token concept.

- **(A) AA-corrected ramp shift — RECOMMENDED.** Ship the table above. Cost: captions and links read one ramp-step darker than the artboard pixels. Removes every AA text failure and both baseline regressions.
- **(B) Canvas-exact.** Ship 3a's values verbatim and record the eight failures. **If B is chosen, the two measured regressions are a user-facing change and MUST be entered in `CHANGELOG.md` Unreleased naming both pairs and both ratios — not only in SPEC-011 § Not implemented** (acceptance item, added on the panel's finding). Whichever of A/B/C ships, the test encodes it.

**FORK 1b, inseparable from the above — selection cannot be made accessible by tint at any value.** 3a marks the selected Scope row with `accent-100 #e9f8ff`, which is **1.03:1** against `bg`. No step in the accent ramp reaches the 3:1 SC 1.4.11 bar for a state indicator (`accent-200` 1.09, `accent-300` 1.30, `accent-400` 1.75 — and by `accent-400` the design is unrecognisable). **FORK 2 — how accessibility is verified, given there are no UI tests and 100% coverage is enforced on non-excluded code.**
- **(A) RECOMMENDED — three layers, no new package.** (1) Pure logic (`ContrastRatio`, `AccessibleNames`) under `Helpers/`, measured, 100% unit-tested.
