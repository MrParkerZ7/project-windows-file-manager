## Concept

3a puts every persistent readout in one of two fixed strips and nowhere else: a **40px action bar** at the foot of the results editor that states the consequence of the current marked set, and a **26px status bar** across the whole window bottom that states the app's condition. The task is that consolidation, and the consolidation is what makes the undo collapse possible.

Today undo is a `↶` glyph stamped next to every destructive button — seven of them (`MainWindow.xaml:1518, 1534, 1787, 2226, 2271, 2405, 2541`). That pattern exists because there was no place that always exists to put it. Once a status bar spans the window, there is: `UndoLastActionCommand` pops `ActionHistory[0]` regardless of which tab raised it, so one affordance in one always-visible strip is strictly more correct than seven scattered ones, four of which sit on a tab (Folders) whose actions push the *same* stack.

The same "one place that always exists" argument settles `ProfileOperationStatus` (D3): it is the last readout left homeless by the profile-bar deletion, and the status bar is the only strip that outlives the popup that raises it.

Two verified defects fall out of the move and must be absorbed here, not deferred:

1. **SPEC-004:69 says the undo CanExecute is `always`.** `MainViewModel.cs:665` gates on `ActionHistory.Count > 0`, and `docs/modules/ui.md:203` already records the correct predicate. The spec is the only lagging artifact. Moving the button is the commit that touches this row, so it is the commit that fixes it.
2. **The marked-set readout goes stale on a direct tick.** SPEC-004 rule 9 documents it plainly: `RefreshSelectedFileCount()` runs after every *command* that mutates selection, and "ticking the mark control directly does not call it — the count refreshes on the next command." Verified in code: nothing subscribes to `ScannedFile.PropertyChanged` (the only `PropertyChanged +=` sites in `MainViewModel.cs` are `ToggleItem` and `FolderSearchResult`). Today that staleness hides behind a 10px `"{0} files selected"` label. In 3a it becomes the headline number directly above a button labelled "Recycle 4 files" — a stale count on a destructive verb is not acceptable, so it gets fixed.

Two constraints shape the implementation, and both are structural rather than stylistic:

**Coverage.** There are no UI tests and 100% line/branch/method coverage is enforced on everything not `[ExcludeFromCodeCoverage]`. So every string-shaping rule this task introduces — the pluralisation, the size formatting, the resource readouts, the undo caption — is pushed *down* into pure Core types that carry no WPF reference and are covered by new xUnit tests. What is left in XAML and in the `[ExcludeFromCodeCoverage]` `MainViewModel` is wiring only: bindings, styles, and one dialog chain.

**The theme seam.** 4a is out of scope as *content* — no theme switch, no semantic colour system — but the frame T-001 builds is explicitly designed so a later palette swap repaints everything. That means **every brush reference in this task's two views is `DynamicResource`**, not `StaticResource`: `StaticResource` bakes the resolved brush into BAML at load, so a 4a palette swap would repaint the whole window *except* the status bar and action bar. Styles, converters and sizes stay `StaticResource` — they are not swapped. Building the seam is not the same as walking through it.

This task is **L**, not M: two new views, two new measured Core types with roughly 26 unit cases, a new property on a serialized model, five `MainViewModel` edits plus three raise-sites, nine deletion sites across four screens including four `Grid` restructures, retirement of T-001's two legacy shim dictionaries, and edits to four specs in the same commit.

## Design

**Two new views, both consuming T-001 tokens and T-003 styles, both dumb.**

```
AppShellView (T-004)                     ← root DockPanel
├─ TitleBar 34px            (T-004)
├─ TabStrip 38px            (T-004)
├─ StatusBarView 26px       (T-009)   DockPanel.Dock="Bottom"   ← full width, one instance
└─ screen host (Duplicates | Folders | History)
   └─ DuplicatesScreenView (T-005)   260 | 1 | * | 1 | 360
      └─ centre column Grid
         ├─ header 30px           (T-007)
         ├─ toolbar 36px          (T-007)
         ├─ column header 26px    (T-007)
         ├─ rows          *       (T-007)
         └─ MarkedActionBarView 40px  (T-009)   ← centre column only
```

The status bar is docked at the **shell** level, so it serves all three screens — which is what makes one undo affordance sufficient for the four Folders-tab buttons being deleted, and what makes it the right echo site for `ProfileOperationStatus` (D3). The action bar is scoped to the **Duplicates centre column**, because it describes the marked set of duplicate copies and nothing else; the Folders and History screens do not get one.

**Status bar anatomy (26px), left → right, per the artboard:**

`Ready` · `↶ Undo` `Recycled 4 files, 10:12` · ——— spacer ——— · `RAM 186 MB` · `CPU 0.4%` · `31 threads`

Left cluster is `DockPanel.Dock="Left"`, resource cluster is `DockPanel.Dock="Right"` so it never yields under pressure; the status caption takes the residual and trims. Gap 18px, `FontSize` 12, foreground `Broadsheet.Brush.Neutral600`, background `Broadsheet.Brush.Surface`, top hairline `Broadsheet.Brush.Divider`.

The status caption is the `StatusMessage` binding — **the single slot**. Scan/recycle/move messages land there as they do today, and under D3(a) profile-operation messages land there too. There is no fourth element.

**Action bar anatomy (40px):**

`4 marked` `27.5 MB · will be recycled` ——— spacer ——— `[ Move to… ]` `[ Recycle 4 files ]`

Background `Broadsheet.Brush.Neutral100`, top hairline `Broadsheet.Brush.Divider`, 12px horizontal padding, buttons 28px tall. `4 marked` is SemiBold body text; `27.5 MB · ` is `Broadsheet.Brush.Neutral600`; `will be recycled` is `Broadsheet.Brush.Accent2` — that one colour comes straight off 3a's own markup (`color:var(--color-accent-2)`), not from a semantic system. See Out of scope.

**Resource lookup discipline — the 4a seam:**

| Reference kind | Lookup | Why |
|---|---|---|
| Every `Brush.*` token | **`DynamicResource`** | a 4a palette swap must repaint these two views with everything else; `StaticResource` freezes them into BAML at load and creates exactly the seam T-001 designs against and T-012 records |
| Every `Style.*` key | `StaticResource` | styles are not swapped; static resolution fails loudly on a typo |
| Converters (`BoolToVisibility`, `InverseBoolToVisibility`) | `StaticResource` | instance identity, never swapped |
| Sizes / thicknesses / doubles | `StaticResource` | metrics are not themed in 3a or 4a |

The trade this makes: `StaticResource` throws `XamlParseException` at window load on a mistyped key, whereas `DynamicResource` resolves to nothing and renders an unstyled (usually transparent) control with no error. The safety net therefore moves off the loader and onto two mechanical checks — the brush-key cross-check in Acceptance and smoke S1 — which is a deliberate cost of building the seam, not an oversight.

**Where the display logic lives — the coverage-driven split:**

| Layer | Holds | Covered? |

## Detail

### 1. `src/WindowsFileManager.Core/Models/MarkedSelection.cs` — NEW, under the coverage gate

File-scoped namespace `WindowsFileManager.Core.Models;` (match `ScannedFile.cs`). Sealed immutable class — **not** a struct, so WPF binds `Marked.CountLabel` without boxing on every refresh.

```
public sealed class MarkedSelection
    public static MarkedSelection Empty { get; }            // Count 0, Bytes 0
    public static MarkedSelection From(IEnumerable<ScannedFile> files)   // one pass; null → Empty
    public int  Count { get; }
    public long Bytes { get; }
    public bool IsEmpty          => Count == 0;
    public string CountLabel     => IsEmpty ? "Nothing marked" : $"{Count} marked";
    public string FormattedBytes => ScannedFile.FormatFileSize(Bytes);   // reuse the app's one formatter
    public string RecycleLabel   => Count switch { 0 => "Recycle", 1 => "Recycle 1 file", _ => $"Recycle {Count} files" };
```

`From` counts and sums in a single `foreach` over files where `IsFileSelected` is true — do not use two LINQ passes; `DuplicateGroups.SelectMany` can be tens of thousands of items and this runs on every mark toggle. No WPF, no `System.Windows` using — Core stays presentation-free per ADR-001.

Build-gate specifics that will bite: StyleCop `SA1600` requires a `/// <summary>` on the type and on **every** public member, and `TreatWarningsAsErrors` + `CodeAnalysisTreatWarningsAsErrors` are both on (`Directory.Build.props`). `$"{Count} marked"` is fine, but any numeric `.ToString()` you add needs `CultureInfo.InvariantCulture` or CA1305 fails the build.

### 2. `src/WindowsFileManager.Core/Models/ResourceReadout.cs` — NEW, under the coverage gate

Pure static formatters lifted out of `MainViewModel.UpdateResourceInfo()` (`MainViewModel.cs:4907-4939`), reproducing the existing numeric rules exactly and changing only the label shape to 3a's:

```
public static class ResourceReadout
    public static string FormatMemory(long workingSetBytes)   // "RAM 186 MB" | "RAM 1.4 GB"
    public static string FormatCpu(double percent)            // "CPU 0.4%"
    public static string FormatThreads(int count)             // "31 threads" | "1 thread"
```

- `FormatMemory`: `var mb = workingSetBytes / (1024.0 * 1024.0);` → `mb < 1024` ? `$"RAM {mb.ToString("F0", CultureInfo.InvariantCulture)} MB"` : `$"RAM {(mb / 1024.0).ToString("F1", CultureInfo.InvariantCulture)} GB"`. The `< 1024` threshold and the `F0`/`F1` precisions are copied verbatim from the current code so SPEC-006 rule 20's *numbers* do not move — only the `"RAM: "` → `"RAM "` label.
- `FormatCpu`: `$"CPU {percent.ToString("F1", CultureInfo.InvariantCulture)}%"`. The core-normalised percentage calculation stays in the VM (it needs `_lastCpuTime`/`_lastCheckTime` state); only formatting moves.
- `FormatThreads`: `count == 1 ? "1 thread" : $"{count.ToString(CultureInfo.InvariantCulture)} threads"` — 3a writes the count first and the noun after, unlike today's `"Threads: 31"`.

`MainViewModel.UpdateResourceInfo()` then reads:
```
ResourceMemory  = ResourceReadout.FormatMemory(_currentProcess.WorkingSet64);
ResourceCpu     = ResourceReadout.FormatCpu(cpuPercent);          // inside the existing elapsed > 0 guard
ResourceThreads = ResourceReadout.FormatThreads(_currentProcess.Threads.Count);
```
The `try { … } catch { }` wrapper, the 2s `DispatcherTimer`, the `elapsed > 0` guard, and the unconditional `_lastCpuTime`/`_lastCheckTime` advance are all untouched (SPEC-006 rules 19 and 21 do not change).

### 3. `ActionHistoryEntry.UndoCaption` — NEW property on an existing Core model

In `src/WindowsFileManager.Core/Models/ActionHistoryEntry.cs`, beside the existing computed `ItemCount`:

```
[System.Text.Json.Serialization.JsonIgnore]
public string UndoCaption => $"{Summary}, {Timestamp.ToString("HH:mm", CultureInfo.InvariantCulture)}";
```

`[JsonIgnore]` is mandatory, not stylistic. This type is serialized whole into `%APPDATA%` `settings.json` (`AppSettings.ActionHistory`, SPEC-009 rule 7, ADR-007 freezes the `ActionHistoryKind` ordinals). `ItemCount` is already an un-ignored computed property and already writes a redundant field — do not add a second one. `System.Text.Json` is in the net8.0 shared framework, so no package reference is needed; add `using System.Text.Json.Serialization;` and `using System.Globalization;`.

`InvariantCulture` is load-bearing twice over: `HH` is 24-hour everywhere, but the `":"` separator resolves through `CurrentCulture.DateTimeFormat.TimeSeparator` and reads as `.` in several locales — and CA1305 fails the build without an explicit provider anyway.

Renders `"Recycled 4 files, 10:12"` for a real `Summary`. The artboard's `"recycle of 4 files"` is illustrative prose; the app's real `Summary` vocabulary (`"Recycled N files"`, `"Moved N files to X"`, `"Recycled <filename>"`) is used verbatim. Do **not** invent a new summary vocabulary here — that would touch every `PushHistory` call site for no gain.

### 4. `MainViewModel` changes — `[ExcludeFromCodeCoverage]`, wiring only

**a. Marked-set state.** Add `private MarkedSelection _marked = MarkedSelection.Empty;` and a `public MarkedSelection Marked { get; private set; }` raising `PropertyChanged`. Extend `RefreshSelectedFileCount()` (`MainViewModel.cs:4870-4876`) to set both in one traversal:

```

Marked = marked;
SelectedFileCount = marked.Count;
```

Keep `SelectedFileCount` as the stored property it is today. Every `CanExecute` predicate (`MainViewModel.cs:687-688`), `HasSelectedFiles`, and SPEC-004 rules 7 and 9 keep working untouched. This is deliberate blast-radius control — do not rewrite `SelectedFileCount` into a `Marked.Count` passthrough.

**b. Live recount on a direct mark toggle — the rule-9 fix.** Add `public ICommand RefreshMarkedCommand { get; }`, constructed beside the other selection commands (`MainViewModel.cs:640-641` block) as `new RelayCommand(_ => RefreshSelectedFileCount())`.

**The consumer is T-007's Keep-column control, which is a chromeless `ToggleButton`, not a `CheckBox`.** That does not change the mechanism — `ToggleButton` derives from `ButtonBase`, so it carries the same `Command` DP — but it does change the markup T-007 must write, and the ordering guarantee is worth stating because the fix depends on it: `ToggleButton.OnClick()` calls `OnToggle()` *first* (which flips `IsChecked` and, through the two-way binding, writes `IsFileSelected`) and only then calls `base.OnClick()`, which raises `Click` and executes `Command`. So the command always observes the post-toggle value. This holds for mouse click and for the `Space` keyboard activation alike.

```
<ToggleButton Style="{StaticResource Broadsheet.Style.ToggleButton.Keep}"
              IsChecked="{Binding IsFileSelected, Mode=TwoWay}"
              Command="{Binding DataContext.RefreshMarkedCommand,
                        RelativeSource={RelativeSource AncestorType=UserControl}}" />
```

(If T-007 inverts the Keep affordance at the binding — see Interfaces — the `Command` attribute is unaffected; it fires on toggle regardless of which direction the converter points.)

**Do not** subscribe to `ScannedFile.PropertyChanged` per file: `ScannedFile` raises only on `IsFileSelected` (`ScannedFile.cs:18-28`) but there can be tens of thousands of instances per scan, `DuplicateGroups` is rebuilt on every scan, and nothing detaches — that is a guaranteed leak. The `Command` binding costs one binding per *visible* row and is virtualised away for the rest.

**c. Undo surface.** Add `public bool HasUndoableAction => ActionHistory.Count > 0;` and `public string LastActionCaption => ActionHistory.Count > 0 ? ActionHistory[0].UndoCaption : string.Empty;`. Miss one and the status bar goes stale; those three lines are the complete set. Keep `UndoTooltip` — it becomes the status-bar button's `ToolTip`.

**d. `MoveToCommand`** (decision D1(a)). `new RelayCommand(_ => MoveTo(), _ => SelectedFileCount > 0)`, where `MoveTo()` calls the existing `BrowseMoveTarget()` (`MainViewModel.cs:4840-4846`) and, only when `MoveTargetPath` actually changed or is non-empty after the dialog, calls `MoveSelectedFiles()`. ## Edge cases

**`DynamicResource` fails silently where `StaticResource` failed loudly.** Switching every brush to `DynamicResource` (to keep the 4a palette swap whole) removes the load-time `XamlParseException` that used to catch a mistyped key. A wrong key now renders a transparent `Border` or an invisible `TextBlock` with no error, in a repo with no visual-regression harness. The replacement guard is the Acceptance key cross-check plus smoke S1 — treat a cross-check miss as build-blocking, not cosmetic. Styles stay `StaticResource` precisely so at least the style keys keep failing loudly.

**A static brush inside T-003's template defeats the seam just as thoroughly.** T-009's markup can be perfectly dynamic and the status bar still freeze, if `Broadsheet.Style.StatusBar`'s `ControlTemplate` resolves its `Background` statically. Named as a requirement on T-003 in Interfaces; verify by reading the style, not just this task's two files.

**Stale marked-set readout (the reason this task fixes rule 9).** Before this change, toggling a per-file mark left `SelectedFileCount` untouched until the next command. In 3a that number sits directly above `Recycle 4 files`, so a stale count is a stale destructive verb. Fixed by `RefreshMarkedCommand` on T-007's Keep `ToggleButton`. **The failure mode if T-007 forgets to wire it is silent** — the bar simply lags — which is why the wiring is an acceptance item in *T-007's* ticket, not only a risk in this one, and why smoke S11 exists.

**`ToggleButton` ordering is what makes the command see fresh state.** `ToggleButton.OnClick()` runs `OnToggle()` (flipping `IsChecked`, which writes `IsFileSelected` through the two-way binding) *before* `base.OnClick()` executes the `Command`. If T-007 ever hand-rolls the toggle — flipping the bound value in a `Click` handler after the fact, or on `PreviewMouseDown` — the recount reads the pre-toggle value and the bar is off by one. Keep the toggle in the control, not in a handler.

**Per-file `PropertyChanged` subscription is the wrong fix.** `ScannedFile` raises only on `IsFileSelected`, but a scan can produce tens of thousands of instances, `DuplicateGroups` is rebuilt on every scan, and nothing detaches handlers. Attaching per file leaks and slows every scan. The `Command` binding costs one binding per visible row and is virtualised away for the rest.

**Deleting a legacy shim is not a build error.** If `Themes/Legacy.Palette.xaml` is removed while another surface still resolves against it, every `DynamicResource` consumer renders transparent and the build stays green. That is exactly why Detail § 8 orders the grep before the delete and allows handing the deletion back.

**`UndoCaption` and `settings.json`.** `ActionHistoryEntry` is serialized whole into `%APPDATA%`. Adding a computed property without `[JsonIgnore]` writes a redundant string to every one of up to 30 entries on every save (SPEC-009 rule 8 saves on every mutation). `ItemCount` already does this — do not compound it.

**`HH:mm` is not culture-safe on its own.** The `HH` is 24-hour everywhere, but the `:` resolves through `CurrentCulture.DateTimeFormat.TimeSeparator` and renders as `.` in several locales. `CultureInfo.InvariantCulture` is required — and CA1305 with `CodeAnalysisTreatWarningsAsErrors` will fail the build without it, so this is enforced, not merely advised.

**The three `OnPropertyChanged(nameof(UndoTooltip))` sites are the complete set.** `MainViewModel.cs:4114` (`PushHistory`), `:4214` (`UndoEntry`), `:4221` (`ClearHistory`). `HasUndoableAction` and `LastActionCaption` must be raised at all three. Miss `:4221` and the status bar keeps advertising an undo for history the user just cleared — a genuinely dangerous stale affordance.

**The profile echo can bury a real status message — and that is the intended trade.** Under D3(a) a profile switch overwrites whatever the status caption held (e.g. a completed-scan summary). Acceptable because profile switching *is* the user's most recent action and because the durable copy lives in the popup footer; the reverse (a scan message burying the profile confirmation) is equally fine. What must not happen is the echo becoming sticky — nothing may re-assert `ProfileOperationStatus` into `StatusMessage` after the fact, or ordinary status messages start flickering back to a stale profile sentence.

**Undo after `MaxHistoryEntries = 30` rolls off.** Unchanged behaviour, newly visible: an old action becomes permanently un-undoable while its files sit in the Recycle Bin. The status bar only ever shows index 0, so it never advertises something that has rolled off. Worth a line in SPEC-004's edge-case table.

**Undo of a recycle after the bin was emptied.** `RestoreFromRecycleBin` finds no match and the status line reports `N not found in Recycle Bin (may have been emptied)` (SPEC-004 rule 24). The status bar is now the *only* place that message lands, which makes its `MaxWidth`/`TextTrimming` load-bearing rather than cosmetic.

**`↶` glyph availability.** U+21B6 renders in Segoe UI Symbol but not in every Source Serif fallback chain. `Broadsheet.Style.Button.Ghost` must keep a `FontFamily` fallback that resolves it, or the button shows a tofu box. Verify at S3 — the current buttons use the default WPF font stack, which resolves it today, so a font change in T-001/T-003 is the actual risk.

**Two hairlines could double up.** The action bar's top border sits inside the centre column; the status bar's top border spans the window. Where the centre column meets the status bar there must be exactly one 1px line, not two stacked — check at S1 with the window at 1600×900.

**`Marked` binds through a class, not a struct.** `{Binding Marked.CountLabel}` re-reads only when `Marked` itself raises `PropertyChanged`. Since `MarkedSelection` is immutable and replaced wholesale on every refresh, this is correct — but it means mutating a `MarkedSelection` in place would silently never update. It has no setters; keep it that way.

**`Run.Text` binding defaults to `TwoWay`.** Omitting `Mode=OneWay` on `<Run Text="{Binding Marked.FormattedBytes}"/>` throws at runtime against a read-only source property. Not caught at build.

**The Delete confirmation still shows only a count, not paths** (SPEC-004 rule 13). 3a's `4 marked · 27.5 MB` in the action bar is now the pre-commit disclosure. Do not "improve" the dialog here — that is a SPEC-004 behaviour change with no artboard mandate.

**Folders-tab undo reachability.** Deleting the four inline `↶`s leaves that screen with no local undo. Correct only because the status bar is docked at shell level, above the screen host. If T-004 lands it inside the Duplicates screen instead, the Folders tab silently loses undo entirely — S14 is the guard.

**"Ready" replaces the onboarding hint.** `_statusMessage`'s current default is `"Add folders and click Scan to find duplicate files."` Changing it to `"Ready"` matches 3a but drops a first-run hint. Hand it to T-006 for the Scope tool-window's empty state; note it in the commit so it is not simply lost.

**Do not sweep the dirty working tree.** 11 modified test files (+1,690 lines) and an untracked `tests/.../ViewModels/ExtensionFilterTests.cs` sit uncommitted from an interrupted coverage run. Commit T-009 with an explicit pathspec — `git commit -m "…" -- src/ docs/specs/ tests/WindowsFileManager.Tests/Models/MarkedSelectionTests.cs …` — never `git add -A`. ## Open decision

Three real forks. All have a recommended default so the engineer is never blocked; take the recommendation if the user does not answer.

**D1 — What does the single "Move to…" button actually do?**
3a's action bar has exactly two buttons: `Move to…` and `Recycle 4 files`. There is no path text box, no `...` browse button, and no chevron. Today (`MainWindow.xaml:1524-1532`) Move is a three-control cluster: a free-form `TextBox` bound to `MoveTargetPath` (`UpdateSourceTrigger=PropertyChanged`), a `...` browse button (`BrowseMoveTargetCommand`), and `📁 Move` (`MoveSelectedFilesCommand`). `MoveTargetPath` is one of the 22 persisted per-profile properties (SPEC-009 rule 6) and is pinned by `ProfileSettingsTests.Constructor_ShouldSetDefaults`. Collapsing three controls into one changes how a persisted setting is reached.
- **(a) Chain — RECOMMENDED.** `Move to…` runs a new `MoveToCommand`: open `Microsoft.Win32.OpenFolderDialog` seeded with the current `MoveTargetPath` (`InitialDirectory`) → on OK write `dialog.FolderName` into `MoveTargetPath` → fall straight into the existing `MoveSelectedFiles()` (its own confirm dialog already shows count + target, so the user still gets a gate). On Cancel: nothing happens, no history entry. `MoveTargetPath` stays a persisted property and stays reachable — it is the dialog seed and it appears in the confirm dialog. **SPEC-009 rules 6 and 11 unchanged.** Matches the artboard exactly; costs one extra click for the repeat-same-target case.
- **(b) Split button.** `Move to…` moves to the remembered `MoveTargetPath` directly; a ▾ chevron opens the picker. Best for repeat use, but 3a draws no chevron and it silently reuses a target the user cannot see — bad for a destructive-adjacent action.
- **(c) Keep the text box**, relocated into the Scope tool-window. Contradicts T-006's verified contents (Scope holds target folders / include-subfolders / skip-names / match-by only) and re-introduces the free-form path that SPEC-004 rule 15 already flags as unvalidated.

**D2 — Where does the busy/progress cluster live in a 26px status bar?**
The current global status bar (`MainWindow.xaml:118-196`) carries five busy elements the 3a artboard does not draw, because 3a draws the idle state only: the ●/⏳ indicator, the `BusyStatus` swap, a 160×8 `ProgressBar`, `BusyCountText`, and `BusyEta`. These are load-bearing — SPEC-004 rule 13 and SPEC-008 both route long recycle/move sweeps through `BeginBusy`/`EndBusy`, and without them a 40k-file sweep looks frozen. Dropping them is a functional regression and is not what "only the framing is IDE-standard" asks for.
- **(a) Inline swap — RECOMMENDED.** The left cluster is one `Grid` cell with two mutually exclusive children: idle (`Ready` + the `↶ Undo` affordance) and busy (⏳ + `BusyStatus` + the 8px `ProgressBar` + `BusyCountText` + `BusyEta`), toggled by `IsBusy` through the existing `BoolToVisibilityConverter` / `InverseBoolToVisibilityConverter`. Everything already fits: the bar is 8px inside a 26px row. Cost: the undo affordance is hidden while a sweep runs — acceptable, since undo during a sweep is not a supported operation anyway.
- **(b) Second row.** A 26px busy row slides in beneath the status bar while `IsBusy`. Keeps undo always visible; costs 26px of layout jump mid-operation and a second bottom hairline the artboard does not have.
- **(c) Push progress into the action bar** (centre column only). Wrong — folder-tab sweeps (SPEC-008) have no action bar to live in.

**D3 — Where does `ProfileOperationStatus` permanently live? (NEW — resolves the homeless property T-004 parked)**
`ProfileOperationStatus` (`MainViewModel.cs:1617`, written at six sites — `:2082, :2094, :2191, :2209, :2220, :2254`) renders today at `MainWindow.xaml:85` as the italic `#558B2F` caption in the docked profile bar. T-004 deletes that bar and parks the binding in the profile popup's footer, calling that placement temporary on the grounds that "its permanent home is T-009's status bar". 3a's status bar draws no such slot: `Ready` · `↶ Undo …` · —— · `RAM` · `CPU` · `threads`, full stop. Somebody has to settle it, and it is settled here.
- **(a) Popup footer is the permanent home; the status bar echoes transiently — RECOMMENDED.** The six write sites route through one new private `SetProfileStatus(string message)` helper in `MainViewModel` that sets `ProfileOperationStatus` **and** `StatusMessage`. The profile popup footer (T-004) keeps its own binding and is the *durable* readout — it is where the user is standing when they create/clone/rename/delete — and the status bar shows the same sentence transiently in its existing status-caption slot until the next status write overwrites it. No fourth element, no artboard deviation, no new property, and the confirmation survives the popup closing (`Switched to 'Photos cleanup'.` is exactly the kind of thing the user wants after the popup dismisses). **T-004 may drop the word "temporary" from its footer note.** Costs one SPEC-009 edit (see Acceptance).
- **(b) Popup only, no echo.** Zero VM change, zero spec change; T-004's footer simply becomes permanent. Rejected as the default because a profile switch then leaves no trace once the popup closes — a regression against today's always-visible bar caption.
- **(c) A fourth left-cluster element in the status bar.** Rejected: 26px at `MinWidth="1000"` is already tight enough that D2 had to make idle and busy mutually exclusive (see Risks); adding a fifth competing string guarantees a clipping bug, and the artboard does not draw it.
