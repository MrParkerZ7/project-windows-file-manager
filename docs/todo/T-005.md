## Concept

Turn 3's brief states the framing rule in one line: *"every panel has a 30px title bar; panels are separated by **1px splitters**; main tabs are underlined editor tabs; each panel gets one toolbar row for its controls; a single status bar at the bottom."* T-004 delivers the tab strip and status bar. **T-005 delivers the "panels separated by 1px splitters" half — the load-bearing skeleton of the Duplicates screen.**

Read literally off 3a's artboard markup, the body of the Duplicates screen is one CSS grid:

```
grid-template-columns: 260px 1px 1fr 1px 360px
```

and the right cell is itself:

```
grid-template-rows: 1fr 1px 1fr        (Preview over Rules)
```

That is three 1px seams. **T-005 owns the two vertical ones.** The third — the horizontal seam inside the 360px column — belongs to **T-008** along with the `RowDefinition`s it separates, because T-008 authors that column's contents and its collapse behaviour. Declaring those rows here as well is what the panel review caught: two tasks building the same row grid. T-005 hands the whole 360px cell to a single `RightToolWindowStack` control and does not look inside it.

The repo has **zero** `GridSplitter` elements today (`grep -c GridSplitter src/WindowsFileManager/Views/MainWindow.xaml` → 0), so both of T-005's are new.

What exists instead is a window-level `DockPanel` (`MainWindow.xaml:70`) wrapping a three-column `Grid` (`:198`, `* / Auto / Auto`) whose side columns are **fixed-width, visibility-toggled slabs** — Analytics `Width="320"` (`:1847`), Folder Action `Width="640"` (`:2009`), File Preview `Width="380"` (`:2575`) — all *outside* the `TabControl`, so every screen shares one set of side panels and none of them can be resized. 3a inverts that: **each screen owns its own columns**, and every seam is draggable.

The conceptual shift is therefore not "add two splitters". It is: *the side panels stop being window furniture and become per-screen tool-windows whose widths are the user's to set and the app's to remember.*

Remembering is what pulls SPEC-009 in — and it is where this task can do better than the code it replaces. SPEC-009 rule 12 records a known defect: window geometry is captured **only** in `Window.Closing`, so a force-kill loses it — exactly the failure ADR-006 was written to stop for everything else. Pane widths will **not** repeat that mistake: they persist at mutation time, on the splitter's `DragCompleted`, through the same `SaveSettings()` path as the other 27 triggers.

The second half of the concept is the responsive question the artboard cannot answer, because an artboard is exactly 1600×900 and a window is not. The design's five tracks are three fixed-ish and one elastic; the honest mapping is a **budget**: the centre editor has a legibility floor (its own column header is `28 + 1fr + 130 + 90 + 70 + 90` with five 10px gaps = 458px of fixed structure before the filename gets a pixel), and the two side panels may take only what is left above that floor. That budget is arithmetic, it is the only decision-making code this task adds, and it is the one piece that goes under the 100% coverage gate. The *vertical* budget inside the right stack is the same arithmetic living in the same class — but it is **called** by T-008, not by T-005 (Interfaces).

## Design

**Shape.** One new `UserControl` — `DuplicatesScreenView` — whose root is a five-column `Grid`. It hosts, but does not author, the panels: Scope (T-006), the results editor (T-007), the whole right stack (T-008 — one control, contents and internal seam included), and the bottom action bar (T-009, which lives *inside* the centre column, not across the window — the artboard puts the 40px action bar in the centre `<section>` and the 26px status bar outside the whole body grid).

```
ShellView (T-004)
└─ Grid rows: 34 title bar | 38 tab strip | * screen host | 26 status bar
   └─ screen host (row 2)
      └─ DuplicatesScreenView            ← T-005 owns this and only this
         └─ Grid  cols: [Scope px] [1] [* results] [1] [RightStack px]
            ├─ col 0  ScopePanel               (T-006 fills)
            ├─ col 1  GridSplitter             ← new, T-005
            ├─ col 2  Grid rows: 30 hdr | 36 toolbar | 26 col-hdr | * list | 40 action bar
            │         ├─ rows 0-3  ResultsEditorPanel   (T-007 fills)
            │         ├─ row  4    ActionBar            (T-009 fills)
            │         └─ row  3    AnalyticsOverlay [OVL] ← right-aligned, ZIndex 20, not resizable
            ├─ col 3  GridSplitter             ← new, T-005
            └─ col 4  RightToolWindowStack     ← T-008 owns it whole: its rows,
                                                 its horizontal splitter, and the
                                                 IsPreviewVisible collapse
```

**Two ownership boundaries the panel review forced, now written down:**

| Boundary | T-005 does | T-008 does |
|---|---|---|
| The 360px column | declares `RightStackColumn`, resolves + persists its **width**, drops one `RightToolWindowStack` into it | declares `PreviewRow` / `PreviewSplitRow` / `RulesRow`, the horizontal `GridSplitter`, and the `IsPreviewVisible` collapse |
| The preview ratio | ships the arithmetic (`ResolvePreviewRatio` / `CaptureRatio`) and the storage (`PreviewPaneRatio`, `MainViewModel.SetPreviewRatio`) | **calls** both from `RightToolWindowStack.xaml.cs` |

The ratio's math and storage stay here because `PaneLayout` and `AppSettings` are one coherent unit that should not be split across two tasks; the *use* of them moves to whoever owns the rows. That is the smallest cut that removes the double-declaration.

**Collapse semantics — T-005 adopts T-008's.** `IsPreviewVisible == false` collapses the Preview pane to a **30px header-only row** (splitter hidden, header retained), not to zero. T-005 previously specified `Height=0` with `MinHeight` zeroed; that is struck. The header-only form is correct for a reason beyond consistency: the Preview header carries the artboard's `Auto ✓` and `✕`, which is the *only* affordance that can re-open the pane. Collapsing to zero destroys the restore path. Since the rows now belong to T-008 this is T-008's code to write — T-005's obligation is to *not fight it*: `RightStackColumn` never collapses, its `MinWidth` stays `280` regardless of `IsPreviewVisible`, and `PaneLayout.HostMinHeight` is budgeted for the **open** state so a collapse never forces a re-layout of the columns.

**Three responsibilities, three homes.**

| Responsibility | Home | Under coverage? |
|---|---|---|
| The arithmetic — clamp, budget, ratio, overlay width | `Helpers/PaneLayout.cs`, pure `double` math, **no WPF types**, **not** `[ExcludeFromCodeCoverage]` | **Yes — 100% required** |
| The plumbing — read `ActualWidth`, assign `GridLength`, hook `DragCompleted` | `Views/Screens/DuplicatesScreenView.xaml.cs` | No (runsettings `Exclude=[WindowsFileManager]*Views*`) |
| The storage — three `double?` on `AppSettings`, two setters on the VM | `Core/Models/AppSettings.cs`, `ViewModels/MainViewModel.cs` | Auto-props (`SkipAutoProps=true`); the VM is already `[ExcludeFromCodeCoverage]` |

This split is deliberate: it is the only arrangement in which the *decisions* are testable without a UI-test harness (there is none) while the *WPF plumbing* stays in the one place `docs/modules/ui.md` § Rules #2 already sanctions — "things a binding cannot express: window geometry…". Pane geometry is the same class of thing.

**No new ResourceDictionary.** The earlier draft introduced `Themes/Broadsheet.Frame.xaml` carrying `Broadsheet.Style.PaneSplitter.*`. That is struck on two counts the panel raised: T-003's component library already ships the splitter styles, and the `Broadsheet.Style.*` prefix was a fourth naming convention alongside T-003's `Bs*Style` and T-004's `Style.*`. **T-005 authors no `<Style>`, no `ControlTemplate`, and no theme file** — it consumes T-003's keys by name. The 1px-paint / 7px-grab requirement becomes a *contract on T-003* (Interfaces), verified here rather than implemented here.

**Desired vs. actual.** The user's dragged width is their *intent* and is what gets persisted. What the `ColumnDefinition` actually receives is intent **resolved against the current host width**. Shrinking the window squeezes the panels; growing it back restores them, because the intent was never overwritten. That is the difference between a layout that degrades and one that just loses your settings.

**No converters, no bindings to `ColumnDefinition`.** Binding `ColumnDefinition.Width` relies on `DataContext` inheriting into `ColumnDefinitionCollection` — historically unreliable and a known WPF wart. The code-behind assigns `GridLength` directly. Net effect: **zero new converters**, zero new XAML resources, one new covered class.

```csharp
public static double ScopeMaxForHost(double hostWidth);
public static double RightStackMaxForHost(double hostWidth, double scopeWidth);
public static double ResolveScopeWidth(double hostWidth, double? persisted);
public static double ResolveRightStackWidth(double hostWidth, double scopeWidth, double? persisted);
public static double ResolvePreviewRatio(double? persisted);              // called by T-008
public static double CaptureRatio(double previewHeight, double rulesHeight); // called by T-008
public static double ResolveAnalyticsOverlayWidth(double resultsWidth);   // [OVL]
private static double Sanitize(double? value, double fallback);  // null / NaN / ±Inf / <= 0 → fallback
```

Bodies:

```csharp
ScopeMaxForHost(h)            = Max(ScopeMinWidth,      Min(ScopeMaxWidth,      h - 2*SplitterThickness - ResultsMinWidth - RightStackMinWidth));
RightStackMaxForHost(h, s)    = Max(RightStackMinWidth, Min(RightStackMaxWidth, h - 2*SplitterThickness - ResultsMinWidth - s));
ResolveScopeWidth(h, p)       = Math.Clamp(Sanitize(p, ScopeDefaultWidth),      ScopeMinWidth,      ScopeMaxForHost(h));
ResolveRightStackWidth(h,s,p) = Math.Clamp(Sanitize(p, RightStackDefaultWidth), RightStackMinWidth, RightStackMaxForHost(h, s));
ResolvePreviewRatio(p)        = Math.Clamp(Sanitize(p, PreviewDefaultRatio),    PreviewMinRatio,    PreviewMaxRatio);
CaptureRatio(pv, ru)          = double.IsFinite(pv + ru) && pv + ru > 0
                                  ? Math.Clamp(pv / (pv + ru), PreviewMinRatio, PreviewMaxRatio)
                                  : PreviewDefaultRatio;
ResolveAnalyticsOverlayWidth(rw)                                                        // [OVL]
                              = Math.Clamp(AnalyticsOverlayWidth, AnalyticsOverlayMinWidth,
                                           Max(AnalyticsOverlayMinWidth, Sanitize(rw, AnalyticsOverlayWidth) - 24));
```

The `Max(Min(…))` shape in the two `…MaxForHost` methods — and the inner `Max` in `ResolveAnalyticsOverlayWidth` — is what keeps `Math.Clamp`'s `min <= max` precondition true at **every** host width, including hosts narrower than `HostMinWidth`. Do not "simplify" it to a bare `Min` — `Math.Clamp` throws `ArgumentException` when `min > max`, and that is a startup crash, not a layout glitch.

**Fidelity check at the design size.** `h = 1600` → `ScopeMaxForHost = Min(480, 1600−2−640−280 = 678) = 480`, so scope resolves to its persisted/default `260`; `RightStackMaxForHost(1600, 260) = Min(560, 1600−2−640−260 = 698) = 560`, so the right stack resolves to `360`; the centre gets `1600 − 2 − 260 − 360 = 978`. The artboard's own centre track at 1600 is `1600 − 260 − 1 − 1 − 360 = 978`. Exact match.

### 2. Splitter styling — consumed from T-003, authored nowhere here

**Struck from this task:** the `Themes/Broadsheet.Frame.xaml` `ResourceDictionary` and the `Broadsheet.Style.PaneSplitter.Vertical` / `.Horizontal` styles it defined. T-003's component library already ships pane-splitter styles, and a second definition here would be both a duplicate and a fourth style-prefix convention (`Broadsheet.Style.*` against T-003's `Bs*Style` and T-004's `Style.*`).

T-005 consumes T-003's two keys by name under whatever prefix T-001 reserves; written here against T-003's current `Bs*Style` convention as **`BsPaneSplitterVerticalStyle`** and **`BsPaneSplitterHorizontalStyle`**. If T-001's reserved prefix differs at build time, both references are renamed and nothing else in this task changes.

What T-005 **requires** of those styles — a contract on T-003, verified by AC-05, not implemented here:

- paints a 1px hairline from the divider brush, centred in a 1px track;
- presents a ~7px hit target (`Width="7"` + `Margin="-3,0,-3,0"` + `Panel.ZIndex` above its neighbours), because a 1px splitter is unusable with a mouse and IDEs paint 1px while grabbing ~7px — and `Grid` does not clip its children, `ClipToBounds` defaulting to `False`;
- `ShowsPreview="False"` (live resize, no ghost), `ResizeBehavior="PreviousAndNext"`, `Focusable="True"`, a `SizeWE` / `SizeNS` cursor, and a hover/drag/keyboard-focus affordance.

T-005 hardcodes no hex, no template, and no `<Style>` block of any kind — AC-04 greps for that.

### 4. `src/WindowsFileManager/Views/Screens/DuplicatesScreenView.xaml.cs` — new, `[ExcludeFromCodeCoverage]`

Excluded twice over: by the runsettings glob `Exclude=[WindowsFileManager]*Views*` (the type's full name `WindowsFileManager.Views.Screens.DuplicatesScreenView` matches `*Views*`) and by the attribute, matching the precedent at `MainWindow.xaml.cs:16`.

```csharp
private bool _isApplyingLayout;
private double? _desiredScopeWidth;       // user intent — NOT the clamped result

```

- **`OnLoaded`** — read `_desired*` from `vm.ScopePanelWidth` / `vm.RightStackWidth`, call `ApplyPaneLayout()`.
- **`OnSizeChanged`** — `ApplyPaneLayout()` (the host got wider or narrower; intent is unchanged, the resolved value moves).

**No `INotifyPropertyChanged` subscription.** The earlier draft subscribed to `vm.PropertyChanged` for `IsPreviewVisible` (and `IsAnalyticsVisible`) and unsubscribed in `OnUnloaded` to avoid a handler leak across tab switches. Both are gone: the preview collapse is T-008's, inside its own control, and the analytics overlay is a plain `Visibility` binding that needs no code. T-005 therefore subscribes to nothing that outlives it and has no unsubscribe obligation — the leak risk moves to T-008 along with the subscription.

```csharp
private void ApplyPaneLayout()
{
    if (_isApplyingLayout) return;          // assigning GridLength re-enters SizeChanged
    _isApplyingLayout = true;
    try
    {
        var host  = BodyGrid.ActualWidth;
        var scope = PaneLayout.ResolveScopeWidth(host, _desiredScopeWidth);
        var right = PaneLayout.ResolveRightStackWidth(host, scope, _desiredRightStackWidth);

        ScopeColumn.MaxWidth      = PaneLayout.ScopeMaxForHost(host);
        RightStackColumn.MaxWidth = PaneLayout.RightStackMaxForHost(host, scope);
        SetWidth(ScopeColumn, scope);
        SetWidth(RightStackColumn, right);

        AnalyticsOverlay.Width =                                          // [OVL]
            PaneLayout.ResolveAnalyticsOverlayWidth(ResultsHost.ActualWidth);
    }
    finally { _isApplyingLayout = false; }
}

private static void SetWidth(ColumnDefinition col, double px)
{
    if (col.Width.GridUnitType != GridUnitType.Pixel || Math.Abs(col.Width.Value - px) > 0.5)
        col.Width = new GridLength(px);     // assign only on real change — kills the layout storm at source
}

private void PaneSplitter_DragCompleted(object sender, DragCompletedEventArgs e) => PersistPaneWidths();

private void PaneSplitter_KeyUp(object sender, KeyEventArgs e)
{
    if (e.Key is Key.Left or Key.Right) PersistPaneWidths();
}

private void PersistPaneWidths()
{
    _desiredScopeWidth      = ScopeColumn.ActualWidth;
    _desiredRightStackWidth = RightStackColumn.ActualWidth;
    if (DataContext is MainViewModel vm)
        vm.SetPaneWidths(_desiredScopeWidth.Value, _desiredRightStackWidth.Value);
}
```

The `KeyUp` hook is not decoration. `GridSplitter` handles arrow keys in `OnKeyDown` and resizes **without** raising `DragCompleted`, so keyboard-only resizing would silently never persist. `ColumnDefinition.ActualWidth` is a real read-only property on the `DefinitionBase` subclass, which is why no wrapper element is needed to measure. (T-008's horizontal splitter needs the identical `KeyUp` treatment for `Key.Up`/`Key.Down` — recorded in Interfaces.)

### Verification — stated honestly

There are no UI tests, no visual-regression harness, and none is introduced here; building one is a different task. Verification is three-legged, and the split is deliberate:

1. **Every decision this task makes lives in `PaneLayout`** — pure `double` math, pinned to 100% line/branch/method by rows 1-31. Row 31 additionally pins the *budget* itself, so a future edit that shaves `PreviewMinHeight` back toward the old `120` without re-deriving `HostMinHeight` fails a test instead of silently clipping the metadata rows.
2. **The WPF plumbing that consumes it is `[ExcludeFromCodeCoverage]` code-behind in the `Views` namespace**, matching the existing `MainWindow.xaml.cs` precedent, and is covered by the manual pass in rows 32-42, run at **1600×900, 1140×550, and maximized on the largest attached monitor**, with results recorded in the PR body.
3. **The persistence round-trip has a real automated pin at the seam that matters** — `SettingsServiceTests.SaveAndLoad_MultiProfile_ShouldRoundTrip` extended from five global fields to eight, which is what would actually catch a serialization regression.

What this does **not** verify: that the rendered frame looks like 3a. Nothing in this repo can assert that today. The pixel claim rests on AC-03's arithmetic (`260 | 1 | 978 | 1 | 360` at 1600) plus a side-by-side against the artboard during review.

## Edge cases

- **Pre-layout `ActualWidth = 0`.** `Loaded` can fire before arrange for a `UserControl` inside a `ContentControl`. `ResolveScopeWidth(0, …)` must return `ScopeMinWidth`, not throw — the `Max(Min(…))` shape in `ScopeMaxForHost` guarantees `Math.Clamp`'s `min <= max` precondition. Same defence in `ResolveAnalyticsOverlayWidth`. Rows 18, 30.
- **`ActualWidth = NaN`** during a measure pass with an infinite constraint. Same defence. Rows 19, 30.
- **Host narrower than `HostMinWidth`.** Still reachable despite `MinWidth=1140` — a `WindowState.Maximized` restore onto a monitor smaller than 1140 logical px, or a mid-session DPI-scale change. All three tracks fall to their minima and the `Grid` overflows by the shortfall, clipping on the right. Documented, not defended: the alternative is auto-collapse, which is fork B2.
- **Host shorter than `HostMinHeight`.** The same class, newly reachable because the height floor rose from an assumed ~243 to a budgeted 433. A restore onto a 768px-tall display with the window near-full-height is fine (768 − 98 = 670 > 433); a 600px-tall virtual desktop is not. WPF grows the window to `MinHeight` on restore, so the only true failure is a desktop shorter than 550px. Documented, not defended.
- **`Math.Clamp` throwing when `min > max`.** The one real crash this design could produce. `ScopeMaxForHost` / `RightStackMaxForHost` never return below their minimum; the `Max()` wrapper is what makes that true and must not be refactored away.
- **Preview collapse leaving no way back.** With the struck `Height=0` + `MinHeight=0` form, collapsing Preview removed its 30px header — and the header carries the artboard's only `✕` / `Auto ✓`, so nothing on screen could re-open it. **T-008's header-only collapse (`Height=30`, splitter hidden, header retained) is the adopted semantic precisely because it keeps the restore affordance in the frame.** T-005's obligation is non-interference (row 39): the column width, its `MinWidth`, and the height budget are all independent of `IsPreviewVisible`.
- **`SizeChanged` re-entrancy.** Assigning `ColumnDefinition.Width` triggers a layout pass that re-raises `SizeChanged`. Guarded by `_isApplyingLayout` **and** by `SetWidth`'s 0.5px tolerance, which stops the storm at the source.
- **Keyboard resize does not raise `DragCompleted`.** `GridSplitter` handles arrow keys in `OnKeyDown`. Without the `KeyUp` hook, keyboard-only users silently never persist a resize. T-005 hooks `Left`/`Right`; T-008 must hook `Up`/`Down` for its own splitter or the ratio never persists from the keyboard. Row 33.
- **`MainWindow_Loaded` force-hides Preview and Analytics** "because Folder is the first tab" (SPEC-009 rule 13), and `TabControl_SelectionChanged` re-applies it. With Duplicates as the first tab under T-004, that logic would open the app with the Preview pane collapsed — contradicting 3a, which draws it open. The fix belongs to T-004 (it owns `MainWindow.xaml.cs`'s tab wiring); T-005 records it here so it is not discovered at review, and neither T-005 nor T-008 should work around it locally.
- **Drag while `_isSwitchingProfile` is set.** `SaveSettings()` returns immediately (SPEC-009 rule 8), so the drag itself writes nothing — but `SetPaneWidths` already mutated `_settings`, and the switch's trailing `_settingsService.Save(_settings)` persists it. Net: the value survives. Row 40.
- **Two instances running.** Last writer wins, as for every other setting (SPEC-009 invariants) — instance A's drag can be overwritten by instance B's next save. Pre-existing, not worsened.
- **Corrupt JSON.** A `"wide"` string where a `double?` is expected raises `JsonException` and drops the **entire** file to defaults (SPEC-009 rule 3) — the user loses their profiles too, not just their panes. Pre-existing, but worth naming in the spec because these three fields add three more chances to hand-edit the file wrong. Row 35.
- **Downgrade then upgrade.** A build without these fields ignores them on read and **drops them on write** (`System.Text.Json` does not round-trip unknown properties), so panes reset to defaults. Acceptable; there is no schema version to branch on (SPEC-009 § Not implemented).
- **Per-monitor DPI change.** Persisted values are logical px, so dragging the window from a 100% to a 150% monitor keeps logical widths and the panel occupies the same fraction. Correct, no action.
- **Handler leak across tab switches — no longer T-005's.** The `vm.PropertyChanged` subscription moved to T-008 with the collapse behaviour. T-005 subscribes to nothing that outlives its own view, so it has no unsubscribe obligation; T-008 inherits both the subscription and the `OnUnloaded` requirement (the VM outlives the view).
- **Analytics overlay covering the wrong things `[OVL]`.** The overlay sits in the centre column's list row only (`Grid.Row="3"`), never spanning the 30px header, the 36px toolbar, the 26px column headers, or the 40px action bar — so the filter controls and the Recycle button stay reachable with the dashboard open. Row 41.
- **Analytics overlay in a narrow centre column `[OVL]`.** At `ResultsMinWidth = 640` a 320px overlay covers half the list. `ResolveAnalyticsOverlayWidth` clamps to `resultsWidth − 24` with a 240px floor, so it never touches the left edge; below ~264px of results width it simply overflows, which cannot happen because `ResultsMinWidth` is 640. Rows 28-30.
- **Very long Scope paths.** `D:\Backup\Photos\2019\Family` at `ScopeMinWidth = 200` needs `TextTrimming` in T-006's row template; T-005 guarantees only the 200px floor.
- **1px splitter columns at fractional DPI.** At 150% scaling a 1px column renders as 1.5 device px and can read as 2px. `SnapsToDevicePixels="True"` on `BodyGrid` is the cheap fix and costs nothing.

## Risks

- **The T-005/T-008 seam re-opens.** This revision exists because both specs built the same right-stack rows, the same horizontal splitter, and two contradictory collapse semantics. The seam is now written down in three places (Design's boundary table, Interfaces § T-008, Dependencies § Coordination), but it is a *convention between two documents*, not a compiler-enforced boundary. If T-008 is revised without re-reading this, the same collision returns. *Mitigation:* AC-01 and AC-02 assert mechanically that this file declares no right-stack rows and exactly two splitters — a re-collision fails an acceptance check rather than surviving to review.
- **The pane-minimum budgets get "tidied" back down.** `245` / `187` look like arbitrary large numbers next to the old `120` / `122`. A future editor trimming them without re-deriving `HostMinHeight` silently clips the Rules compose row or the Preview metadata block, and nothing renders an error — the content is just gone. *Mitigation:* matrix row 31 asserts `PreviewMinHeight + 1 + RulesMinHeight == HostMinHeight`, and §1 itemises every component so a trim has to argue with a specific line.
- **The frame is unverifiable by machine.** 100% coverage on `PaneLayout` proves the arithmetic, not that the screen looks like 3a. A regression that mis-parents a panel or drops a splitter compiles clean and passes CI. *Mitigation:* AC-02's grep counts, AC-03's arithmetic, and a mandatory three-size manual pass recorded in the PR body.
- **`Math.Clamp` with `min > max` throws.** A single careless simplification of `ScopeMaxForHost` turns a narrow window into a startup crash. *Mitigation:* rows 17-19 and 29-30 pin it, and the `Max(Min(…))` shape carries a comment saying why it is shaped that way.
- **`ClipToBounds` upstream silently kills the hit target.** If T-004's screen host or T-002's panel root sets `ClipToBounds="True"`, the consumed style's −3px overhang is clipped and the grab area drops to 1px — the frame *looks* right and is nearly unusable. Now doubly worth checking because the style is T-003's and its author cannot see this frame's ancestors. *Mitigation:* AC-05 checks ancestors explicitly.
- **T-003's splitter style does not meet the contract.** T-005 no longer owns the splitter's appearance or hit target, so a T-003 style that paints 3px, or omits the negative-margin overhang, is a defect T-005 can only report. *Mitigation:* the contract is written in Interfaces as a requirement on T-003 and verified by AC-05 here; discovering it late costs a T-003 revision, not a T-005 rewrite.
- **SPEC-009's counted lists drift.** Rule 10 states "**27** call sites" and "28 occurrences of the identifier"; rule 8 says "the five window fields". Adding **two** methods (`SetPaneWidths`, `SetPreviewRatio`) and three fields invalidates all three counts — and the two-method split makes the arithmetic easier to get wrong than the single-method draft did. Miss one and the spec is wrong in a way no test catches. *Mitigation:* AC-21 (c)+(d) name every count that moves and both method names.
- **`MinWidth` 1000 → 1140 **and** `MinHeight` 500 → 550 are two real user-facing losses `[B1]`.** The height raise is new to this revision and is a direct consequence of budgeting the pane minima honestly. Anyone tiling the app half-screen on a 1080p display (960px) can no longer size it that way, and a short window loses 50px more. Fork B exists because only the user can accept that — and the user should be shown both numbers, not just the width.
- **The analytics overlay is invented framing `[OVL]`.** 3a draws no analytics surface at all, so the overlay is the one place this task departs from the artboard. It is defensible (it preserves a shipped feature that would otherwise be homeless, and it is the only option compatible with T-008's two-pane right stack) but it is a judgement, and a reviewer comparing against the canvas will find it. *Mitigation:* it is named in Decision, marked `[OVL]` everywhere it appears, and A3 is recorded as the clean alternative if the user prefers to drop the feature outright.
- **The `ColumnDefinition` binding temptation.** A reviewer will reasonably ask why this is code-behind rather than bindings. The answer — `DataContext` inheritance into `ColumnDefinitionCollection` is historically unreliable — is easy to forget and easy to "fix" into a bug. *Mitigation:* T-012's ADR records it, and `docs/modules/ui.md` § Rules #2 gains the line.
- **`SizeChanged` layout storm.** A missing re-entrancy guard pins a CPU core on window resize — visible in the app's own resource monitor (SPEC-006), which makes it embarrassing as well as slow.
- **Sequencing.** Four hard dependencies (now including T-003, which this revision promoted from soft to hard) put T-005 behind the entire first half of the epic, while T-006 / T-007 / T-008 sit behind T-005. This is the epic's critical path; slipping T-002 or T-003 slips everything after it.
- **Analyzer friction on new files.** `TreatWarningsAsErrors` + `CodeAnalysisTreatWarningsAsErrors` turn CA1052 (static holder), CA1707, SA1210 ordering and friends into build failures. Cheap to fix, easy to hit on the first commit.

## Open decision

**Fork A is now RESOLVED — it is no longer a user question.** The panel review found A1 unbuildable: T-008 owns the 360px column, specs it as exactly two panes, and states in its own Out-of-scope that the analytics panel does **not** move into the right stack. Adding a third tool-window plus a fourth splitter from T-005 would have two tasks authoring the same `RowDefinitionCollection`. A1 is struck.

**Resolution: the analytics dashboard becomes a right-aligned overlay inside the results column (the former A2).** Concretely — a second child of the centre column's `Grid`, spanning its list row, `HorizontalAlignment="Right"`, `Panel.ZIndex="20"`, width from `PaneLayout.ResolveAnalyticsOverlayWidth(...)`, `Visibility` still driven by `IsAnalyticsVisible` through the existing `BoolToVisibilityConverter`. Why this and not the alternatives:

- It keeps the right stack at **exactly the two panes 3a draws** and T-008 specs — zero contention.
- It **does not regress a shipped feature**. The `✦ Analytics` `ToggleButton` at `MainWindow.xaml:834`, the `CloseAnalytics_Click` handler and the whole `ScanAnalytics` surface keep working untouched.
- It adds **no splitter, no row, no new VM state** — the overlay is not resizable and is not persisted.
- Its cost, stated plainly: the artboard never draws this surface. An overlay is invented framing. It is the smallest invention available, and it is confined to a surface 3a leaves undefined (3a simply has no analytics affordance at all).

The only alternative that remains is **A3 — drop analytics from the Duplicates screen entirely**, which requires deleting the `✦ Analytics` toggle at `:834` in the same commit and recording the loss in SPEC-006 § *Not implemented*. A3 is a visible feature regression, so it is recorded in Out of scope rather than chosen. Every A2-only clause below is marked `[OVL]` so A3 can be cut cleanly if the user overrules this.

**Fork B remains a real user call — raise the window minimums, or auto-collapse the right stack on narrow windows?**
The frame's true width floor is `ScopeMin 200 + 1 + ResultsMin 640 + 1 + RightStackMin 280 = 1122` px of screen-host width. Its height floor is now `PreviewMin 245 + 1 + RulesMin 187 = 433` px of right-stack height (recomputed against the shipped panel contents — see Detail §1), plus `34 + 38 + 26 = 98` of chrome = **531**. Today `MainWindow.xaml:9` sets `MinHeight="500" MinWidth="1000"`, and **neither** floor is met.
  - **(B1, recommended)** Raise to `MinWidth="1140"` and `MinHeight="550"`. Deterministic, zero new behaviour, the layout can never break.
  - **(B2)** Keep the current minimums and auto-collapse the right stack below the floor. Preserves the small-window case but invents a collapse rule the canvas does not draw, and auto-collapse that fights the user is the classic IDE annoyance.
This spec is written for **B1**. Note that B1's cost grew when the pane minima were recomputed: it is now two losses, not one — a user tiling the app half-screen on a 1080p display (960px) can no longer size it that way, **and** a user with a 500px-tall window loses 50px more. B2 is recorded in Out of scope as a follow-on if the user picks it.
