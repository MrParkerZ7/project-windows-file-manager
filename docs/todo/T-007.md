## Concept

The centre column of 3a is the screen's reason to exist: everything else — Scope, Preview, Rules, the action bar — orbits the list of duplicate groups. Today that centre is not a list; it is a five-row stack of coloured `Border`s (`MainWindow.xaml:930-1690`) in which the results occupy the bottom `GroupBox` and everything above it is a WrapPanel of pastel toolbars competing for the same eye: a `#F0F4FF` **Base Filters** bar, a `#F8F9FC` extension-chip strip, a `#FFFBF0` rule builder, and a `#FFF3E0` action strip. The user has to scan four differently-coloured boxes to find out how the list in front of them was narrowed.

3a replaces that with the IDE convention: **one 30 px header, one 36 px toolbar row, one column header, then rows.** The header states the result set (`Duplicate groups` · `3 of 3 · 41.2 MB reclaimable`) and owns expansion (`Expand all` / `Collapse all`). The toolbar states the narrowing, left to right, in the order a person actually thinks: *Type* → *Copies ≥* → *Size ≥* → *Sort* → a hairline → *Mark: All · Newer · Older · By rules · None*. Below it a four-name column header — **File / copy · Modified · Size · Keep** — that both group rows and copy rows align to.

The single most important change is the last column. Today selection is a checkbox meaning *"this file is selected for deletion"*: the affirmative click means destruction. 3a inverts the reading — the column is called **Keep**, a filled dot means this copy survives, a hollow dot means it goes. The underlying flag does not change (`ScannedFile.IsFileSelected` is still the only per-file state, still means *marked for action*); what changes is that the UI now shows the user the thing they care about — what survives — rather than the thing the code stores.

That inversion also forces a defect into the open. Today the per-copy checkbox binds `IsFileSelected` and nothing else (`MainWindow.xaml:1647`), while the counter that drives *"N files selected"*, `HasSelectedFiles`, and `DeleteSelectedFilesCommand.CanExecute` is recomputed only inside the bulk selectors (`RefreshSelectedFileCount()`, `MainViewModel.cs:4870`). A hand-ticked box therefore changes what a delete *does* without changing what the UI *says it will do*. 3a puts that readout directly above a destructive verb (`Recycle 4 files`, T-009), so the epic can no longer carry the bug: the Keep control invokes a refresh on every direct tick.

The second change is vocabulary. The word "select" appears in the baseline as `✓ All`, `✓ Newer`, `✓ Older`, `✕ Clear`, per-group `✓ Select All` / `✕ Clear`, and `N files selected` — six spellings of one idea, scattered across two toolbars. 3a collapses them to one cluster with one verb: **Mark**. `By rules` folds `ApplyFilterRulesCommand` (today a `▶ Apply` button buried in the rule builder) into that same cluster, so every way of marking files sits in one place. Nothing in the selection engine changes; only its front door does.

This task deliberately does **not** touch what a duplicate is, what a scan looks for, what happens when you recycle, or any colour beyond the Broadsheet neutral/accent tokens T-001 extracts. It restructures the frame around behaviour that already works — and, in doing so, forces three specs to finally describe what the code does.

## Design

**Shape.** One new `UserControl` occupies the `1fr` centre column of T-005's `260px | 1px | 1fr | 1px | 360px` grid. It is a five-row `Grid`:

```
Row 0  Auto   ToolWindowHeader        30 px   "Duplicate groups"  ·  "N of M · X reclaimable"  ·  Expand all / Collapse all
Row 1  Auto   Toolbar                 36 px   Type ▾ · Copies ≥ [n] · Size ≥ [n][unit ▾] · Sort ▾ ┃ Mark: All Newer Older By-rules None
Row 2  Auto   ColumnHeader            26 px   (gutter) · FILE / COPY · MODIFIED · SIZE · KEEP · (verbs)
Row 3  *      ListView (groups)               group row 32 px  +  collapsible copy rows 30 px
Row 4  Auto   <owned by T-009 — action bar>
```

Rows 0-3 are T-007. Row 4 is left as an empty `Grid.Row` placeholder with a comment naming T-009, so the two tasks do not fight over the same `RowDefinitions` block.

---

**Container shape — settled here, normative for T-011.** The list is a `ListView` with **no `View` set** — there is **no `GridView`**, no `GridViewColumnCollection`, and no `GridViewRowPresenter` anywhere in this control. This is not a preference; `GridViewRowPresenter` renders **exactly one row of cells per item container**, and a T-007 item container is *a group*: a 32 px header row **plus** N collapsible 30 px copy rows. A GridView cannot express that shape, so adopting it would mean flattening the hierarchy and losing 3a's group/copy structure.

Consequences, stated unconditionally so the two specs agree:

- **T-007 owns the initial `ListViewItem` container style.** It is declared in this control as a bare `Border` + `ContentPresenter` retemplate (`HorizontalContentAlignment=Stretch`, `Padding=0`, `BorderThickness=0`, `Background=Transparent`) with one `IsSelected` trigger. It exists from the moment T-007 lands, because T-007 lands before T-011.
- **T-011's `Broadsheet.ResultRow` is retargeted, not applied as published.** T-011 extends *this* container style with focus visuals, keyboard affordances and AT names. It **must not** reintroduce `GridViewRowPresenter` or bind `GridView.ColumnCollection` — those would render nothing here. If T-011 needs its own key, it takes over the style T-007 declares and keeps the `ContentPresenter` shape.
- **Column alignment is not GridView's job.** The six-column contract below is declared identically in the column-header row and both data templates. There is no `GridViewHeaderRowPresenter`; Row 2 *is* the column header.

**The shared six-column contract.** The artboard pins one grid used by three different templates:

```
28px  |  1fr  |  130px  |  90px  |  70px  |  90px      gap 10px
────────────────────────────────────────────────────
 ▼/▶     name/path   Modified   Size    Keep    verbs
```

Rows 2 (column header), the group-row template, and the copy-row template each declare this identical `ColumnDefinition` set. The widths are declared once as `GridLength` resources in the control's own `UserControl.Resources` and referenced by `StaticResource` in all three places — one edit point, three consumers. `SharedSizeGroup` is deliberately **not** used: shared-size scopes force a synchronous cross-row measure pass that fights `VirtualizingStackPanel` recycling, and this grid's widths are fixed anyway, so the scope would buy nothing and cost scroll smoothness.

---

**Design-token and style-key policy — T-007 invents no key names.** The earlier draft of this spec named its own keys (`Brush.Bg`, `RowLinkButtonStyle`, …) and they matched neither T-001's token dictionary nor T-003's component catalogue. That is corrected structurally rather than by guessing new names:

1. **T-007 declares no design-token or component-style key.** Every brush, font, size and style it uses is consumed by the key name **published by the owning task** — T-001 for tokens, T-003 for component styles — lifted verbatim from that task's dictionary at implementation time.
2. **The Detail section lists roles, not names.** Each row states the visual role, the owning task, and the artboard value that role must carry, so a reviewer can check the mapping without T-007 having pre-empted the naming.
3. **A missing key is a change to the owning task's dictionary, never a local declaration and never an inline hex.** Two roles are known today to be absent from T-001's token set — an *accent tint* ground for the extension tag and a *subtle divider* for the copy-row hairline. Both are requested as T-001 contract additions with exact values, and both carry a documented fallback onto tokens T-001 already carries if the addition is refused (see Detail → *Token roles*).
4. **A pre-flight reconciliation is an acceptance item.** Before markup is written, every key this control will reference is grepped against T-001's dictionary file and T-003's catalogue; the count of unresolved keys must be zero. `DynamicResource` fails **silently** at runtime (no build error, no exception — just an unpainted brush), so this check is the only thing standing between a typo and a shipped grey screen.

---

**Group / copy hierarchy.** The outer `ListView` binds to the existing `FilteredDuplicateGroups` `ICollectionView` — the filter predicate, the sort descriptions and the extension facet are untouched machinery. Each `ListViewItem` renders *one group*: a 32 px group row (surface ground, hairline under) plus, when expanded, an `ItemsControl` over `group.Files` rendering 30 px copy rows on the editor ground with a subtler hairline. Expansion is model state — `DuplicateGroup.IsExpanded` — not container state, because `Expand all` / `Collapse all` must work on groups whose `ListViewItem` has been recycled away by virtualization. Collapsed groups do not merely hide their copy rows; a `ContentControl` swaps its `ContentTemplate` to `{x:Null}`, so the copy containers are never generated at all.

**The Keep control (D1 A/B/C).** A chromeless **`ToggleButton`** carrying T-003's keep-cell style, `IsChecked` two-way to `IsFileSelected` (filled dot = kept = `false`), **and a `Command` binding to `RefreshMarkedCommand`**. `ToggleButton` derives from `ButtonBase`, so `Command` is available on it — and the WPF ordering is exactly what this needs: `ToggleButton.OnClick()` calls `OnToggle()` (which flips `IsChecked` and pushes the two-way binding to `ScannedFile.IsFileSelected`) **and then** `base.OnClick()`, which raises `Click` and executes `Command`. The refresh therefore always runs *after* the model is updated, on mouse click and on the keyboard `Space` path alike. Programmatic changes (the bulk `Mark:` commands) do **not** raise `Click` — correct, because those commands already call `RefreshSelectedFileCount()` themselves.

**Filter commit model.** The artboard has **no Apply button**. The three numeric/facet inputs therefore commit themselves: the `MinFileSizeText` / `MinDuplicateCount` text boxes use `UpdateSourceTrigger=LostFocus` plus the repo's existing `TextBoxEnterKeyBehavior` (which calls `BindingExpression.UpdateSource()` before executing its command — verified at `TextBoxEnterKeyBehavior.cs:56-58`), and the three property setters call `ApplyFilters()`. Committing on blur-or-Enter rather than per-keystroke means typing `100` filters once at `100`, not three times at `1`, `10`, `100`.

**The Type facet.** The baseline's always-visible strip of extension checkboxes (`MainWindow.xaml:1047-1082`) folds into the toolbar's `Type ▾` chip: a `ToggleButton` whose caption is a computed summary (`All` / `.jpg` / `3 types` / `None`) opening a `Popup` that contains the same `ItemsControl` of checkboxes plus the existing `All` / `None` command buttons. Multi-select semantics, `ExtensionFilter.IsChecked`, and the per-item `PropertyChanged → ApplyFilters` subscription are all preserved verbatim; only the container changes.

**Verb placement.** The artboard shows two inline verbs per row and an overflow on copies (`Open · ⋯`). The baseline has five group verbs and three copy verbs. Rather than drop commands, the artboard's own overflow idiom is applied to both levels: group row → `Preview · Recycle · ⋯` where `⋯` = { Mark all in group, Keep all in group }; copy row → `Open · ⋯` where `⋯` = { Preview, Recycle }. No command is lost, and no affordance is invented that the artboard does not already use one level down.

**What is deliberately left alone.** The scan pipeline, `FilterDuplicateGroup`, `ApplySorting`, the ten sort labels (renaming them would silently break `ProfileSettings.SelectedSortOption` round-trips — see Risks), `ScannedFile.IsFileSelected`, every delete/move/undo path, and every colour decision beyond consuming the tokens T-001 publishes.

### Core — `DuplicateGroup.cs`

```csharp
public class DuplicateGroup : INotifyPropertyChanged
{
    private bool _isExpanded = true;

    public event PropertyChangedEventHandler? PropertyChanged;

    /// <summary>Gets or sets a value indicating whether this group's copy rows are shown.</summary>
    public bool IsExpanded
    {
        get => _isExpanded;
        set
        {
            if (_isExpanded != value)
            {
                _isExpanded = value;
                PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(nameof(IsExpanded)));
            }
        }
    }

    /// <summary>Gets the first file's name without its extension (the group-row title).</summary>
    public string FirstFileBaseName => Files.Count > 0
        ? System.IO.Path.GetFileNameWithoutExtension(Files[0].FilePath)
        : string.Empty;

    /// <summary>Gets a value indicating whether every copy has the same byte size.</summary>
    public bool HasUniformFileSize =>
        Files.Count > 0 && Files.All(f => f.FileSize == Files[0].FileSize);
}
```

`ScannedFile` already implements `INotifyPropertyChanged` for `IsFileSelected` (`ScannedFile.cs:18-26`), and `DuplicateGroup` already carries a pure-presentation member (`DeleteAllLabel`, emoji and all), so this follows the model's own precedent rather than inventing a layering exception. The raise-only-on-change guard mirrors `ScannedFile.IsFileSelected` exactly.

`HasUniformFileSize` exists because the artboard's group caption reads *"{size} each"*, which is a lie in name-pattern mode: `DuplicateScannerService.cs:235` sets `FileSize = orderedFiles.Max(f => f.FileSize)` for regex groups, whose members are **not** the same size. The template switches the caption to *"up to {size} each"* when the flag is false.

<ToggleButton Grid.Column="4"
              Style="{DynamicResource «T-003 keep cell, TargetType=ToggleButton»}"

                                RelativeSource={RelativeSource AncestorType=UserControl}}"

Three things this markup pins down, each previously missing:

1. **The refresh hook.** `ToggleButton` derives from `ButtonBase`, so `Command` is available. `ToggleButton.OnClick()` runs `OnToggle()` — flipping `IsChecked` and pushing the two-way binding into `ScannedFile.IsFileSelected` — **and then** `base.OnClick()`, which executes `Command`. The refresh therefore always sees the updated model, on both the mouse path and the keyboard `Space` path. Without this line the action bar's headline count and its `Recycle N files` label go stale on every direct tick, directly above a destructive verb (Risks #14). No `CommandParameter`: `RefreshMarkedCommand` re-derives the whole count.
2. **The control type.** `ToggleButton`, not `RadioButton` — a `RadioButton` in a per-group `GroupName` auto-unmarks its siblings, which is the exactly-one-keeper product of decision **D1-D**, not the free multi-mark model the code and SPEC-004 describe. Under A/B/C there is no `GroupName` because there is no radio group.
3. **The visual.** The dot lives entirely in T-003's style: a 15 px ring in the body-foreground token, filled when `IsChecked` is `False` (**filled = kept**), hollow when `True` (**hollow = marked**), with the two tooltips *"Kept — this copy stays"* / *"Marked — this copy will be recycled"*. No `Ellipse`, no colour and no `ControlTemplate` is authored here.

This is the **only** per-copy state affordance in 3a (the artboard's 28 px gutter on copy rows is empty — the baseline checkbox is gone), so it must be interactive; a read-only indicator would make single-copy selection unreachable.

**Selection-changed hand-off.** `MainWindow.xaml.cs:298 DuplicateGroups_SelectionChanged` stops `VideoPlayer` / `AudioPlayer`, which live in the preview panel (T-008) and are unreachable from inside this `UserControl`. `ResultsEditorView` therefore declares a bubbling routed event and re-raises:

```csharp
public static readonly RoutedEvent GroupSelectionChangedEvent = EventManager.RegisterRoutedEvent(
    "GroupSelectionChanged", RoutingStrategy.Bubble, typeof(RoutedEventHandler), typeof(ResultsEditorView));

public event RoutedEventHandler GroupSelectionChanged
{ add => AddHandler(GroupSelectionChangedEvent, value); remove => RemoveHandler(GroupSelectionChangedEvent, value); }

private void OnGroupSelectionChanged(object sender, SelectionChangedEventArgs e)
    => RaiseEvent(new RoutedEventArgs(GroupSelectionChangedEvent));

private void OnGroupOverflowClick(object sender, RoutedEventArgs e)
{
    if (sender is Button b && b.ContextMenu is { } menu) { menu.PlacementTarget = b; menu.IsOpen = true; }
}
```

`MainWindow.xaml` subscribes: `<duplicates:ResultsEditorView GroupSelectionChanged="DuplicateGroups_SelectionChanged"/>` — the existing handler body is unchanged.

### Fidelity deviations from the artboard (deliberate, each justified)

1. **`letter-spacing` on the column header** — WPF `TextBlock` has no letter-spacing property. Uppercase literals only.
2. **`⋯` on the group row** — the artboard shows only `Preview · Recycle`, but the baseline has five group verbs. The overflow idiom is lifted verbatim from the artboard's own copy row rather than dropping `SelectAllInGroupCommand` / `ClearSelectionInGroupCommand`.
3. **Sort labels keep their existing text** (`"Wasted space (most)"`, not `"Wasted space ↓"`) — renaming them breaks profile round-trips (Risks).
4. **`"up to {size} each"`** in name-pattern mode where the artboard says `"{size} each"` — the artboard only depicts content mode, where sizes are uniform.
5. **No per-row dimming by mark state** — the artboard's `{{ f.pathColor }}` is ambiguous and colour-as-meaning is turn-4 territory; every copy path renders in the body-foreground token, the dot alone carries the state.
6. **Two token roles may render at reduced fidelity** if T-001 declines the accent-tint and subtle-divider additions — the fallbacks are named in *Token roles* and are recorded as deviations, not inlined as hexes.

## Edge cases

| Case | Behaviour | Why |
|---|---|---|
| **A direct Keep tick vs a bulk `Mark:` command** | Both refresh the marked-file readouts. The direct tick refreshes because the Keep control's `Command` runs `RefreshMarkedCommand`; the bulk commands refresh because they already call `RefreshSelectedFileCount()` themselves (`MainViewModel.cs:2824, 2851, 2878, 3035, 3074`). | The baseline refreshed **only** on the bulk path (`MainWindow.xaml:1647` binds `IsFileSelected` and nothing else), so a hand-ticked box left `SelectedFileCount`, `HasSelectedFiles` and `DeleteSelectedFilesCommand.CanExecute` stale while `DeleteSelectedFiles()` still acted on the real flags (`:4633`). 3a puts that count above `Recycle N files`, so the gap closes here. |
| **Ordering of the toggle and the command** | The model is updated *before* the refresh runs, always. | `ToggleButton.OnClick()` = `OnToggle()` (flips `IsChecked`, pushes the two-way binding into `ScannedFile.IsFileSelected`) **then** `base.OnClick()` (raises `Click`, executes `Command`). ## Open decision

Two genuine forks. Neither can be settled from the 3a artboard, the code, or the specs — both change what the product promises, so the user must pick.

---

**D1 — What does the Keep column *mean*? (zero-keeper policy **and** control type — one decision, not two)**

This fork was previously written as a policy question only. The cross-task review showed it is really a **control-type** question wearing a policy hat: T-003 publishes **`BsKeepRadioStyle` (a `RadioButton` style)** for this cell and T-011 requires a **per-group `GroupName`** on it. A WPF `RadioButton` with a per-group `GroupName` auto-unchecks its siblings — which *is* a semantic declaration: **exactly one copy survives per group.** That is a different product from the one on disk.

Today (`SPEC-004` edge case *"Delete all copies in a group"*): **any number of copies may be marked, including all of them.** `Mark: All` marks every copy in every group; `DeleteAllInGroup` removes a whole group; `ScannedFile.IsFileSelected` is a free per-file `bool` with no keep-one enforcement anywhere. 3a introduces a column literally named **Keep**, whose empty state now visibly promises "nothing here survives". That promise has to be honoured, softened, left as-is — or replaced by radio semantics.

| | Option | Control | Consequence |
|---|---|---|---|
| **A** | **No guard** — Keep is purely the visual inverse of `IsFileSelected`; a group with zero keepers renders all-hollow and nothing else happens. | `ToggleButton` | Zero risk, zero spec churn beyond the column itself. But the column's name over-promises: a user who reads "Keep" as "one is always kept" can still lose a whole group via **Mark: All → Recycle**. |
| **B** *(recommended)* | **Advisory marker** — a group whose copies are all marked shows a `⚠` in the group row's Keep cell (which the artboard leaves empty) plus a tooltip *"no copy kept — all N copies will be recycled"*. Nothing is blocked. | `ToggleButton` | Honours the column's promise without changing any command. Costs one Core property (`AllCopiesMarked`), one notify hook, one `DataTrigger`. SPEC-004's edge-case row gains a sentence; no rule changes. |
| **C** | **Enforce ≥1 keeper** — the last unmarked copy refuses to be marked; `Mark: All` leaves one copy kept per group. | `ToggleButton` + guard | A real behaviour change: breaks the documented ability to recycle every copy of a group, invalidates SPEC-004's *"there is no keep-one enforcement"* invariant and the `DeleteAllInGroup` path, and needs its own confirm-dialog rewording. |
| **D** | **Exactly one keeper — radio semantics.** Keep becomes a per-group `RadioButton` group: picking a keeper unmarks the previous keeper and marks every other copy. | `RadioButton` + `GroupName={group id}` | What T-003's `BsKeepRadioStyle` and T-011's `GroupName` requirement currently assume. It is the **largest** behaviour change in the epic: `Mark: All` (zero keepers) and *"keep 3 of 5"* become unrepresentable, `DeleteAllInGroup` contradicts the control, `ApplyFilterRulesCommand`'s free multi-mark output can no longer be rendered, and SPEC-004 rules 2/3/4/5/8/12/13 plus SPEC-003 rule 4 all change. |

**Recommended: B.** It is the only option that makes the word *Keep* honest without rewriting SPEC-004's action semantics mid-redesign.

**How each option settles the two sibling contracts (this is the part that was blocking):**

- **If A, B or C** — the Keep cell is a **`ToggleButton`** (chromeless, ringed-dot visual, `IsChecked` ⇄ `IsFileSelected`). Consequence, stated unconditionally so no sibling is left guessing: **T-003 republishes its keep-cell style with a `TargetType="ToggleButton"`** (same ringed-dot visual, key renamed off `…RadioStyle` — the *look* is a radio dot, the *control* is not a radio), and **T-011's per-group `GroupName` requirement is void** — there is no radio group, so there is nothing for selection to leak across, and T-011's AT pass covers the toggle's `AutomationProperties.Name` and `Focusable` instead.
- **If D** — the Keep cell is a `RadioButton`, T-003's `BsKeepRadioStyle` and T-011's `GroupName` stand as published, `DuplicateGroup` gains a stable `GroupName` string, and **T-007 must be re-estimated**: it absorbs a selection-engine rewrite, four SPEC-004 rule changes, and a rework of `Mark: All` / `By rules` / `DeleteAllInGroup`.

**Blocking.** Detail below is written for **A/B** (they share every mechanic; B adds one Core property, one notify hook and one trigger). C adds a guard. **D changes the estimate.**

**D2 — Mini Preview (`IsMiniPreview`) has no home in 3a. Retire it, or keep it?**

Verified: the 3a group row is **32 px** and contains name + ext tag + counts — no thumbnail, no icon. The baseline group row hosts a 60×60 `MiniPreviewConverter` thumbnail inside a `Border` gated on `IsMiniPreview` (`MainWindow.xaml:1596-1636`, `SPEC-005` rule 18), and 3a gives Preview its own permanently-visible 360 px tool-window (T-008), which shows the same thumbnail larger.

| | Option | Consequence |
|---|---|---|
| **A** *(recommended)* | **Retire it.** Delete the inline thumbnail `Border` from the group template, delete the `Mini Preview` toggle, keep `IsMiniPreview` on `ProfileSettings` as a dead-but-loadable field (so old `settings.json` still deserialises — `ProfileSettingsTests.Constructor_ShouldSetDefaults` pins its default and must keep passing). | Canvas-faithful, removes a surface made redundant by the always-on Preview tool-window, and keeps the group row at exactly 32 px. Costs a `SPEC-005` edit (rule 18 + the `Mini Preview` entry-point row deleted) and removes a shipped feature. |
| **B** | **Keep it as an opt-in row-height expansion** — thumbnail block retained, collapsed by default; when `IsMiniPreview` is true the group row grows from 32 px to ~76 px. The toggle needs a new home (nothing in 3a's results header holds it beyond `Expand all` / `Collapse all`). | No feature loss, but the 32 px row contract from the artboard only holds in the off state, and the toggle has to be invented somewhere the canvas does not show one. |

**Recommended: A.** **Non-blocking** — the Detail below is written for A, with the one-paragraph delta for B called out inline. A wrong guess here costs one template block, not a redesign.
