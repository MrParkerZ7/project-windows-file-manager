## Concept

The right 360px column stops being "a 380px preview slab bolted to the window" and becomes two IDE tool-windows, each with the same 30px header contract as Scope and the results editor. **T-005 builds the column, its rows and the splitter between them; this task builds the two things that live in it.**

The Preview tool-window is the smaller half of the change: the existing seven-renderer preview state machine (`image` / `video` / `audio` / `text` / `infocard` / `unsupported` / `none`) re-housed, plus the three metadata facts 3a asks for that the app has never surfaced — pixel dimensions, modified date, and full path. Re-housing it moves four `x:Name`d media controls out of `MainWindow.xaml.cs`'s reach, which forces one genuine architectural improvement: the results list stops reaching across the window to stop the players, and instead raises a signal on the view-model that the Preview tool-window listens for.

The Rules tool-window is the larger half, and it is where this epic pays off a two-year-old lie. Today a rule is a dense chip reading `Include | Filename | "IMG_"  [Regex, IgnoreCase]`, sitting under a `?` popup that says *"Ignore ALWAYS overrides Contains"* using two action names the code stopped using. The code has actually been first-match-wins-by-priority since it shipped. 3a's answer is to render each rule as a sentence a human can read aloud — *"Never mark path containing `\Originals\`"* — under a caption stating the resolution strategy in three words: **first match wins**. Once that caption is on screen it becomes a promise, and this task is where the promise, the loop at `MainViewModel.ApplyFilterRules`, and SPEC-003 are finally made to say the same thing.

The mechanical trick that makes the promise stick: the sentence vocabulary and the caption string both live as `const`s and pure functions in `WindowsFileManager.Core`, inside the 100%-enforced coverage boundary, and XAML binds them rather than restating them. The drift class that produced the stale popup — *"UI text is a XAML attribute nothing tests"* — is closed for this surface specifically, because the strings are now code with tests, not attributes.

## Design

**Shape of the delivered surface.** The frame — the 360px column, the three row definitions, the horizontal splitter, the collapse mechanism — is **T-005's** and is drawn here only as context (marked `[T-005]`). This task delivers the two boxed regions.

**Four design commitments, each with a reason:**

1. **`✕` collapses the pane to zero, and the header goes with it — T-005's mechanism, not ours.** In the old layout `IsPreviewVisible=false` collapsed a 380px `Border` and the window reflowed. Now the boolean drives T-005's `PreviewRow.Height` to `0` and hides `PreviewSplitter`; `ApplyPaneLayout` restores the user's dragged ratio on reopen. Nothing in `PreviewToolWindow.xaml` reads or reacts to `IsPreviewVisible` — it is a plain `UserControl` that assumes it is visible when it is measured. The re-open path is the results editor's per-copy `Preview` verb (T-007 → `PreviewFile()` → SPEC-005 rule 10 sets `IsPreviewVisible = true` on every branch). This is a real behavior change and it is why SPEC-005 rule 12's *host* sentence must be rewritten — **by T-005**.

2. **The results list signals through the view-model; it never reaches across the window.** `x:Name` scope is per-XAML-root, so once `VideoPlayer` and `AudioPlayer` live in `PreviewToolWindow.xaml`, the existing `DuplicateGroups_SelectionChanged` body (`MainWindow.xaml.cs:298–310`) stops compiling. Replacing it with a `PropertyChanged` subscription on `PreviewMediaUri` / `PreviewType` alone would silently drop a case: the group list is `SelectionMode="Extended"` (`MainWindow.xaml:1546`), so ctrl-clicking a second group raises `SelectionChanged` **without** moving the anchor and therefore without changing either property — yet today it stops playback. So the design is a *selection-changed path*, VM-mediated: `MainViewModel` gains `RequestStopPreviewMedia()` raising `PreviewMediaStopRequested`; the selection handler calls it; `PreviewToolWindow.xaml.cs` subscribes and stops both players. The property-change subscription is kept **in addition**, as the path for programmatic preview changes that originate outside a selection (the per-file `👁 Preview` verb, `ClosePreview` from a bulk action). Both routes call one idempotent `StopPlayers()`; `MediaElement.Stop()` on a stopped player is a no-op, so double-firing is harmless. This removes a cross-control dependency instead of papering over it, and it is the only interface obligation this task places on T-007's handler.

3. **The sentence is two runs, not one string.** The pattern must render in the mono face (3a: `font-family:ui-monospace`) while the clause renders in the body face. A single `TextBlock.Text` binding cannot style a substring, and a `Run`-based `TextBlock` with mixed bindings is brittle under `TextTrimming`. So the cell is a horizontal `StackPanel` of exactly two `TextBlock`s: `{Binding ClauseText}` and `{Binding Pattern}`, the second carrying the mono font role and the trimming. This keeps the clause an atomic, testable Core projection instead of six XAML converters wired in series.

4. **Vocabulary is Core data, XAML is a consumer.** `Mark` / `Never mark` / `name` / `path` / `containing` / `matching` and the caption `first match wins` are `const string`s on a new Core static class. `FilterRule.ClauseText` composes them; the compose-row `ComboBox`es render them through one covered converter; the caption `TextBlock` binds `{x:Static …}`. Nothing in this feature's user-visible wording exists only as a XAML attribute any more — precisely the property the old `CUSTOM FILTER RULES` `Tag` lacked when it drifted.

**What is emphatically not redesigned:** the seven-branch classification chain, the extension sets, the text sniff, the 1-second regex timeout, the `Exclude` post-pass asymmetry, the thumbnail cache, `MediaVolume`'s shared-slider quirk. This task re-frames the preview and re-renders the rules; it changes matching semantics **not at all**.

### 4. `FilterRule` and `FilterRuleVocabulary` (Core — under the gate)

New `FilterRuleVocabulary`:
```csharp
public static class FilterRuleVocabulary
{
    public const string MarkVerb = "Mark";
    public const string NeverMarkVerb = "Never mark";
    public const string NameNoun = "name";
    public const string PathNoun = "path";
    public const string ContainingRelation = "containing";
    public const string MatchingRelation = "matching";
    public const string FirstMatchWinsCaption = "first match wins";
    public const string RegexTag = ".*";
    public const string IgnoreCaseTag = "Aa";

    public static string Verb(FilterAction action) =>
        action == FilterAction.Exclude ? NeverMarkVerb : MarkVerb;
    public static string Noun(FilterTarget target) =>
        target == FilterTarget.Filepath ? PathNoun : NameNoun;
    public static string Relation(bool isRegex) =>
        isRegex ? MatchingRelation : ContainingRelation;

    // Fork-2 option A1 only:
    public static (string Pattern, bool IsRegex) ParsePattern(string raw)
    {
        var t = raw.Trim();
        return t.Length >= 2 && t[0] == '/' && t[^1] == '/'
            ? (t[1..^1], true)
            : (t, false);
    }
}
```
`Verb` / `Noun` / `Relation` are expression-bodied ternaries → **two branches each**; the coverage script reads branch-rate from Cobertura, so every `[Theory]` must cover both sides of all three. `ParsePattern` has three branches (`Length>=2`, leading `/`, trailing `/`) plus the `Trim` — cover `"/x/"`, `"x"`, `"/x"`, `"x/"`, `"/"`, `"//"`, `"  /x/  "`.

On `FilterRule`, add:
```csharp
[JsonIgnore]
public string ClauseText =>
    $"{FilterRuleVocabulary.Verb(Action)} {FilterRuleVocabulary.Noun(Target)} {FilterRuleVocabulary.Relation(IsRegex)}";
```
and convert `Pattern`, `IsRegex`, `IgnoreCase`, `Action`, `Target` from auto-properties to backed properties following the existing `IsEnabled` shape — `if (field != value) { field = value; Raise(nameof(X)); Raise(nameof(ClauseText)); Raise(nameof(DisplaySummary)); }` — and give `Priority` the same treatment (its setter is called by `RefreshRulePriorities`, and today an `ObservableCollection.Move` repositions containers without re-evaluating the `Priority` binding, so the number goes stale after a reorder; that latent bug becomes visible the moment the number is the only ordering cue on screen).

Consequences, all handled in this commit:
- `SkipAutoProps=true` in `coverlet.runsettings` means auto-props are free but **backed properties are not**. Six properties × (getter, changed-setter, unchanged-setter) all need coverage.
- `FilterRuleTests.FilterRule_PatternOrActionSetter_DoesNotRaisePropertyChanged` (:189) asserts the opposite of the new behavior and **must be rewritten**, not deleted — invert it to `…_DoesRaisePropertyChanged` and add the same-value no-raise case.
- `DisplaySummary` is **kept unchanged** — its four tests (`:23`, `:38`, `:144`, `:160`) stay green — and gets a real consumer as the row's `ToolTip`, so it does not become tested-but-dead.
- StyleCop `SA1600` requires an XML doc comment on every new public member; `SA1201`/`SA1202` require const → field → property ordering. `TreatWarningsAsErrors` + `CodeAnalysisTreatWarningsAsErrors` make each a build failure, not a warning.
- `CA1707` / `CA1802`: `const string` is fine; do not use `static readonly`.

## Edge cases

**Where the artboard and reality disagree, and what wins**

- **The Preview tool-window is roughly half a 360px column tall; the old panel was full-window-height at 380px wide.** A video renderer + transport row + volume slider + filename + four metadata rows do not fit at rest. Resolution: the renderer area is the only `*` row inside the panel, so it absorbs all the loss; name and metadata are `Auto` and survive to a ~30px renderer. Below that the user drags T-005's splitter. Do **not** make the metadata grid scrollable — a scrollbar on four rows reads as a bug.

- **`✕` collapses the pane to zero, so the panel's own header disappears with it.** This is T-005's mechanism and it is the accepted resolution, but it has a consequence the earlier draft dodged with a 30px header stub: there is no in-place reopen. The reopen path is the results editor's `👁 Preview` verb (T-007), which works because `PreviewFile` sets `IsPreviewVisible = true` on *every* branch (SPEC-005 rule 10). **The residual hole:** press `✕` with an empty result list and there is nothing to click until the next scan. That is real, it is small, and it belongs to T-005 as the grid owner if a persistent reopen strip is wanted — T-008 does not invent one.

- **Ctrl-clicking a second group changes neither preview property.** The group list is `SelectionMode="Extended"` (`MainWindow.xaml:1546`). Adding group B to a selection anchored on group A raises `SelectionChanged` but does not move `SelectedDuplicateGroup`, so `PreviewMediaUri` and `PreviewType` are untouched — and today's handler still stops playback. A `PropertyChanged`-only subscription would silently drop this, which is exactly the kind of regression that surfaces a month later as "sometimes the video keeps playing". Hence the VM event, and hence case **B6** in the matrix. Do not "simplify" the two routes down to one.

- **`x:Name` scope is per-XAML-root.** The moment `VideoPlayer` moves into `PreviewToolWindow.xaml`, every `MainWindow.xaml.cs` reference to it stops compiling. That is a compile error, not a runtime surprise — good — but it is ~120 lines of handler migration nobody estimates correctly the first time.

- **`BitmapImage.PixelWidth` lies when `DecodePixelWidth` is set.** It returns 600. Reading it would ship `600 × 450` under a label that says `Pixels`. The separate header read is mandatory, and `BitmapCacheOption.None` on that read holds a file lock that breaks recycling — the exact operation this app exists to perform.

- **`Priority` never notified.** `ObservableCollection.Move` raises a `Move` collection event that repositions containers without re-evaluating item-level bindings, so today's priority badge goes stale after `▲`/`▼`. Nobody noticed because the badge was one of nine things on a dense chip. In 3a the number is one of four cells and the *only* cue for resolution order. Fixing this is not polish; it is the difference between the caption being true and being decorative.

- **`FilterRule` change-notification and `SkipAutoProps`.** Turning five auto-properties into backed properties moves them from "free" to "must be 100% covered, both branches of each `if`". Budget the tests; the coverage script fails the build, not the PR review.

- **`DisplaySummary` must not be "modernised".** Four tests pin its exact format (`Include | Filename | "IMG_" [Regex, IgnoreCase]`) and one JSON test pins that it is `[JsonIgnore]`. Repurposing it as the row tooltip keeps it alive and honest; rewriting it costs four test edits for no user benefit.

- **`Apply` is enabled with zero rules.** `ApplyFilterRulesCommand.CanExecute` is `DuplicateGroups.Count > 0`; `EnableAll`/`DisableAll` are `FilterRules.Count > 0`. So on a fresh scan with no rules, `Apply` is live and `Enable all` is dead. That looks like a bug and is not — `ApplyFilterRules` early-returns with a status line. Do not "fix" it here; it is SPEC-003 rule 5's documented first bullet.

- **A disabled `Exclude` rule still excludes** under `Select All / Newer / Older` (`ApplyIgnoreRules` reads `Action`, never `IsEnabled`). The row will be dimmed and unticked while the rule is still shaping selection. This is the single most confusing thing on the new panel and it is *pre-existing*. It belongs in the caption tooltip, not in a silent code change.

- **Invalid regex is indistinguishable from a regex that matches nothing.** `MatchesFilter` swallows every failure. A user who types `[unclosed`, sees the row render cleanly, presses `Apply` and gets `0 files selected` has no way to tell which happened. Out of scope to fix, in scope to not make worse — do not add a green "rule added" affirmation that implies validation occurred.

- **Catastrophic backtracking costs up to 1s *per file*, on the UI thread.** With the rules panel now permanently on screen inviting authorship, `Apply` on a 5 000-file result with a pathological pattern freezes the window for over an hour. Unchanged behavior, newly more reachable. Flag it in the ADR (T-012); do not fix it here.

- **The `else if (header == "History")` branch is dead, and it is T-004's to resurrect or bury.** `Header` is a `TextBlock` (`MainWindow.xaml:1715`), `as string` yields `null`, control reaches `else`. T-004's `Tag`-based routing makes the branch live, which *changes* behavior (History would start hiding the Preview pane). T-008 hands over the observation and edits nothing in that method — two tasks rewriting one 35-line method is how a green build ships a wrong window.

- **`UserControl` cannot see `MainWindow.Resources`.** `BoolToVisibility`, `HelpButtonStyle` and every converter currently live in `Window.Resources` (`MainWindow.xaml:14–68`). Anything the panels need must be at `App.xaml` scope. If T-001 has not done that yet, the panels will build and then throw `ResourceReferenceKeyNotFoundException` at runtime — a XAML-load failure with no compile-time signal. Same failure mode for any style key that does not match T-003's published catalogue, which is why every key in this task is stated as a role to be resolved, not a name to be typed.

- **`{Binding DataContext.…, RelativeSource={RelativeSource AncestorType=Window}}`** still resolves from inside a `UserControl` nested in the `Window`, so a lazy copy-paste of the existing chip bindings *works* — right up until a future task hosts a panel outside a `Window`. Use `AncestorType=UserControl`.

- **Uncommitted work in the tree.** 11 modified test files (+1 690 lines) and an untracked `tests/…/ViewModels/` directory from an interrupted coverage run — including `FilterRuleTests.cs`, which this task must also edit. Land or discard that batch **before** starting; merging two independent rewrites of the same test file by hand is how green suites go red for reasons nobody can reconstruct.

## Risks

**1. The coverage gate turns a UI task into a Core-test task, and the estimate hides it.** Converting five `FilterRule` auto-properties (plus `Priority`) to notifying backed properties moves them out of `SkipAutoProps`'s free pass into 100% line **and branch** enforcement — roughly 20 new assertions, plus 8 `ClauseText` combinations, plus 7 `ParsePattern` shapes, plus 7 converter cases, plus rewriting an existing test that asserts the old non-notifying behavior. An engineer who budgets this as "two XAML files" will be two-thirds done when `Check-Coverage.ps1` fails. *Mitigation:* write the Core tests first; they are the only part of this task that is mechanically verifiable at all.

**2. Nothing tests the thing most likely to break.** `Views` is pattern-excluded, `MainViewModel` and the code-behind are `[ExcludeFromCodeCoverage]`. A 100% green coverage report is fully compatible with a panel that throws `ResourceReferenceKeyNotFoundException` on first paint, a metadata row that never collapses, and a media player that no longer stops on ctrl-click. The build is not evidence. *Mitigation:* the manual script in § Acceptance is the actual test plan; run it before committing, not after. **B6** and **P5b** are the two cases a reviewer will skip and a user will hit.

**3. The stop-playback path can be "simplified" back into a bug.** The two subscription routes look redundant — a future reader deletes the event and keeps the `PropertyChanged` hook, and ctrl-click stops stopping playback with no test failing anywhere (`MainViewModel` and both code-behinds are coverage-excluded). *Mitigation:* a comment at `RequestStopPreviewMedia()` naming `SelectionMode="Extended"` and case B6 by name, and the B6 row in the matrix; T-012 records the pattern.

**4. The file-handle regression is silent until it destroys the app's core function.** If the pixel-dimension read uses `BitmapCacheOption.None` (the obvious choice, and what most examples show), the preview holds the file open and recycling that file throws. Preview-then-recycle is the app's most common interaction. *Mitigation:* case **P13** is non-negotiable; run it on a real file, not a fixture.

**5. Deleting 613 lines from a 2 796-line file will take collateral.** The Custom Rules block (1083–1474) and the preview block (2572–2792) are separated by 1 100 lines of unrelated markup, and the file has 78 `<Style>` blocks with only 6 `x:Key`s — implicit `TargetType` styles that may be cascading into the deleted subtrees from an enclosing scope, or out of them. *Mitigation:* delete in two commits, build between, and diff the rendered window against a pre-change screenshot; do not trust a clean compile.

**6. The caption becomes a promise the code can still break.** `first match wins` is now on screen permanently. The `break` at the end of the inner `foreach` is what makes it true, and nothing tests that loop. A future refactor removing the `break` (to make `Exclude` "always win" — which is what the *old help text* claimed and what a well-meaning reader might "restore") silently makes the visible caption a lie again, the exact failure this task exists to end. *Mitigation:* T-012 must name the loop as caption-load-bearing; add a comment at the `break` citing the caption const by name so a grep from either end finds the other.

**7. Fork 1 answered as (A) adds hover-only affordances.** Reorder and remove become invisible at rest — IDE-idiomatic and 3a-faithful, but a discoverability regression against today's always-visible chip buttons, the kind noticed a week later as "the buttons disappeared". *Mitigation:* the `ContextMenu` is the always-available path; T-011 must give the row keyboard equivalents, not just mouse hover.

**8. Scope bleed toward turn 4.** A "Never mark" row is the most natural place in the whole app to reach for red, and a tag chip the most natural place to reach for a tint. Both are turn-4 ideas; the moment one lands the task is mis-targeted. *Mitigation:* acceptance check **X2** catches the mechanical form; review catches the rest.

**9. Boundary regression — someone re-adds the host.** The deleted `RightToolWindowStack` is the *obvious* thing to write when you sit down to build two panels that stack. If it comes back, the column gets two sets of rows and two splitters, or T-005's `ApplyPaneLayout` drives a grid nothing is in. *Mitigation:* acceptance checks **X3** and the four boundary-compliance greps run before anything else; state the ownership line in the PR description, not just the spec.

Accepted (T-005 owns the mechanism), small, and real. *Mitigation:* verify **P5b** on a populated list; raise a persistent reopen affordance to T-005 if user testing (T-013) flags it. Do **not** solve it locally by reintroducing a header stub — that is the contradiction the panel blocked on.

**11. SPEC-005 rule 12 and SPEC-010's popup count are each edited by two tasks.** Rule 12's two sentences are disjoint by agreement (T-005 = host/collapse, T-008 = renderers), so a collision is textual, not semantic — but only if both tasks honour the split. ## Open decision

Two real forks the artboard does not settle, plus four boundary reconciliations forced by the panel review. The reconciliations are settled here (they are not forks — they are cases where this task was wrong about who owns what); the two forks still need an answer before build.

**RECONCILIATION 1 — T-005 owns the right stack's rows and its horizontal splitter. This task owns neither.**
The earlier draft built `Views/Panels/RightToolWindowStack.xaml` with its own three-row grid, its own `GridSplitter`, and its own `IsPreviewVisible`→row-height code-behind. T-005 already declares exactly that inside `DuplicatesScreenView.xaml` (`PreviewRow` / `PreviewSplitRow` / `RulesRow`, the `PreviewSplitter`, and `ApplyPaneLayout`), and its AC-02 asserts three `GridSplitter`s in its own file. The artboard agrees with T-005: there are **three** splitters, not two — body `260px 1px 1fr 1px 360px` gives two vertical, and the right stack's `1fr 1px 1fr` gives the third. The earlier Interfaces claim "T-005 owns the two vertical splitters; T-008 owns the horizontal one" was wrong about both the artboard and T-005's Detail. **`RightToolWindowStack.xaml` is deleted from this task.** T-008 authors two `UserControl`s and drops them into the cells T-005 publishes. If T-005's fork A1 gives the right stack a third pane, T-008 is unaffected — it fills the two cells T-005 designates for Preview and Rules, by T-005's published row names, whatever the total pane count.

**RECONCILIATION 2 — collapse is to zero, not to a 30px header stub.**
The earlier draft collapsed the Preview row to `Height="30"` so the header, `Auto ✓` and `✕` survived and the pane could be reopened in place. T-005 collapses it to `0` and hides the splitter, taking the header with it. Both cannot ship, and T-005 owns the mechanism, so **T-005's collapse-to-zero wins.** The consequence has to be stated rather than wished away: once collapsed, this surface offers no in-place reopen. The reopen path is the results editor's per-copy `Preview` verb (**T-007**), which routes to `PreviewFile()` — and SPEC-005 rule 10 already guarantees `PreviewFile` sets `IsPreviewVisible = true` on *every* branch, `unsupported` included. That is an existing, always-visible, non-hover affordance, and it is the single interface obligation this reconciliation places on T-007. It is recorded as a residual risk (a user who presses `✕` with an empty result list has nothing to click until the next scan) and handed to T-005 as the grid owner if it wants a persistent reopen strip; T-008 does not invent one.

**RECONCILIATION 3 — T-004 owns `TabControl_SelectionChanged`, whole.**
The earlier draft deleted the `else if (header == "History")` branch as unreachable and deleted the `_savedPreviewVisible` save/restore. T-004 rewrites the same method around `Tag`-based routing, which makes that branch *live*, and keeps the field and its restore. **T-008 makes no edit to `TabControl_SelectionChanged` at all.** The `_savedPreviewVisible` mechanism keeps working unchanged under the new layout, because `IsPreviewVisible` still means exactly "the Preview pane is open" — only what the boolean *drives* changed, and that is T-005's code. The dead-branch observation is handed to T-004 as an input, not acted on here.

**RECONCILIATION 4 — style and brush keys are consumed from the published catalogues, never coined here.**
The earlier draft named keys (`ToolWindowHeaderStyle`, `TagChipStyle`, `TagToggleStyle`, `Brush.TextFaint`, `Brush.Neutral700`) that diverge from T-001's and T-003's actual namespaces, and one of them — the 6%-alpha row hairline — is not in T-001's token set at all. Everything in § Interfaces is therefore stated as a **role**, and the build step is: resolve each role against T-003's published style catalogue and T-001's published token list before writing a line of XAML. A role with no published counterpart is raised to that task, not authored locally. The one genuinely new token this surface needs is the 6%-alpha rule-row hairline (3a: `color-mix(in srgb, var(--color-text) 6%, transparent)`); it is a request to T-001, with a documented fallback (reuse the standard divider token at full strength and accept the heavier rule) so T-008 is not blocked on it.

**FORK 1 — Where do the rule-row editing affordances go?** *(unchanged; still open)*
Today every rule chip (`MainWindow.xaml:1250–1472`) is fully editable inline: Action ComboBox, Target ComboBox, editable Pattern TextBox, `.*` toggle, `Aa` toggle, ▲/▼ reorder, ✕ remove. 3a's rule row has **four cells only** — checkbox, priority number, sentence, flag tags. No reorder arrows, no remove, no inline editors. Shipping the artboard literally is a functional regression, and reordering is not cosmetic: priority order **is** the first-match-wins resolution order (SPEC-003 rules 2 and 5), so removing ▲/▼ removes the user's only control over which rule wins.
- **(A) Hover-revealed row actions + context menu** *(recommended)* — the row keeps its four artboard cells at rest; on `IsMouseOver` / `IsKeyboardFocusWithin` a right-aligned `▲ ▼ ✕` group fades in over the tag cell (a `Grid` overlay, so the resting layout is byte-identical to 3a). A `ContextMenu` carries `Edit rule…`, `Move up`, `Move down`, `Remove rule`, `Remove all rules` (the otherwise-homeless `ClearAllRulesCommand`). Editing opens the compose row pre-filled in "edit" mode. Cost: one `ContextMenu`, one overlay `StackPanel`, one VM edit-mode flag. Keyboard: `Alt+↑` / `Alt+↓` / `Delete` on the focused row (T-011 verifies).
- **(B) Drag-to-reorder + ✕ only** — closer to 3a visually, but WPF has no built-in `ItemsControl` drag-reorder; it is ~150 lines of adorner/drop-index code in the `Views` namespace, i.e. wholly untestable under this repo's gate, and it strands `Edit`.
- **(C) Ship 3a literally, move all editing to a modal `Rules…` dialog** — cleanest row, worst ergonomics; every reorder becomes a dialog round-trip on a screen whose whole point is one-glance rule triage.
Recommendation **(A)**. Detail below is written against (A); under (B) or (C) the row template and the § Interfaces export list change and nothing else does.

**FORK 2 — How is regex expressed in the compose row?** *(unchanged; still open)*
3a's compose row is `[Mark ▾] [name ▾] [input placeholder "text or /regex/"] [Add]` — no `.*`, no `Aa`. The placeholder asserts slash-wrapping selects regex. But the rule rows show `Aa` on row 1 and `.*` on row 2, so both flags still exist as rule state, and nothing in 3a offers any way to set `IgnoreCase`.
- **(A1) Keep both toggles, and ship the slash shorthand** *(recommended)* — compose row is `[action ▾] [target ▾] [pattern] [.*] [Aa] [Add]`, the two flags as 22px compact toggles between the box and Add. `FilterRuleVocabulary.ParsePattern(string)` in Core strips a `/…/` wrapper and returns `isRegex: true`, which `AddFilterRule` applies **before** honouring the `.*` toggle. The placeholder is then literally true. Behavior change → SPEC-003 rule 1 gains the shorthand; the parser is in Core, so it is unit-tested.
- **(A2) Keep both toggles, change the placeholder to `pattern`** — zero behavior change, zero new Core code, but the artboard string is abandoned.
- **(B) Slash shorthand only, drop both toggles** — matches 3a exactly and loses the only affordance for `IgnoreCase` (default `true`), so case-sensitive rules become unauthorable. Regression; not recommended.
Recommendation **(A1)**. Detail is written against (A1); under (A2) delete `ParsePattern` and its tests and set the placeholder to `pattern`.

**Non-forks, settled from the artboard (recorded so nobody re-litigates them):** the planner's hint places `Enable all` / `Disable all` in the Rules *header*; the 3a markup puts `+ Rule` and `Apply` in the 30px header and `Enable all` / `Disable all` in a separate 32px toolbar row with `first match wins` right-aligned — the artboard wins, and it matches turn 3's stated convention ("each panel gets one toolbar row for its controls"). The hint orders the compose row `[pattern] [Mark ▾] [name ▾] [Add]`; the markup orders it `[Mark ▾] [name ▾] [pattern] [Add]` — the markup wins.
