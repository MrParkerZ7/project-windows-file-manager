## Concept

Today the app's top edge is a **docked full-width "profile bar"** (`MainWindow.xaml:71`) holding a status string, a `Profile:` label, a `ComboBox`, four verb buttons and a `?` popup — followed by a stock `TabControl` whose three tabs read `Folder`, `Duplication` and a hand-decorated gold `🕘 History`. It is a settings strip wearing the costume of chrome.

3a replaces that with the **IDE frame**: a 34px identity bar (app name · profile switcher · window controls) and, under it, a 38px **editor tab strip** where the active tab carries a 2px accent underline sitting *on* the strip's hairline, and the strip's right end holds the primary action plus a quiet caption reporting the last run. Everything that is configuration (create/clone/rename/delete a profile, the help for it) moves *inside* the profile switcher's dropdown, which is the IntelliJ "run-configuration selector" idiom the whole exploration is built on.

That reframing is not cosmetic. It changes three things the code currently depends on:
1. **Tab identity.** Tabs are renamed and reordered to `Duplicates · Folders · History`, so `Duplicates` becomes tab index 0 and the startup tab. `MainWindow.xaml.cs:190` routes panel visibility off `Header as string`; that string is about to change, and the History tab's header stops being a `TextBlock` and becomes a plain string — which makes a branch that has **never executed** start executing (`docs/modules/ui.md` gotcha 18; pinned as an edge case in SPEC-005:140 and SPEC-006:127).
2. **Scan moves out of a tab and onto the frame** — with it, the `Files scanned: N` live readout, which today is the *only* progress signal a duplicate scan produces (`ScanAsync` never calls `BeginBusy`, so the status bar's progress bar and count stay hidden for the whole scan). Today's two buttons (`Scan for Duplicates` at `MainWindow.xaml:727` and the visibility-bound `Cancel` at `:732`) collapse into the strip's single button.
3. **The strip needs a fact the app does not record.** "last scan 10:12 · 4.2 s" needs a wall-clock completion time. `ScanAnalytics.Duration` exists; nothing anywhere stores *when* a scan finished.

This task builds the frame those three consequences hang off, and it is the container T-005…T-009 render inside — which is why it is P1 and why getting the routing contract right here saves every later task from re-deriving it.

## Design

**Where the code lands.**

```
src/WindowsFileManager/
  App.xaml                          ← merge Tokens (T-001) → Components (T-003) → Shell (this task)
  Themes/Shell.xaml                 ← NEW. Shell-only styles + the converter instance. NO tokens, NO metrics.
  Views/MainWindow.xaml             ← the DockPanel head is replaced; the TabControl is restyled.
  Views/MainWindow.xaml.cs          ← tab routing rewritten off Tag; 3 window-button handlers; StateChanged.
  Helpers/Converters.cs             ← + ScanCaptionConverter
  Helpers/ShellChrome.cs            ← NEW. one attached DP that feeds the strip's right slot.
  ViewModels/MainViewModel.cs       ← + LastScanCompletedAt, LastScanDuration (set on the success path only)
tests/WindowsFileManager.Tests/
  Helpers/ScanCaptionConverterTests.cs      ← NEW, must be 100%
  Helpers/ShellChromeTests.cs               ← NEW, must be 100%
  Views/ResourceKeyIntegrityTests.cs        ← NEW, pure-XML, plugs the StaticResource/DynamicResource blind spot
```

`.xaml` under a `UseWPF` SDK project is auto-globbed as `Page`; **no csproj edit is needed** for `Themes/Shell.xaml`.

**The frame, top to bottom.**

```
Window  (Margin 0 — the current DockPanel Margin="4" goes away; chrome must be flush)
└ Border  x:Name="ShellRoot"   Background={DynamicResource <T-001 page brush>}
  └ DockPanel
    ├ Dock=Top  TitleBar        34px  Background={<T-001 surface brush>}  hairline bottom
    │   ├ "Folder File Control"   <T-001 heading font> 14 SemiBold
    │   ├ ProfileSwitcher         ToggleButton + Popup   → "Photos cleanup ▾"
    │   └ (Option A) — ▢ ✕        right, WindowChrome.IsHitTestVisibleInChrome=True
    ├ Dock=Bottom  (T-009's status bar — NOT this task; leave the existing bottom Border in place)
    └ TabControl  Style=Broadsheet.Style.TabControl.EditorStrip
        strip 38px:  [ Duplicates | Folders | History ] ......... [ Scan ] [caption]
        content:     whatever T-002 left behind, untouched
```

**Why the TabControl is retemplated rather than overlaid.** The Scan cluster must live on the *same* 38px strip as the tab headers and must never be overlapped by a header. Overlaying a right-aligned `StackPanel` in a shared `Grid` cell puts the cluster above the `TabPanel` in z-order and lets a wide header slide under it. So the `TabControl` template gets a **two-column strip Grid** — column 0 `*` holds `<TabPanel IsItemsHost="True"/>`, column 1 `Auto` holds a `ContentPresenter` whose `Content` comes from a new attached property. That is one small, fully-testable DP against a whole class of layout bug.

**Why the profile verbs move into a Popup.** 3a's title bar shows exactly one profile affordance. The four verbs, the operation status and the `PROFILES` help popup have to go *somewhere* and the artboard's dropdown caret is the invitation. A `ToggleButton` + `Popup` (rather than a `ComboBox`) is the WPF idiom that can host a switch-list *and* a verb footer in one dropdown; a `ComboBox` can only do it by fighting its own `ItemsPanel`. The list items bind `SwitchProfileCommand` with the name as `CommandParameter` rather than driving `ActiveProfileName`'s two-way setter — the command already carries `CanExecute = p is string name && name != ActiveProfileName (OrdinalIgnoreCase)`, so the currently-active row renders disabled for free, which is the affordance the old ComboBox faked with a selection highlight.

**Why the caption's formatting is a converter and not a VM string.** `MainViewModel` is `[ExcludeFromCodeCoverage]`; a `LastScanCaption` string property computed in the VM would ship completely untested. Splitting it — the VM only reads the clock (`DateTime.Now`, one line inside the already-excluded class), a converter in `WindowsFileManager.Helpers` does all the formatting — puts every branch of the interesting half **inside** the coverage gate, where the CI script already enforces 100%. Same reasoning ADR-002 gives for `PercentToWidthConverter` living in `Helpers` while its panel wiring lives in the VM.

**Token discipline — one namespace, one owner.** T-001 owns colours, fonts, weights and metrics; T-003 owns component styles; T-004 owns *shell-shaped* styles only (the editor tab, the strip template, the window button, the profile switcher) and publishes them into the same `Broadsheet.*` namespace. This task therefore adds **zero** hex literals, **zero** font-family literals, and **zero** size resources. Two resolution modes, deliberately different:
- **Brushes / fonts / weights → `DynamicResource`.** They resolve at render time, they survive a later theme-dictionary swap, and a miss degrades rather than crashes.
- **Metrics used for layout (`Broadsheet.Metric.TitleBarHeight`, `Broadsheet.Metric.TabStripHeight`) → `StaticResource`.** A missing metric is a *structural* failure — the strip silently sizes to content and 3a's 34/38 rhythm is gone with no error. `StaticResource` throws at window construction instead, which is the behaviour you want for a load-bearing number. This is safe because `App.xaml` merges `Tokens.xaml` **before** `Shell.xaml` (D-1), and `StaticResource` lookup from a merged dictionary walks the already-merged siblings in order.
The exact Broadsheet values, for T-001 to carry: bg `#F3F2F2`, surface `#EAE9E9`, text `#201E1D`, accent `#0088B0`, accent-600 `#1186AC`, accent-700 `#006786`, neutral-100 `#F8F4F4`, neutral-600 `#7D7979`, divider = 16% of `#201E1D` → **`#29201E1D`** in WPF ARGB (0.16 × 255 = 41 = 0x29). Those values are T-001's to declare; T-004 never writes one.

## Detail

### D-1 · `App.xaml` — the dictionary chain

`App.xaml` is 314 bytes and declares nothing. Replace `<Application.Resources>` with a merged chain, **in this order** (later wins on key collision, and earlier entries are what `StaticResource` in a later dictionary can see):

```xml
<Application.Resources>
  <ResourceDictionary>
    <ResourceDictionary.MergedDictionaries>
      <ResourceDictionary Source="pack://application:,,,/Themes/Tokens.xaml" />      <!-- T-001 -->
      <ResourceDictionary Source="pack://application:,,,/Themes/Components.xaml" />  <!-- T-003 -->
      <ResourceDictionary Source="pack://application:,,,/Themes/Shell.xaml" />       <!-- this task -->
    </ResourceDictionary.MergedDictionaries>
  </ResourceDictionary>
</Application.Resources>
```

The order is now **load-bearing, not cosmetic**: `Shell.xaml` resolves T-001's two metrics with `StaticResource`, which only sees dictionaries merged before it. Tokens → Components → Shell is a hard requirement, asserted by `ResourceKeyIntegrityTests` (case 22).

`Shell.xaml` declares **exactly four styles and one converter instance**, all in the `Broadsheet.*` namespace:

`Broadsheet.Style.Tab.Editor` · `Broadsheet.Style.TabControl.EditorStrip` · `Broadsheet.Style.WindowButton` (Option A only) · `Broadsheet.Style.ProfileSwitcher` · `Broadsheet.Converter.ScanCaption`.

### D-5 · `Helpers/ShellChrome.cs` — the strip's right slot

```csharp
namespace WindowsFileManager.Helpers;

/// <summary>Attached properties for the IDE-frame shell chrome.</summary>
public static class ShellChrome
{
    /// <summary>Identifies the StripRightContent attached property.</summary>
    public static readonly DependencyProperty StripRightContentProperty =
        DependencyProperty.RegisterAttached(
            "StripRightContent", typeof(object), typeof(ShellChrome),
            new PropertyMetadata(null));

    /// <summary>Gets the content rendered at the right end of the tab strip.</summary>
    public static object? GetStripRightContent(DependencyObject element)
    {
        ArgumentNullException.ThrowIfNull(element);
        return element.GetValue(StripRightContentProperty);
    }

    /// <summary>Sets the content rendered at the right end of the tab strip.</summary>
    public static void SetStripRightContent(DependencyObject element, object? value)
    {
        ArgumentNullException.ThrowIfNull(element);
        element.SetValue(StripRightContentProperty, value);
    }
}
```

`ArgumentNullException.ThrowIfNull` is required — `CA1062` fires on a public method dereferencing a reference parameter, and `CodeAnalysisTreatWarningsAsErrors` turns that into a build failure. Each guard is a **branch**, so both the null and non-null paths need a test or the 100% branch gate fails. Do **not** add `[ExcludeFromCodeCoverage]` here: unlike `FormattedTextBehavior` / `TextBoxEnterKeyBehavior` (which manipulate live visual state) this class is pure DP plumbing and is trivially testable.

### D-7 · The Scan cluster — content for the right slot

❗ **Property-value precedence is the whole design of this block.** In WPF a local value (an attribute set directly on the element) outranks a style `Setter` *and* a style `Trigger` setter. An earlier draft set `Content="Scan"` and `Command="{Binding ScanCommand}"` as attributes and then tried to override them from a `DataTrigger` — the button would have stayed "Scan"/`ScanCommand` forever and **cancellation would have been silently deleted**. Both properties therefore live **only** in `Setter`s. Equally: an element may not carry a `Style="…"` attribute *and* a `<Button.Style>` child — that is "Style property set more than once", a `XamlParseException`. Only the child element is used, with `BasedOn`.

Set on the `TabControl` in `MainWindow.xaml`:

```xml

    <StackPanel Orientation="Horizontal" VerticalAlignment="Center">

      <!-- NO Style= attribute, NO Content=, NO Command= attribute. All three are Setters. -->
      <Button x:Name="ScanButton" MinHeight="28" Padding="14,0" FontSize="13">
        <Button.Style>
          <Style TargetType="Button" BasedOn="{StaticResource <T-003 primary button key>}">
            <Setter Property="Content" Value="Scan" />
            <Setter Property="Command" Value="{Binding ScanCommand}" />

Delete either without a replacement and you have shipped a regression. The in-tab `SCAN & DISPLAY OPTIONS` help `ToggleButton` at `:741` stays where it is — it is T-005's surface, not the strip's.

`ScanCommand`'s `CanExecute` is `!IsScanning && TargetPaths.Any(t => t.IsEnabled)`; `RelayCommand.CanExecuteChanged` forwards to `CommandManager.RequerySuggested`, so the disabled state re-queries on its own — no wiring, no `RaiseCanExecuteChanged` call needed.

### D-8 · `ScanCaptionConverter` — appended to `Helpers/Converters.cs`

```csharp
/// <summary>
/// Formats the tab strip's last-scan caption: "last scan 10:12 · 4.2 s".
/// values[0] = DateTime? completion time, values[1] = TimeSpan duration.
/// </summary>
public class ScanCaptionConverter : IMultiValueConverter
{
    /// <inheritdoc/>
    public object Convert(object[] values, Type targetType, object parameter, CultureInfo culture)
    {
        if (values is null || values.Length < 2
            || values[0] is not DateTime completedAt
            || values[1] is not TimeSpan duration)
        {
            return string.Empty;
        }

        var provider = culture ?? CultureInfo.CurrentCulture;
        var seconds = Math.Max(0d, duration.TotalSeconds);

        return string.Concat(
            "last scan ",
            completedAt.ToString("HH\\:mm", provider),
            " · ",
            seconds.ToString("F1", provider),
            " s");
    }

    /// <inheritdoc/>
    public object[] ConvertBack(object value, Type[] targetTypes, object parameter, CultureInfo culture)
        => throw new NotSupportedException();
}
```

- `values[0] is not DateTime` is the single guard that catches **all three** empty cases — a `null` from `DateTime?`, `DependencyProperty.UnsetValue` during template construction, and a wrong-typed binding. It returns `string.Empty`, which renders the caption invisible before the first scan.
- The colon in `"HH\\:mm"` is **escaped**, making it a literal — the caption reads `10:12` on every culture instead of picking up a locale time separator.
- `provider` is threaded into both `ToString` calls because `CA1305` (specify `IFormatProvider`) is an error here.
- `Math.Max(0d, …)` clamps a negative `TimeSpan` — reachable if a system clock adjustment lands inside a scan — and is its own branch.
- Registered once, in `Themes/Shell.xaml`: `<helpers:ScanCaptionConverter x:Key="Broadsheet.Converter.ScanCaption" />`.

### D-9 · `MainViewModel` — the only two new members

## Edge cases

**Local values beat style triggers.** WPF's property-value precedence puts a local attribute above every style `Setter` and every style `Trigger` setter. Any state-dependent property — the Scan button's `Content`/`Command`, the caption's `Text`, the maximize button's glyph — must be set **only** through `Setter`s inside the style. Set it as an attribute and the trigger fires, changes nothing visible, and the failure is silent: no exception, no warning, no analyzer, no test unless someone actually starts a scan. Case 41 exists for exactly this. Related and equally silent-until-runtime: `Style="…"` as an attribute *plus* a `<Button.Style>` child is "Style property set more than once" — a `XamlParseException` at window construction.

**Two keys for one value is invisible drift.** A duplicate-key test only sees collisions *within* a dictionary; `Size.TabStripHeight` in `Shell.xaml` and `Broadsheet.Metric.TabStripHeight` in `Tokens.xaml` are two different keys and no test fires. Six months later one is 38 and the other is 40 and the strip is off by two with a green build. The rule is absolute: T-004 declares no metric, brush, font or button-style key. Case 23 enforces it.

**A role-equivalent key name is the same drift, one layer up.** `Brush.Bg` is not `Broadsheet.Brush.Bg` — as a `DynamicResource` it resolves to nothing, degrades to a WPF default, and the build stays green. That is why D-2 is a *pre-flight copy* from the real dictionaries, not a retype from this spec, and why case 20 walks every referenced key.

**The dead branch that comes alive.** History's `IsHistoryActive = true` path in `TabControl_SelectionChanged` has never run in production — `Header as string` is `null` for a `TextBlock` header. `Tag`-based routing fires it for the first time. `IsHistoryActive` has **no consumer in XAML** today (grep: only `IsFolderControlActive` is bound, at `MainWindow.xaml:2012`), so the visible change is narrower than it looks: the preview and analytics panels now hide on History. It is deliberately revived, not deleted — see D-15's ownership note; do not let a later task re-remove it as unreachable.

**The startup tab moves and the user sees it.** Duplicates first means `MainWindow_Loaded` stops force-hiding, so on a default profile (`IsAutoPreview = true`, `IsAnalyticsVisible = true` by field initialiser) both side panels are visible at launch where they used to be hidden. Intended; must be in SPEC-005, SPEC-006 and SPEC-009 rule 13 in the same commit.

**Scan produces no `IsBusy`.** `ScanAsync` never calls `BeginBusy` — verified at `MainViewModel.cs:2259–2325`. The status bar's `ProgressBar`, `BusyCountText` and `BusyEta` are dead for the whole duplicate scan. The in-tab `Files scanned: N` TextBlock is the only signal; if it is deleted without landing in the caption slot, a long scan looks frozen.

**Cancelled and failed scans keep the old caption.** Deliberately unlike `Analytics`, which SPEC-006 nulls at scan start. "last scan" means the last one that *finished*.

**Nothing is persisted, so the caption is empty after every restart** — consistent with SPEC-006's "analytics are not persisted, not exported, not comparable across runs" non-goal.

**A `DynamicResource` typo fails silently.** No exception, no warning, no build error — the control just renders with the WPF default and the Broadsheet look quietly degrades. `ResourceKeyIntegrityTests` (case 20) exists specifically for this; without it the only detection is a human noticing a wrong grey.

**A `StaticResource` typo throws at window construction**, not at compile time — a `XamlParseException` the moment `MainWindow` is created. Case 19. This is why the two layout metrics use `StaticResource` deliberately: a missing height is structural and should crash, not silently collapse the strip to content height.

**Merge order is load-bearing, not cosmetic.** `StaticResource` in `Shell.xaml` can only see dictionaries merged *before* it. Put `Shell.xaml` ahead of `Tokens.xaml` in `App.xaml` and the metric lookups fail at startup. Case 22.

**A missing embedded heading font also fails silently** — WPF falls back to the default UI font with no diagnostic. Case 21.

**Attached property in a `ControlTemplate` needs the parenthesised path.** `TemplateBinding helpers:ShellChrome.StripRightContent` does not compile; only `{Binding RelativeSource={RelativeSource TemplatedParent}, Path=(helpers:ShellChrome.StripRightContent)}` works.

**`TabPanel` must keep `IsItemsHost="True"`** in the retemplated `TabControl`, or the headers vanish with no error.

**`WindowChrome.IsHitTestVisibleInChrome` (Option A).** Any interactive element inside `CaptionHeight` is swallowed by the drag region without it. The profile switcher and all three window buttons need it. This is the most likely way the change ships looking broken while being perfectly valid XAML.

**Maximize clip (Option A).** `WindowStyle="None"` + non-zero `ResizeBorderThickness` overhangs the work area; D-12's `StateChanged` padding is the mitigation. Verify on both a primary and a secondary monitor.

**Snap Layouts is lost under Option A** and is not restored here — that needs a `WM_NCHITTEST` hook returning `HTMAXBUTTON`, which is out of scope. Record it.

**High contrast under Option A**: the app-drawn caption stops following the system theme. Named, handed to T-011.

**Zero `AutomationProperties` exist in the repo today** and there are no `InputBindings`/`KeyBinding` anywhere — the shell has no accelerators to preserve, but it also has no accessibility baseline to inherit. T-004 must not add unnamed icon-only buttons to T-011's pile.

**Culture.** The app is English-only with hardcoded strings, but the converter threads the binding's `CultureInfo` through both `ToString` calls (CA1305 forces a provider anyway). On `de-DE` the caption reads `4,2 s`; the time separator stays a literal `:` because `"HH\\:mm"` escapes it. Both pinned.

**`F1` midpoint rounding is deliberately not pinned** — .NET's formatting midpoint behaviour is not a contract worth asserting. Tests pin `4.24 → "4.2"` and `4.26 → "4.3"` only.

**`ProfileNames` mutates while the popup is open** (a rename or delete from inside the popup). `ObservableCollection` + `ItemsControl` handles it; verify the popup does not close mid-verb and that `StaysOpen="False"` does not dismiss it when `ProfileNameDialog` takes focus. If the modal dismisses the popup, the verb still runs correctly — accept that, do not fight it.

**Long profile names** must ellipsize in the switcher rather than grow the 34px bar (case 27).

**The working tree is already dirty** — 11 modified test files (+1,690 lines) plus `Helpers/FormattedTextBehaviorTests.cs` and `ViewModels/` untracked, from an interrupted coverage run in a closed session. Deal with those in their own commit **before** starting, or this task's commit becomes unreviewable and the spec-sync rule becomes unverifiable.

## Risks

**R1 — Custom chrome regresses window management, and nothing catches it (HIGH, Option A only).** No UI tests, no visual-regression harness. Snap Layouts, high-contrast, DWM shadow, maximize clipping and per-monitor DPI are all reachable only by hand. *Mitigation:* cases 38–43 are an explicit manual gate; Option B is a one-attribute retreat that keeps every OS affordance; the two losses that are **not** mitigated (Snap Layouts, high-contrast caption) are written down and handed to T-011 rather than discovered later.

**R2 — Window geometry stops persisting (HIGH, Option A only).** SPEC-009 rule 12 says `SaveWindowState` has exactly one caller, `MainWindow_Closing`. If custom chrome ever bypasses `Window.Closing`, geometry silently stops saving and the failure is invisible until the next launch. *Mitigation:* the close button uses `SystemCommands.CloseWindow(this)`, which routes through `Closing`; case 40 verifies `settings.json` after an ✕ close. Do not substitute `Application.Current.Shutdown()`.

**R3 — Silent design-token failure (HIGH).** A `DynamicResource` miss, a role-equivalent key name, or a non-embedded heading font produces no error at all — the frame just looks subtly wrong, and nobody can say which of the 70 retired colours regressed. *Mitigation:* D-2's literal-copy pre-flight plus `ResourceKeyIntegrityTests` (cases 19–23), which turn all five failure modes — missing static key, missing dynamic key, unembedded font, wrong merge order, re-declared token — into a red test.

**R4 — The History branch waking up breaks something downstream (MEDIUM).** A branch that has never executed is a branch nobody has tested. `IsHistoryActive` has no XAML consumer today, which bounds the blast radius, but the panel-visibility side effects on History are genuinely new. *Mitigation:* case 28 exercises all three tabs both ways; SPEC-005 and SPEC-006 both record the new behaviour so the next reader is not surprised.

**R5 — Losing cancel or losing scan progress (MEDIUM).** The artboard shows one button and one caption; a literal reading deletes both `Cancel` and `Files scanned: N`. Because `ScanAsync` never raises `IsBusy`, the status bar cannot cover for the second one. *Mitigation:* D-7's `Setter`-based trigger pair; acceptance checkboxes; cases 31–33 and 41.

**R6 — Analyzer wall on new code (MEDIUM).** `TreatWarningsAsErrors` + `CodeAnalysisTreatWarningsAsErrors` + StyleCop means CA1062 (null-guard), CA1305 (format provider), SA1600 (XML docs on every public member), SA1601 (partial docs) and file-header/ordering rules all fail the build. *Mitigation:* D-5 and D-8 are written analyzer-clean; run `dotnet build -c Release` before writing tests, not after.

**R7 — 100% coverage on new `Helpers` code (MEDIUM).** `WindowsFileManager.Helpers*` is in the runsettings `Include` and nothing excludes it. Every `ArgumentNullException.ThrowIfNull` and every `is not` guard is a branch. Miss one and CI fails at the coverage script, not at compile. *Mitigation:* the matrix's 14 unit cases were derived from the branch list, not from happy paths.

**R8 — Colour creep (MEDIUM).** T-001 retires 70 hardcoded hexes; a rebuilt title bar is the easiest place to reintroduce one "just for the hover state". *Mitigation:* the `git diff` no-new-hex acceptance check.

**R9 — Header-string routing returns (LOW but recurring).** The bug this task fixes is exactly "code branched on a display string, then the display string changed." *Mitigation:* `Tag` is the contract, stated in §Interfaces so T-002/T-005 inherit it; the removed `Header ==` comparisons are grep-verifiable at review.

**R10 — Merge collision with T-002 (LOW, now sequenced away).** Both rewrite `MainWindow.xaml`. *Mitigation:* T-002 is a hard dependency and lands first; T-004 then touches only the head (lines ~71–113), the `TabControl` element, three `TabItem` opening tags and one code-behind method.

**R11 — The dirty working tree contaminates the commit (LOW, certain if ignored).** +1,690 uncommitted test lines are sitting there right now. The spec-sync rule is only auditable if the commit contains this task and nothing else. *Mitigation:* first checklist item.

**R12 — Property-value precedence silently deletes cancellation (HIGH, and the exact defect the first draft shipped).** A local `Content="Scan"` / `Command="{Binding ScanCommand}"` attribute outranks the `IsScanning` `DataTrigger`; the button never becomes Cancel, and because the old in-tab Cancel button is deleted in the same change, **an in-flight scan becomes uncancellable**. Nothing catches it: it compiles, no analyzer fires, no unit test touches XAML, and a reviewer skimming the block sees a trigger that looks correct. The same trap applies to the caption's `Text` and the maximize glyph. *Mitigation:* D-7 sets all state-dependent properties through `Setter`s only, forbids a `Style=` attribute beside `<Button.Style>`, and case 41 is a mandatory manual check that actually starts and cancels a scan.

**R13 — Two tasks editing one method (MEDIUM, resolved by ownership, not by ordering).** `TabControl_SelectionChanged` was claimed by both T-004 (Tag routing, live History branch) and T-008 (delete the branch, drop the `_saved*` fields). Whichever landed second would silently revert the other, and because the method has no test, CI would stay green either way. *Mitigation:* D-15 assigns the method, both fields and the branch to T-004 with a single final shape, grounded in 3a's artboard (the right stack belongs to the Duplicates editor, not the shell); T-008 cites and does not edit; an acceptance checkbox asks the reviewer to confirm T-008's branch contains no `MainWindow.xaml.cs` change; any genuine need to change the shape returns as an amendment to this spec.

## Open decision

ONE fork, and only the user can settle it: **does the app take over the Windows title bar?**

3a's artboard puts the app name, the profile switcher AND the window controls (— ▢ ✕) on one 34px strip. Read literally that is **custom chrome** — the app draws the caption itself. That is not a styling choice, it is a platform-behaviour choice with real cost, and this repo has zero UI tests to catch what breaks.

**Option A — custom chrome (RECOMMENDED, and what the rest of this spec is written against).**
`WindowStyle="None"` + `<WindowChrome CaptionHeight="34" ResizeBorderThickness="6" GlassFrameThickness="0" UseAeroCaptionButtons="False" CornerRadius="0" />`, with three app-drawn buttons calling `SystemCommands.MinimizeWindow/MaximizeWindow/RestoreWindow/CloseWindow`.
- Gains: pixel-exact 3a. One 34px strip, no doubled chrome above it.
- Costs, all real and all named here so nobody discovers them later: Windows 11 **Snap Layouts** (the flyout on hover-over-maximize) is lost unless a `WM_NCHITTEST` hook returns `HTMAXBUTTON` over the maximize button — this task does **not** add that hook; the **high-contrast** system theme no longer repaints the caption (the app-drawn strip keeps Broadsheet colours); the DWM drop shadow is gone at `GlassFrameThickness="0"`; and maximizing can clip by the resize-border width, which rule D-12 below mitigates.

**Option B — keep the native title bar (fallback).**
`WindowStyle="SingleBorderWindow"` stays. The 34px strip sits *below* the OS caption and carries the app name + profile switcher only; the — ▢ ✕ cluster is **not** built (the OS supplies it). Snap Layouts, high-contrast caption, and the DWM shadow all keep working untouched, and rules D-11, D-12, D-13 and the whole `Broadsheet.Style.WindowButton` resource drop out of scope.
- Cost: the window is 34px taller in chrome than 3a shows, and the artboard's window-control row is not reproduced.

Everything else in this spec — the tab strip, the profile switcher popup, the Scan cluster, the caption, the routing fix, the converter, every spec edit — is **identical under both options**. Only §Detail D-11/D-12/D-13 and the `Broadsheet.Style.WindowButton` resource differ. Start on the shared 90% while the answer comes back; do not guess.

Four smaller calls already made here (recorded so they are auditable, not re-litigated):

- **Scan is global, and does not switch tabs.** 3a shows Scan on the strip, which is above all three tabs. Pressing it while Folders or History is selected runs the scan and leaves the tab where it is. Auto-switching to Duplicates is invented behaviour and is listed in Out of scope.

- **Scan absorbs Cancel.** 3a's strip has one button. While `IsScanning` the same button becomes `Cancel` bound to `CancelCommand`, because deleting the only cancel affordance would be a functional regression, and a second permanent button is not what the artboard shows. **The flip is implemented entirely with `Setter`s inside one `BasedOn` style — see D-7 and R12; a local `Content=`/`Command=` attribute would outrank the trigger and silently kill cancellation.**

- **T-004 is the sole owner of `TabControl_SelectionChanged`, and lands its final shape.** No other task in this epic edits that method. The final shape is `Tag`-based routing that keeps the `_savedPreviewVisible` / `_savedAnalyticsVisible` snapshot and keeps a live `history` branch. The competing plan (T-008 deleting the History branch as dead code and dropping the `_saved*` fields) is **rejected on 3a grounds, not on ordering grounds**: 3a's `260 | 1 | 1fr | 1 | 360` grid — Scope on the left, Preview and Rules on the right — is the layout of the **Duplicates results editor**, not of the shell. Folders and History are their own editor tabs and 3a gives neither a preview or rules stack. So hiding preview + analytics when Folders or History is selected, and restoring them on Duplicates, is 3a-correct and permanent. The History branch is dead *today* only because the header is a `TextBlock`; T-004 revives it deliberately. If T-008 concludes the right stack should instead be shell-level and span all three tabs, that is a change to the **frame**, and it comes back through this spec's contract as an explicit amendment — never as a silent delete of a method T-008 does not own. T-008 cites D-15; T-008 does not touch `MainWindow.xaml.cs`'s routing.

- **T-004 declares no design tokens and invents no key names.** Every colour, font, weight, metric and button style is consumed from T-001 / T-003 at **their published spelling**, in the canonical `Broadsheet.*` namespace (`Broadsheet.Metric.TitleBarHeight` = 34, `Broadsheet.Metric.TabStripHeight` = 38 are already published — T-004 consumes them and declares no size of its own). The role-equivalent names an earlier draft of this spec used (`Brush.Bg`, `Style.Button.Primary`, `Size.TitleBar.Height`) were a third naming scheme and are withdrawn. The mechanical guard is D-2's pre-flight plus `ResourceKeyIntegrityTests`, which fails red on any key that does not resolve in the merged application dictionary.
